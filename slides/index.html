OVN sits on top of OVS in all major Red Hat networking products

OVS and OVN are foundational to Red Hat's networking strategy. OVS provides the data plane - the actual packet switching. OVN provides the control plane - the logical network abstractions. In RHOSP, we migrated from ML2/OVS to ML2/OVN. RHOSO uses OVN natively. OpenShift uses OVN-Kubernetes as the default CNI. Even RHEL ships OVS for general-purpose virtual switching.

A Brief History

  • 2009 - Open vSwitch created at Nicira
  • 2012 - VMware acquires Nicira
  • 2013 - OVS becomes a Linux Foundation project
  • 2015 - OVN announced as OVS subproject
  • 2017 - Red Hat adopts OVN for OpenStack
  • 2019 - OVN-Kubernetes becomes OCP default CNI
  • 2021 - OVN becomes independent project under OVS umbrella
  • 2023+ - RHOSO uses OVN natively; continued evolution
Understanding the history helps contextualize why things are the way they are. OVS started at Nicira as a production-quality virtual switch. When OVN was created in 2015, the goal was to provide a native virtual networking layer on top of OVS, eliminating the need for external controllers for common use cases. Red Hat has been a major contributor to both projects.

Networking Refresher

Building a common foundation

Let us start with a networking refresher. Even experienced engineers benefit from revisiting the fundamentals, because OVS and OVN operate at specific layers of the stack and understanding where they fit is critical.

L2/L3 Recap

Layer 2 - Data Link

  • MAC addresses (48-bit)
  • Ethernet frames
  • Switching (MAC learning)
  • Broadcast domain
  • ARP for MAC discovery

Layer 3 - Network

  • IP addresses (IPv4/IPv6)
  • IP packets
  • Routing (longest prefix match)
  • Subnet boundaries
  • TTL, fragmentation
OVS operates at L2-L4 | OVN adds logical L2 and L3 abstractions
Layer 2 is about local network delivery using MAC addresses. A switch learns which MAC is on which port and forwards accordingly. Layer 3 is about routing between networks using IP addresses. OVS can match and act on fields from L2 through L4. OVN builds logical switches (L2) and logical routers (L3) on top of OVS flows.

Ethernet Frame Structure

| Dst MAC (6B) | Src MAC (6B) | 802.1Q (4B) | EtherType (2B) | Payload (46-1500B) | FCS (4B) |
                                     optional
                                   VLAN tag

  802.1Q Tag breakdown:
  | TPID: 0x8100 (2B) | PCP (3b) | DEI (1b) | VLAN ID (12b) |
                                                       0-4095
This is the structure of an Ethernet frame. The key fields for our purposes are the source and destination MAC addresses, the optional 802.1Q VLAN tag (which OVS uses extensively), and the EtherType which identifies the payload protocol. The VLAN ID is 12 bits, giving us 4096 possible VLANs - a limitation that drives the need for overlay technologies.

VLANs allow us to segment a physical network into isolated broadcast domains. VM A and VM C are in the same VLAN 100 and can communicate at L2 even though they are on different ports. VM B in VLAN 200 is isolated from them. Trunk ports carry traffic for multiple VLANs between switches. The 4094 VLAN limit is one reason we need overlay technologies in cloud environments.

Network Overlays - Why?

Problems with Physical Networking

  • VLAN limit (4094)
  • Spanning tree complexity
  • MAC table exhaustion
  • L2 domain tied to physical topology
  • VM migration across L3 boundaries

Overlays Solve This

  • Millions of logical networks (24-bit VNI)
  • Decouple logical from physical
  • Tunnel over any IP network
  • VM mobility across L3
  • Multi-tenant isolation
Cloud environments can have thousands of tenants, each needing isolated networks. 4094 VLANs is not enough. Physical topology changes require network reconfiguration. Overlay networks solve these problems by encapsulating tenant traffic in tunnels over the existing physical network. The logical topology is completely decoupled from the physical one. This is fundamental to how OVN works.

VXLAN / Geneve Encapsulation

Original Frame:
| Eth Hdr | IP Hdr | TCP/UDP | Payload |

After Encapsulation:
| Outer Eth | Outer IP | Outer UDP | VXLAN/Geneve Hdr | Original Frame |
  ^              ^             ^                ^
  Physical       Tunnel        dst:4789(VXLAN)  VNI (24-bit)
  Network        Endpoints     dst:6081(Geneve) = 16M networks

VXLAN

  • UDP port 4789
  • Fixed 8-byte header
  • 24-bit VNI
  • Widely supported

Geneve (OVN default)

  • UDP port 6081
  • Variable-length header with TLV options
  • 24-bit VNI
  • Extensible metadata
Both VXLAN and Geneve encapsulate the original Ethernet frame inside a UDP packet with a tunnel header. The VNI (Virtual Network Identifier) is 24 bits, giving about 16 million logical networks. OVN uses Geneve by default because its variable-length TLV options allow OVN to pass metadata like logical ingress port and datapath information through the tunnel. This metadata is essential for OVN's distributed processing model.

SDN separates what to do (control plane) from how to do it (data plane)
Software Defined Networking separates the network intelligence (control plane) from the packet forwarding (data plane). This is exactly what OVS and OVN do - OVN is the controller that computes the rules, OVS is the switch that applies them. The CMS - like OpenStack or Kubernetes - tells OVN what the desired network state should be.

OVS Deep Dive

The data plane workhorse

Now let us get into OVS itself. We will look at its architecture, components, and how it processes packets. This is the foundation everything else builds on.

What is Open vSwitch?

  • Production-quality, multilayer virtual switch
  • Designed for massive network automation
  • Supports standard management interfaces and protocols
  • Licensed under Apache 2.0

Why Not Linux Bridge?

  • No OpenFlow support
  • Limited programmability
  • No tunneling (built-in)
  • No fine-grained flow control

OVS Advantages

  • OpenFlow programmable
  • OVSDB for config management
  • Built-in tunneling (GRE, VXLAN, Geneve)
  • QoS, mirroring, sFlow/IPFIX
OVS is not just another bridge - it is a full-featured programmable switch. While Linux bridge does basic L2 forwarding, OVS can match on dozens of packet fields, apply complex actions, tunnel traffic, enforce QoS, and be managed remotely. It is the de facto standard virtual switch for SDN environments.

This is the core OVS architecture. Three main components: ovsdb-server stores the switch configuration, ovs-vswitchd is the main daemon that processes OpenFlow rules, and the kernel module is the fast-path datapath. When a packet arrives, the kernel module checks its flow cache. On a hit, it processes the packet entirely in kernel space. On a miss, it sends the packet up to ovs-vswitchd in user space, which looks up the OpenFlow tables and installs a new datapath flow in the kernel.

ovsdb-server

  • Persistent configuration store
  • Uses OVSDB protocol (RFC 7047)
  • JSON-RPC over TCP or Unix socket
  • Stores bridges, ports, interfaces, tunnels
  • Schema-driven (strongly typed)
  • Supports transactions and monitoring

# Show schema

# Monitor changes in real time
ovsdb-client monitor Bridge

# Backup/restore
ovsdb-client backup > backup.db
ovsdb-client restore < backup.db
The ovsdb-server is the brains of the configuration. It stores everything about the switch setup - what bridges exist, what ports they have, what interfaces are connected, tunnel endpoints, QoS settings, and so on. It persists across restarts. The OVSDB protocol allows remote management, which is how OVN and other controllers interact with OVS configuration. The database file is typically at /etc/openvswitch/conf.db.

ovs-vswitchd

  • Core switching daemon
  • Implements OpenFlow switch logic
  • Manages flow tables (OpenFlow pipeline)
  • Translates OpenFlow to datapath flows
  • Handles flow cache misses from kernel
  • Manages tunnel endpoints
ovs-vswitchd is the slow path - handles cache misses and programs the fast path (kernel datapath)
ovs-vswitchd is the most important component. It implements the full OpenFlow pipeline - multiple tables, priorities, match fields, and actions. When the kernel datapath encounters a packet that does not match any cached flow, it sends it to ovs-vswitchd. The daemon evaluates the OpenFlow tables, determines the actions, sends the packet back with instructions, and installs a datapath flow in the kernel so that subsequent matching packets are handled entirely in kernel space.

OVS Kernel Module (Datapath)

  • High-performance packet processing in kernel space
  • Exact-match flow cache (megaflow cache)
  • Handles the vast majority of packets (fast path)
  • Supports hardware offload on compatible NICs

Fast Path (Kernel)

  • Packet matches cached flow
  • Process entirely in kernel
  • Microsecond latency
  • Millions of pps

Slow Path (User Space)

  • Cache miss - no matching flow
  • Sent to ovs-vswitchd via Netlink
  • OpenFlow table lookup
  • New cache entry installed
The kernel module is where performance matters. The megaflow cache stores wildcarded flow entries that can match ranges of traffic. On a cache hit, the packet is processed in kernel space at near wire speed. Only the first packet of a new flow goes to user space. This two-tier architecture gives OVS both the flexibility of OpenFlow and the performance of kernel-level switching.

This is the core packet processing flow. When a packet arrives at an OVS port, the kernel module checks the megaflow cache. If there is a match, it executes the cached actions immediately - this is the fast path and handles the vast majority of traffic. If there is no match, the packet is sent to user space via Netlink. ovs-vswitchd evaluates the OpenFlow tables, determines the correct actions, executes them on the packet, and installs a new cache entry so future packets take the fast path.

  • Each table contains flow entries with priority, match, and actions
  • Packet is matched against entries in priority order (highest first)
  • Actions include: output, drop, mod_dl_dst, resubmit, set_field
  • resubmit sends packet to another table (pipeline chaining)
OpenFlow tables form a pipeline. A packet enters table 0 and is matched against flow entries in priority order. The matching entry's actions are executed. A key action is resubmit, which sends the packet to another table for further processing. This allows building complex multi-stage pipelines. OVN uses about 30+ tables in its pipeline for ingress and egress processing.

OpenFlow: Match/Action

# Simple L2 forwarding
ovs-ofctl add-flow br0 "table=0, dl_dst=00:11:22:33:44:55, actions=output:3"

# VLAN tagging
ovs-ofctl add-flow br0 "table=0, in_port=1, actions=mod_vlan_vid:100,output:2"

# VLAN stripping
ovs-ofctl add-flow br0 "table=0, in_port=2, dl_vlan=100, actions=strip_vlan,output:1"

# IP-based routing
ovs-ofctl add-flow br0 "table=0, ip, nw_dst=10.0.1.0/24, \
  actions=mod_dl_dst:00:aa:bb:cc:dd:ee,output:4"

# Drop by source MAC
ovs-ofctl add-flow br0 "table=0, dl_src=de:ad:be:ef:00:01, actions=drop"

# Resubmit to next table
ovs-ofctl add-flow br0 "table=0, ip, actions=resubmit(,10)"
Here are concrete examples of OpenFlow flows. Each flow has a match part and an action part. You can match on any combination of L2, L3, and L4 fields. Actions can modify headers, output to ports, drop packets, or resubmit to other tables. In practice, OVN generates thousands of these flows automatically. Understanding this syntax is crucial for troubleshooting because you will often need to read OVS flow dumps to diagnose issues.

Learning to read flow dumps is an essential troubleshooting skill. The cookie helps trace which OVN logical flow generated this OpenFlow rule. The n_packets counter tells you whether traffic is actually hitting a flow - if the counter is zero, packets are not reaching that point in the pipeline. The priority determines match order within a table - when troubleshooting, always check if a higher-priority rule is matching first.

OVN Deep Dive

Logical networking at scale

Now we move to OVN - the layer that provides logical networking abstractions on top of OVS. OVN is what makes OVS usable at cloud scale without requiring manual flow programming.

What is OVN?

  • Open Virtual Network - network virtualization for OVS
  • Provides logical switches, routers, ACLs, DHCP, NAT, LB
  • Distributed architecture - no single point of failure
  • Native OVS integration (same project community)
  • Replaced external SDN controllers for common use cases
OVN translates high-level network intent into low-level OVS flows across all hosts
OVN was created to provide the common networking services that every cloud needs - switching, routing, security, DHCP - without requiring an external SDN controller. It is tightly integrated with OVS and uses the same database technology. OVN's key innovation is distributed processing - each compute node has an ovn-controller that locally programs OVS flows, so there is no centralized bottleneck for data plane operations.

Distributed vs Gateway Routers

Distributed Router

  • Runs on every compute node
  • Handles east-west routing locally
  • No hairpinning through central node
  • Optimal for inter-subnet VM traffic
  • Cannot perform SNAT (no single egress)

Gateway Router

  • Bound to specific chassis (gateway nodes)
  • Handles north-south traffic
  • Performs SNAT, DNAT
  • Connects to provider/external networks
  • HA via gateway_chassis or HA chassis group
Modern OVN uses a single router with distributed + gateway ports - east-west traffic stays distributed, north-south goes through gateway chassis
In older OVN versions, you had separate distributed and gateway routers. Modern OVN combines both concepts in a single logical router. East-west traffic between subnets is routed locally on the compute node where the source VM runs - this is the distributed part. North-south traffic that needs SNAT or access to external networks is redirected to a gateway chassis - this is the gateway part. The gateway chassis is configured per router port using gateway_chassis options.

  • Applied per logical switch or port group

OVN ACLs implement security rules using conntrack (connection tracking). OVN provides several built-in services. DHCP is handled natively within OVN - the DHCP response is generated locally by ovn-controller on each node, so there is no network dependency on a remote DHCP server. NAT is configured on logical routers - SNAT maps internal IPs to an external IP for outbound traffic, DNAT maps external IPs to internal IPs for inbound (floating IPs in OpenStack). Load balancing provides L4 distribution of traffic to multiple backends, which is how Kubernetes services work in OVN-Kubernetes.

OVN High Availability

Database HA (RAFT)

  • NB and SB DBs use OVSDB RAFT clustering
  • 3 or 5 node cluster
  • Automatic leader election
  • Survives minority failures

Gateway HA

  • Multiple gateway chassis per router port
  • BFD-based liveness detection
  • Automatic failover
  • Priority-based selection

ovn-northd HA

  • Active-passive with RAFT leader as coordinator
  • Only the active instance processes changes
  • Standby instances ready to take over
OVN provides HA at every level. The databases use RAFT consensus clustering - typically 3 nodes, where the cluster continues operating as long as a majority (2 of 3) are healthy. ovn-northd runs in active-standby mode with RAFT-based coordination. Gateway ports have multiple chassis with priorities and BFD-based health checking - if the active gateway node fails, traffic automatically moves to the next priority chassis. In RHOSP and RHOSO, these HA mechanisms are configured out of the box.

Ingress Pipeline

  1. Port Security (L2 check)
  2. Pre-ACL
  3. ACL (conntrack, allow/drop)
  4. QoS
  5. LB (load balancer DNAT)
  6. Stateful
  7. Pre-Hairpin
  8. L2 Lookup (MAC learning)
  9. Destination Lookup

  1. Pre-LB
  2. Pre-ACL
  3. LB
  4. ACL (egress security)
  5. Stateful
  6. Port Security (L2/L3)
  7. Delivery

Use ovn-sbctl lflow-list to see the logical flows organized by table

OVN logical flows are organized into an ingress pipeline and an egress pipeline, each with multiple stages. The ingress pipeline processes traffic coming into a logical port - checking port security, applying ACLs with connection tracking, doing load balancer DNAT, and looking up the destination MAC. The egress pipeline runs on the destination side - applying egress ACLs, checking port security again, and delivering the packet. Understanding these stages is crucial for interpreting ovn-trace output.

DHCP is handled natively by OVN on each compute node. Routing is distributed - east-west traffic stays local. Only SNAT/floating IP traffic goes to the gateway nodes. The OVN databases run in a RAFT cluster across the controller nodes for HA. This architecture scales better and eliminates the network node bottleneck.

If that looks correct, move to ofproto/trace to verify the OpenFlow translation is correct. End-to-End Trace Example

# Step 1: Logical trace (OVN level)
ovn-trace --detailed ls1 \
  'inport=="port1" && eth.src==fa:16:3e:aa:bb:cc && \
   eth.dst==fa:16:3e:dd:ee:ff && ip4.src==10.0.0.11 && \
   ip4.dst==10.0.0.12'

# Step 2: OpenFlow trace (OVS level)
ovs-appctl ofproto/trace br-int \
  in_port=5,dl_src=fa:16:3e:aa:bb:cc,dl_dst=fa:16:3e:dd:ee:ff,\
  dl_type=0x0800,nw_src=10.0.0.11,nw_dst=10.0.0.12

# Step 3: Check actual traffic (wire level)
tcpdump -i tap-port1 -nn icmp
tcpdump -i genev_sys_6081 -nn  # check tunnel traffic
This is the three-step trace methodology in practice. First, ovn-trace confirms that OVN's logical pipeline would allow and correctly route the packet. Second, ofproto/trace confirms that the OpenFlow rules on the local OVS actually implement the expected behavior. Third, tcpdump on the relevant interfaces confirms that packets are actually flowing. If step 1 shows the right result but step 2 does not, the problem is in ovn-controller's translation. If step 2 is correct but step 3 shows no traffic, the problem is upstream of OVS.

Troubleshooting

Real-world scenarios and solutions

Let us put everything together with real-world troubleshooting scenarios. These are based on common support cases and production issues.

Troubleshooting Methodology

  1. Define the problem - what exactly is broken? Scope?
  2. Check the obvious - services running? DB connectivity?
  3. Verify logical config - is the intent correct in NB DB?
  4. Check bindings - are ports bound to the right chassis?
  5. Trace the path - where does the packet get dropped?
  6. Check physical - tunnels up? MTU correct? Firewall?
  7. Correlate logs - errors in OVS/OVN/CMS logs?
Always follow a structured approach. Random debugging wastes time. Start by clearly defining the problem - is it all traffic or specific flows? All VMs or one VM? Then check the basics - are services running, can ovn-controller reach the SB DB? Then work through the stack methodically. Many issues are misconfigurations in the NB DB or incorrect port bindings. Others are physical issues like MTU mismatches on the underlay network that cause tunnel packet fragmentation.

Scenario 1: VM Cannot Reach External Network

Symptom

VM can ping other VMs on the same subnet but cannot reach the external network

Investigation Steps

  1. Check if floating IP / SNAT is configured: 
    ovn-nbctl lr-nat-list <router>
  2. Check gateway chassis assignment: 
    ovn-nbctl lrp-get-gateway-chassis <router-port>
  3. Check gateway chassis is reachable: 
    ovn-sbctl list Chassis | grep -A5 <gateway-hostname>
  4. Trace the path: 
    ovn-trace --detailed <switch> '...'
This is one of the most common support cases. The VM can communicate locally but not externally. The checklist: First, is there a SNAT rule or floating IP? Without NAT, the VM has no way to reach the external network. Second, is a gateway chassis assigned? Without it, there is nowhere to perform the NAT. Third, is the gateway chassis actually reachable? Check BFD status and tunnel connectivity. Fourth, trace the packet to see where it gets dropped. Common root causes: missing NAT rule, no gateway chassis, gateway node unreachable, br-ex misconfiguration on the gateway node.

Scenario 2: Intermittent Pod Connectivity

Symptom

Pods intermittently lose connectivity to services; some requests timeout

Investigation Steps

  1. Check ovn-controller status on affected nodes: 
    ovn-appctl -t ovn-controller connection-status
ovn-appctl -t ovn-controller coverage/show
  2. Check for SB DB replication lag: 
    ovs-appctl -t /var/run/ovn/ovnsb_db.ctl cluster/status OVN_Southbound
  3. Check OVS flow count and datapath stats: 
    ovs-ofctl dump-flows br-int | wc -l
ovs-appctl coverage/show | grep -i flow
  4. Check for conntrack table exhaustion: 
    conntrack -C   # current count
cat /proc/sys/net/netfilter/nf_conntrack_max
Intermittent issues are harder to diagnose. Common causes include ovn-controller losing its connection to the SB DB, causing flows to become stale. SB DB replication lag can cause inconsistent state across nodes. High flow counts can exhaust OVS table space or slow down recomputation. Conntrack table exhaustion causes new connections to be dropped. Start by checking component health and connectivity, then look at resource utilization.

Scenario 3: Security Group Rules Not Applied

Symptom

A new security group rule is not taking effect - traffic still blocked/allowed

Investigation Steps

  1. Verify rule exists in NB DB: 
    ovn-nbctl acl-list <switch>
ovn-nbctl list ACL
  2. Check if logical flows are generated: 
    ovn-sbctl lflow-list <switch> | grep "acl"
  3. Trace with OVN: 
    ovn-trace --detailed <switch> '...'
  4. Check conntrack state (stale entries may persist): 
    conntrack -L | grep <ip>
Security group issues often involve conntrack. OVN ACLs are stateful - they use connection tracking. If you add a rule to block traffic but there is already an established conntrack entry, the existing connection may continue until it times out. To immediately enforce, you may need to flush the conntrack entry. Also check the priority of ACLs - a higher-priority allow rule may be overriding your new deny rule. Use ovn-trace to see exactly which ACL rule matches.

MTU: A Frequent Troublemaker

  • Standard Ethernet MTU: 1500 bytes
  • Geneve encapsulation overhead: ~58 bytes
  • Inner MTU must be: 1500 - 58 = 1442 bytes (or raise outer)

Symptoms of MTU Issues

  • Ping works, HTTP fails
  • SSH connects, SCP hangs
  • Small packets OK, large ones drop
  • Path MTU Discovery (PMTUD) failures

Solutions

  • Set jumbo frames (9000) on physical
  • Or reduce VM/pod MTU to 1442
  • Verify: ip link show on all hops
  • Test: ping -M do -s 1400 <dest>
MTU issues are one of the most common and most frustrating networking problems in overlay networks. The Geneve header adds about 58 bytes of overhead. If the physical network MTU is 1500, then the maximum inner packet size is 1442 bytes. Larger packets either get fragmented (adding overhead and reducing performance) or get dropped if DF (Don't Fragment) is set. The classic symptom is that ping works (small packets) but applications fail or hang (large packets). Either increase the physical network MTU to 9000 (jumbo frames) or ensure all VMs and pods have their MTU set to 1442.

Limitations & Wrap-up

What to watch out for and next steps

Let us close with the important limitations to be aware of, key takeaways, and resources for continued learning.

OVS Limitations

  • Flow table size - very large flow counts impact revalidation time
  • First packet latency - cache miss requires userspace processing
  • Kernel module dependency - must match kernel version
  • No native L3 routing - requires external controller or OVN
  • DPDK complexity - CPU pinning, hugepages, PMD tuning
  • Limited hardware offload support - vendor-specific, partial coverage
OVS is powerful but has limitations. Very large flow tables (tens of thousands) can cause slow revalidation cycles. The first packet of a new flow always takes the slow path through userspace. The kernel module must be compatible with the running kernel, which can complicate upgrades. OVS-DPDK provides high performance but at the cost of significant configuration complexity. Hardware offload is improving but still limited to specific NIC vendors and specific match/action combinations.

OVN Limitations

  • Scale ceiling - SB DB replication becomes bottleneck at very large scale
  • Recomputation time - large topology changes can cause flow churn
  • No L7 features - no application-layer inspection or policy
  • Limited load balancing - L4 only, basic algorithms (no health checks)
  • RAFT cluster sensitivity - requires stable low-latency interconnect
  • Debugging complexity - multiple abstraction layers to trace through
OVN's scale ceiling is primarily the Southbound database. In very large deployments (thousands of nodes, hundreds of thousands of ports), the SB DB replication and ovn-controller recomputation can become slow. OVN operates at L2-L4 only - if you need L7 policies, you need additional components. The load balancer is basic compared to dedicated solutions. RAFT clustering requires reliable, low-latency network between the cluster members - running the cluster across high-latency links can cause instability.

If recomputation exceeds a few seconds, you may see transient connectivity issues during configuration changes. Regular DB compaction and monitoring these metrics is essential at scale.

Performance Tuning Tips

OVS Tuning

  • Increase handler and revalidator threads
  • Tune megaflow cache size
  • Enable DPDK for high throughput
  • CPU isolation for PMD threads
  • Jumbo frames on physical network

OVN Tuning

  • Minimize ACL count (use port groups)
  • DB compaction schedule
  • Monitor ovn-controller CPU usage
  • Tune inactivity_probe on DB connections
  • Consider incremental processing (default in newer versions)
For OVS, the main tuning levers are thread counts, cache sizes, and optionally DPDK. For OVN, the focus is on reducing flow count (port groups help consolidate ACLs), keeping the database compact, and ensuring ovn-controller has enough CPU for timely recomputation. Newer OVN versions have incremental processing which significantly reduces recomputation time by only updating the affected flows rather than recomputing everything.

Key Takeaways

  1. OVS is the data plane - the highway that carries packets
  2. OVN is the control plane - the traffic management system
  3. They work together - OVN programs OVS, never replace each other
  4. Distributed architecture - routing and switching happen locally on each node
  5. Troubleshoot top-down - logical config → flows → wire
  6. Tools are your friends - ovn-trace, ofproto/trace, tcpdump
  7. It is the same OVN - skills transfer across RHOSP, RHOSO, and OCP
If you remember nothing else from this workshop, remember these seven points. OVS and OVN are complementary - OVN provides the brains, OVS provides the muscle. The distributed architecture is what makes it scale. Always troubleshoot from the top (logical intent) down to the bottom (physical packets). And the skills you build transfer across all Red Hat products that use OVN.
