Module 11: Management and Tooling Reference

Overview

This module is a comprehensive reference for every command-line tool you will use when managing, inspecting, and troubleshooting OVS and OVN. Earlier modules introduced these tools in context; this module consolidates them into a single reference with complete syntax, practical examples, and tips for daily operations.

Keep this module open when working on a live system. When a customer opens a case and you need to quickly check bridge configuration, dump flows, trace a packet, or inspect the OVN database, you will find the exact command here.

OVS Management Tools

ovs-vsctl - Switch/Bridge Management

Purpose: Configure the OVS database (ovsdb). This is the primary tool for creating and managing bridges, ports, and interfaces. It communicates with the ovsdb-server daemon.

How it works: ovs-vsctl reads from and writes to the Open_vSwitch database schema. Every bridge, port, interface, and configuration parameter is stored in this database. Changes made with ovs-vsctl take effect immediately - ovs-vswitchd monitors the database and applies changes as they are committed.

Common Commands

show - Display current configuration:

sudo ovs-vsctl show
a1b2c3d4-e5f6-7890-abcd-ef1234567890
    Bridge br-int
        fail_mode: secure
        Port br-int
            Interface br-int
                type: internal
        Port "tap12345678-90"
            Interface "tap12345678-90"
        Port "ovn-node2-0"
            Interface "ovn-node2-0"
                type: geneve
                options: {csum="true", key=flow, remote_ip="172.16.0.2"}
    Bridge br-ex
        Port br-ex
            Interface br-ex
                type: internal
        Port "eth1"
            Interface "eth1"
    ovs_version: "3.1.0"

add-br / del-br - Bridge management:

# Create a bridge
sudo ovs-vsctl add-br br-test

# Create a bridge with a specific datapath type (e.g., netdev for DPDK)
sudo ovs-vsctl add-br br-dpdk -- set bridge br-dpdk datapath_type=netdev

# Delete a bridge (also removes all ports on it)
sudo ovs-vsctl del-br br-test

# List all bridges
sudo ovs-vsctl list-br

add-port / del-port - Port management:

# Add a port to a bridge
sudo ovs-vsctl add-port br-int eth2

# Add a port with a specific type
sudo ovs-vsctl add-port br-int vxlan0 -- set interface vxlan0 \
  type=vxlan options:remote_ip=172.16.0.2

# Add a port with a VLAN tag
sudo ovs-vsctl add-port br-int vlan100 tag=100 -- set interface vlan100 type=internal

# Add a bond (two interfaces bonded together)
sudo ovs-vsctl add-bond br-int bond0 eth1 eth2

# Delete a port
sudo ovs-vsctl del-port br-int eth2

# List ports on a bridge
sudo ovs-vsctl list-ports br-int

set / get / list / find - Database operations:

# List all records in a table
sudo ovs-vsctl list bridge
sudo ovs-vsctl list port
sudo ovs-vsctl list interface

# List a specific record
sudo ovs-vsctl list interface eth1

# Get a specific field
sudo ovs-vsctl get interface eth1 ofport
sudo ovs-vsctl get bridge br-int datapath_id
sudo ovs-vsctl get interface eth1 statistics

# Set a field
sudo ovs-vsctl set bridge br-int other_config:flow-eviction-threshold=2500
sudo ovs-vsctl set interface eth1 ingress_policing_rate=1000
sudo ovs-vsctl set interface eth1 ingress_policing_burst=100

# Find records matching a condition
sudo ovs-vsctl find interface type=geneve
sudo ovs-vsctl find port tag=100
sudo ovs-vsctl find interface ofport=-1    # find ports that failed to configure

External IDs:

External IDs are key-value metadata that OVN and other controllers attach to OVS objects. They are critical for identifying which OVN logical port corresponds to which OVS port.

# View external IDs on a port
sudo ovs-vsctl get interface tap12345678-90 external_ids

# Example output:
# {iface-id="port-uuid-1234", iface-status=active}

# Set an external ID
sudo ovs-vsctl set interface tap12345678-90 \
  external_ids:iface-id="port-uuid-1234"

# Find a port by its OVN iface-id
sudo ovs-vsctl find interface external_ids:iface-id="port-uuid-1234"
Key Concept

The iface-id external ID is how ovn-controller binds an OVS port to an OVN logical port. When you create a VM or pod, the orchestrator (Nova, kubelet) creates the OVS port and sets iface-id to the OVN logical port UUID. ovn-controller sees this and claims the port binding in the Southbound database. If iface-id is missing or wrong, the port will not be bound and the VM/pod will have no network connectivity.

Useful One-Liners

# Show all ports with their OVN iface-ids
sudo ovs-vsctl --columns=name,external_ids list interface | \
  grep -A1 "iface-id"

# Show all tunnel ports
sudo ovs-vsctl find interface type=geneve
sudo ovs-vsctl find interface type=vxlan

# Show bridge fail mode
sudo ovs-vsctl get bridge br-int fail_mode

# Count total ports on br-int
sudo ovs-vsctl list-ports br-int | wc -l

# Show OVS version
sudo ovs-vsctl --version

# Check if a specific port exists
sudo ovs-vsctl port-to-br tap12345678-90

ovs-ofctl - OpenFlow Management

Purpose: Interact directly with the OpenFlow tables on an OVS bridge. This is the tool for inspecting, adding, modifying, and deleting flow entries.

Common Commands

dump-flows - Show all flow entries:

# Dump all flows on br-int
sudo ovs-ofctl dump-flows br-int

# Specify OpenFlow protocol version (OVN uses OpenFlow 1.5)
sudo ovs-ofctl dump-flows br-int -O OpenFlow15

# Sort by table number for readability
sudo ovs-ofctl dump-flows br-int -O OpenFlow15 --sort=table

# Filter flows by table
sudo ovs-ofctl dump-flows br-int -O OpenFlow15 table=0

# Filter flows matching specific criteria
sudo ovs-ofctl dump-flows br-int -O OpenFlow15 "ip,nw_dst=10.0.0.1"
sudo ovs-ofctl dump-flows br-int -O OpenFlow15 "in_port=5"
sudo ovs-ofctl dump-flows br-int -O OpenFlow15 "cookie=0x4a5c0b13/-1"

When working with OVN-managed bridges, always use -O OpenFlow15 (or -O OpenFlow13 at minimum). OVN programs flows using features from OpenFlow 1.3+. Without specifying the protocol version, ovs-ofctl defaults to OpenFlow 1.0, which cannot display many OVN flows correctly.

add-flow / del-flows / mod-flows - Flow manipulation:

# Add a flow (for standalone OVS, not OVN-managed bridges)
sudo ovs-ofctl add-flow br-test \
  "table=0,priority=100,in_port=1,ip,actions=output:2"

# Delete all flows in a table
sudo ovs-ofctl del-flows br-test "table=0"

# Delete flows matching specific criteria
sudo ovs-ofctl del-flows br-test "in_port=1"

# Modify existing flows
sudo ovs-ofctl mod-flows br-test \
  "table=0,priority=100,in_port=1,ip,actions=output:3"

Never add, delete, or modify flows on a bridge managed by OVN (br-int). The ovn-controller daemon will overwrite your changes during its next reconciliation cycle.

dump-ports - Port statistics:

sudo ovs-ofctl dump-ports br-int
sudo ovs-ofctl dump-ports br-int tap12345678-90
OFPST_PORT reply (xid=0x4): 15 ports
  port  5: rx pkts=15234, bytes=1827410, drop=0, errs=0, frame=0, over=0, crc=0
           tx pkts=12456, bytes=1123456, drop=0, errs=0, coll=0

Non-zero drop counters indicate packets being dropped at the port level.

dump-ports-desc - Port descriptions:

sudo ovs-ofctl dump-ports-desc br-int -O OpenFlow15

snoop - Watch OpenFlow messages:

sudo ovs-ofctl snoop br-int

Tips for Filtering Flow Output

# Count flows per table
sudo ovs-ofctl dump-flows br-int -O OpenFlow15 | \
  grep -oP 'table=\d+' | sort | uniq -c | sort -rn

# Find flows with zero packet counts
sudo ovs-ofctl dump-flows br-int -O OpenFlow15 | grep "n_packets=0"

# Find flows matching a specific IP
sudo ovs-ofctl dump-flows br-int -O OpenFlow15 | grep "10\.0\.0\.1"

ovs-dpctl - Datapath Management

Purpose: Interact with the OVS kernel datapath - the fast-path component that caches forwarding decisions.

Understanding the Datapath

OVS has two flow processing levels:

  1. OpenFlow tables (in ovs-vswitchd) - the full pipeline.

  2. Datapath flow cache (in kernel) - simplified exact-match flows for fast forwarding.

Cache hits are forwarded entirely in the kernel (fast path). Cache misses go to ovs-vswitchd (slow path).

# Show cached datapath flows
sudo ovs-dpctl dump-flows
sudo ovs-appctl dpctl/dump-flows

# Show datapath ports and statistics
sudo ovs-dpctl show
Key Concept

Datapath flows are not the same as OpenFlow flows. OpenFlow flows define policy (with wildcards). Datapath flows are cached exact-match results of evaluating specific packets. There can be many datapath flows for a single OpenFlow flow.

ovs-appctl - Runtime Commands

Purpose: Send runtime commands to running OVS daemons.

ofproto/trace - Packet simulation (see Module 10 for details):

sudo ovs-appctl ofproto/trace br-int \
  "in_port=5,tcp,dl_src=fa:16:3e:aa:bb:cc,dl_dst=fa:16:3e:dd:ee:ff,\
   nw_src=10.0.0.1,nw_dst=10.0.0.2,tp_dst=80"

fdb/show - MAC learning table:

sudo ovs-appctl fdb/show br-int

bond/show - Bond status:

sudo ovs-appctl bond/show bond0

coverage/show - Performance counters:

sudo ovs-appctl coverage/show

Key counters:

Counter Description

handler

Upcalls from kernel to userspace

flow_mod

OpenFlow flow modifications

upcall_flow_limit_hit

Upcalls dropped due to flow limit

vlog/set - Adjust log levels:

sudo ovs-appctl vlog/set ofproto:dbg
sudo ovs-appctl vlog/set ofproto:warn    # restore
sudo ovs-appctl vlog/list                # show current levels

Debug logging generates enormous output and can fill disk quickly. Always restore to warn or info after debugging.

memory/show - Memory usage:

sudo ovs-appctl memory/show

ovsdb-client - Database Client

Purpose: Direct database queries, monitoring, and dumps.

sudo ovsdb-client dump                                    # full database
sudo ovsdb-client dump Open_vSwitch Bridge                # specific table
sudo ovsdb-client monitor Open_vSwitch Interface name,ofport  # real-time changes
sudo ovsdb-client list-dbs                                # list databases
sudo ovsdb-client get-schema Open_vSwitch                 # schema

OVN Management Tools

ovn-nbctl - Northbound Database Management

Purpose: Configure OVN logical networks. The NB DB is the "intent" database describing the desired network topology.

Logical Switch Operations

sudo ovn-nbctl ls-add ls1                    # create
sudo ovn-nbctl ls-del ls1                    # delete
sudo ovn-nbctl ls-list                       # list all

# Logical switch port operations
sudo ovn-nbctl lsp-add ls1 vm1-port
sudo ovn-nbctl lsp-set-addresses vm1-port "00:00:00:00:00:01 10.0.0.1"
sudo ovn-nbctl lsp-set-port-security vm1-port "00:00:00:00:00:01 10.0.0.1"
sudo ovn-nbctl lsp-list ls1
sudo ovn-nbctl lsp-del vm1-port

Logical Router Operations

sudo ovn-nbctl lr-add lr1                    # create
sudo ovn-nbctl lr-del lr1                    # delete
sudo ovn-nbctl lr-list                       # list all

# Router port operations
sudo ovn-nbctl lrp-add lr1 lr1-ls1 00:00:00:aa:aa:01 10.0.0.254/24
sudo ovn-nbctl lrp-list lr1
sudo ovn-nbctl lrp-del lr1-ls1

Connect a logical switch to a router:

sudo ovn-nbctl lsp-add ls1 ls1-lr1
sudo ovn-nbctl lsp-set-type ls1-lr1 router
sudo ovn-nbctl lsp-set-addresses ls1-lr1 router
sudo ovn-nbctl lsp-set-options ls1-lr1 router-port=lr1-ls1

Static routes:

sudo ovn-nbctl lr-route-add lr1 0.0.0.0/0 203.0.113.254
sudo ovn-nbctl lr-route-list lr1
sudo ovn-nbctl lr-route-del lr1 0.0.0.0/0

NAT rules:

sudo ovn-nbctl lr-nat-add lr1 snat 203.0.113.1 10.0.0.0/24
sudo ovn-nbctl lr-nat-add lr1 dnat_and_snat 203.0.113.50 10.0.0.1
sudo ovn-nbctl lr-nat-list lr1
sudo ovn-nbctl lr-nat-del lr1 dnat_and_snat 203.0.113.50

ACL Operations

# Allow incoming TCP port 80
sudo ovn-nbctl acl-add ls1 to-lport 1000 \
  'outport == "vm1-port" && tcp.dst == 80' allow-related

# Deny all other incoming traffic
sudo ovn-nbctl acl-add ls1 to-lport 900 \
  'outport == "vm1-port"' drop

# Allow all outgoing traffic
sudo ovn-nbctl acl-add ls1 from-lport 1000 \
  'inport == "vm1-port"' allow-related

sudo ovn-nbctl acl-list ls1

Port Groups:

sudo ovn-nbctl pg-add web-servers vm1-port vm2-port vm3-port
sudo ovn-nbctl acl-add web-servers to-lport 1000 'tcp.dst == 80' allow-related
sudo ovn-nbctl pg-del web-servers
Key Concept

In OpenStack, each security group becomes an OVN port group. ACLs applied to a port group cover all member ports efficiently.

Load Balancer Operations

sudo ovn-nbctl lb-add my-lb 10.0.0.100:80 \
  10.0.0.1:8080,10.0.0.2:8080,10.0.0.3:8080
sudo ovn-nbctl ls-lb-add ls1 my-lb
sudo ovn-nbctl lr-lb-add lr1 my-lb
sudo ovn-nbctl lb-list
sudo ovn-nbctl lb-del my-lb

DHCP Operations

sudo ovn-nbctl dhcp-options-create 10.0.0.0/24
DHCP_UUID=$(sudo ovn-nbctl --bare --columns=_uuid find dhcp_options cidr="10.0.0.0/24")
sudo ovn-nbctl dhcp-options-set-options $DHCP_UUID \
  lease_time=3600 router=10.0.0.254 server_id=10.0.0.254 \
  server_mac=00:00:00:aa:aa:01 dns_server="{8.8.8.8, 8.8.4.4}"
sudo ovn-nbctl lsp-set-dhcpv4-options vm1-port $DHCP_UUID

Generic Database Operations

sudo ovn-nbctl list logical_switch
sudo ovn-nbctl find logical_switch_port type=router
sudo ovn-nbctl get logical_switch ls1 _uuid
sudo ovn-nbctl set logical_switch_port vm1-port enabled=false

ovn-sbctl - Southbound Database Management

Purpose: Inspect the compiled state in the SB DB - logical flows, port bindings, chassis registrations. You typically do not write to the SB DB directly.

show - Display chassis and port bindings:

sudo ovn-sbctl show
Chassis "node-1"
    hostname: node-1.example.com
    Encap geneve
        ip: "172.16.0.1"
        options: {csum="true"}
    Port_Binding "vm1-port"
    Port_Binding "vm2-port"
Chassis "node-2"
    hostname: node-2.example.com
    Encap geneve
        ip: "172.16.0.2"
    Port_Binding "vm3-port"
Key Concept

If a port does not appear under any chassis in ovn-sbctl show, it is unbound. An unbound port means ovn-controller on no node has claimed it - typically the OVS port with the matching iface-id does not exist or ovn-controller is not running.

lflow-list - List logical flows:

sudo ovn-sbctl lflow-list
sudo ovn-sbctl lflow-list ls1
sudo ovn-sbctl lflow-list ls1 | grep "ls_in_acl"

Each logical flow shows: Datapath, Pipeline (ingress/egress), Table, Priority, Match, Action, UUID.

Other queries:

sudo ovn-sbctl chassis-list
sudo ovn-sbctl find port_binding logical_port="vm1-port"
sudo ovn-sbctl get port_binding vm1-port chassis
sudo ovn-sbctl list mac_binding

ovn-trace - Logical Packet Tracer

Purpose: Simulate packet processing through OVN’s logical pipeline (see Module 10 for full details).

sudo ovn-trace [OPTIONS] DATAPATH MICROFLOW
Option Description

--detailed

Show every logical flow matched (default)

--summary

Key decisions only

--minimal

Just the final result

--ct new/est/rel/inv

Simulate connection tracking state

Examples:

sudo ovn-trace --detailed ls1 \
  'inport == "vm1" && eth.src == 00:00:00:00:00:01 && eth.dst == 00:00:00:00:00:02 && ip4.src == 10.0.0.1 && ip4.dst == 10.0.0.2 && ip.ttl == 64 && tcp.dst == 80'

sudo ovn-trace --ct new --detailed ls1 \
  'inport == "vm-client" && eth.src == 00:00:00:00:00:50 && eth.dst == 00:00:00:00:01:00 && ip4.src == 10.0.0.50 && ip4.dst == 10.0.0.100 && ip.ttl == 64 && tcp.dst == 80'

ovn-detrace - Physical to Logical Flow Mapper

Purpose: Map OVS OpenFlow cookie values back to OVN logical flows.

sudo ovs-ofctl dump-flows br-int -O OpenFlow15 | \
  ovn-detrace --ovnsb=unix:/var/run/ovn/ovnsb_db.sock

sudo ovs-appctl ofproto/trace br-int "<flow>" 2>&1 | \
  ovn-detrace --ovnsb=tcp:192.168.1.100:6642

ovn-controller appctl Commands

sudo ovs-appctl -t ovn-controller connection-status   # SB DB connection
sudo ovs-appctl -t ovn-controller ct-zone-list         # conntrack zones
sudo ovs-appctl -t ovn-controller chassis/show         # chassis info
sudo ovs-appctl -t ovn-controller recompute            # trigger flow recompute
sudo ovs-appctl -t ovn-controller vlog/set dbg         # debug logging
sudo ovs-appctl -t ovn-controller vlog/set info        # restore

If -t ovn-controller does not work, try the full path: -t /var/run/ovn/ovn-controller.<pid>.ctl.

Exercises

Exercise 11.1: OVS Database Exploration

Objective: Use ovs-vsctl to inspect the OVS configuration.

  1. Run sudo ovs-vsctl show and identify all bridges and ports.

  2. Use sudo ovs-vsctl list bridge for full database records.

  3. Use sudo ovs-vsctl find interface type=geneve to list tunnels.

  4. For each tunnel, note the remote IP and correlate with ovn-sbctl show.

Exercise 11.2: Flow Table Analysis

Objective: Analyze the flow tables on br-int.

  1. Dump all flows with sudo ovs-ofctl dump-flows br-int -O OpenFlow15 --sort=table.

  2. Count flows per table.

  3. Identify the highest-priority flow in table 0.

  4. Find flows with zero packet counts.

  5. Use ovn-detrace to annotate the flows.

Exercise 11.3: OVN Topology Mapping

Objective: Map the complete logical and physical topology.

  1. List all logical switches, routers, and ports with ovn-nbctl.

  2. List chassis and port bindings with ovn-sbctl.

  3. Determine which chassis each port is bound to.

  4. Draw the logical and physical topology.

Exercise 11.4: ACL and Security Group Analysis

Objective: Inspect ACLs and trace their effect.

  1. List ACLs with ovn-nbctl acl-list.

  2. Find corresponding logical flows with ovn-sbctl lflow-list | grep acl.

  3. Trace a packet that should be allowed.

  4. Trace a packet that should be denied.

  5. Identify the decisive table and flow.

Exercise 11.5: Runtime Diagnostics

Objective: Assess system health with runtime commands.

  1. Check ovn-controller connection status.

  2. Run ovs-appctl coverage/show and identify top counters.

  3. Run ovs-appctl memory/show and note flow rule count.

  4. Check conntrack table usage.

  5. Check OVN database sizes.

  6. Review recent logs for warnings or errors.
