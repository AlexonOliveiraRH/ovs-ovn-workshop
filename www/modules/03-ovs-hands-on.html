Module 03 - OVS Hands-On Lab

Prerequisites

Lab Environment

This lab requires a single virtual machine (or physical machine) running RHEL 9 or Fedora. All exercises run on a single node. Exercise 6 simulates two OVS instances by using network namespaces and a loopback tunnel.

Component Requirement

OS

RHEL 9.x or Fedora 38+

CPU

2+ vCPUs

RAM

2 GB minimum

Disk

10 GB free space

Access

Root or sudo privileges

Network

One management interface (for SSH)

All commands in this lab assume you are running as root or using sudo. The lab is designed to be entirely self-contained on a single machine using network namespaces to simulate virtual machines.

Required Packages

Install these packages before starting:

  • openvswitch - Provides ovs-vswitchd, ovsdb-server, and all OVS utilities

  • iproute - Provides ip command for namespace and link management

  • iperf3 - Network throughput testing (used in Exercise 8)

  • tcpdump - Packet capture and analysis (used in Exercises 6 and 7)

  • net-tools - Provides ifconfig and netstat (optional, for reference)

sudo dnf install -y openvswitch iproute iperf3 tcpdump net-tools

Exercise 1: Installing and Starting OVS

Objective: Install Open vSwitch, start its services, and verify all components are running correctly. You will learn which daemons OVS uses and how to inspect its database.

sudo dnf install -y openvswitch

Complete!

On RHEL 9, the package is available from the Fast Datapath repository. If not enabled, run sudo subscription-manager repos --enable fast-datapath-for-rhel-9-x86_64-rpms first. On Fedora, openvswitch is available in the standard repositories.

Expected output:

nf_nat                 49152  1 openvswitch
nf_defrag_ipv6         24576  1 openvswitch
libcrc32c              16384  2 openvswitch,nf_conntrack
Key Concept

OVS has two forwarding paths. The kernel module (openvswitch.ko) handles the "fast path" - once a flow is learned, packets are switched directly in the kernel for maximum performance. The ovs-vswitchd userspace daemon handles the "slow path" - the first packet of each new flow goes up to userspace for flow table lookup and classification, and then a datapath flow is installed in the kernel for subsequent packets. Think of it like a restaurant: the first order goes to the chef (userspace) who decides the recipe, and then the line cooks (kernel) prepare all identical orders automatically.

Think of it as OVS’s "memory".

What just happened?

You installed OVS and verified its three core components:

  1. ovsdb-server - The database daemon that stores all configuration (bridges, ports, flows). It is the "brain" that remembers how the switch is configured.

  2. ovs-vswitchd - The forwarding daemon that makes switching decisions. It reads from the database and programs the kernel datapath. It is the "decision maker".

  3. openvswitch kernel module - The fast-path data plane that forwards packets at near-hardware speed. It is the "muscle" that moves packets.

These three components work together: ovsdb-server stores configuration, ovs-vswitchd reads it and makes forwarding decisions, and the kernel module executes those decisions at high speed.

Exercise 2: Creating Your First Bridge

Objective: Create an OVS bridge, examine its properties, understand the default OpenFlow rules, and learn how the bridge appears as both a network device and a datapath.

Step 1: Create a bridge

# Create a bridge called "br0"
sudo ovs-vsctl add-br br0

Step 2: Examine the bridge

# Show the OVS configuration (now includes the bridge)
sudo ovs-vsctl show

Expected output:

a1b2c3d4-e5f6-7890-abcd-ef1234567890
    Bridge br0
        Port br0
            Interface br0
                type: internal
    ovs_version: "3.3.0"
Key Concept

When you create a bridge, OVS automatically creates an "internal" port with the same name. This internal port is a virtual network interface that the Linux host can use to communicate with the bridge. Think of it as the bridge having a "management port" built-in - like the management interface on a physical switch that allows the switch itself to have an IP address.

Step 3: Examine the default OpenFlow rules

# Dump the OpenFlow flow table
sudo ovs-ofctl dump-flows br0

Expected output:

 cookie=0x0, duration=45.123s, table=0, n_packets=0, n_bytes=0, priority=0 actions=NORMAL
Key Concept

The default flow rule priority=0 actions=NORMAL tells OVS to behave like a traditional learning switch. Any packet that does not match a higher-priority rule will be handled using MAC-address learning and flooding - exactly how a regular Ethernet switch works. This is the "catch-all" rule, and NORMAL means "do what a normal switch would do."

 
# Show the flow table in a more verbose format
sudo ovs-ofctl dump-flows br0 --no-stats

Expected output:

 priority=0 actions=NORMAL

Step 4: Understand the internal port

# See the bridge as a Linux network interface
ip link show br0

Expected output:

5: br0: <BROADCAST,MULTICAST> mtu 1500 qdisc noop state DOWN mode DEFAULT group default qlen 1000
    link/ether 5a:4b:3c:2d:1e:0f brd ff:ff:ff:ff:ff:ff

The interface is currently DOWN because we have not brought it up or assigned an IP address yet.

Step 5: Assign an IP to the bridge internal port

# Bring the bridge interface up and assign an IP
sudo ip addr add 10.0.0.254/24 dev br0
sudo ip link set br0 up
# Verify the IP assignment
ip addr show br0

Expected output:

5: br0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc noqueue state UNKNOWN group default qlen 1000
    link/ether 5a:4b:3c:2d:1e:0f brd ff:ff:ff:ff:ff:ff
    inet 10.0.0.254/24 scope global br0
       valid_lft forever preferred_lft forever
    inet6 fe80::584b:3cff:fe2d:1e0f/64 scope link
       valid_lft forever preferred_lft forever
Key Concept

Assigning an IP to the bridge’s internal port is like assigning a management IP to a physical switch’s SVI (Switched Virtual Interface). The host can now reach anything on the 10.0.0.0/24 network that is connected to br0. This is useful for acting as a gateway or for the host to communicate with VMs attached to the bridge.

Step 6: Show the bridge in the datapath

# Show the kernel datapath
sudo ovs-dpctl show

Expected output:

system@ovs-system:
  lookups: hit:0 missed:0 lost:0
  flows: 0
  masks: hit:0 total:0 hit/pkt:0.00
  cache: hit:0 hit-rate:0.00%
  port 0: ovs-system (internal)
  port 1: br0 (internal)
Key Concept

The ovs-dpctl show command shows the kernel-level datapath - this is the fast-path forwarding plane. Each port in the datapath has a numeric ID (port 0, port 1, etc.). When the kernel module forwards packets, it uses these port numbers. The ovs-system datapath is the default system datapath that all bridges share. Think of the datapath as the "hardware" layer of OVS, while ovs-vsctl shows the "configuration" layer.

Verification

# Confirm bridge exists and has an IP
sudo ovs-vsctl list-br
ip addr show br0 | grep "inet "
sudo ovs-ofctl dump-flows br0 --no-stats

Expected output:

br0
    inet 10.0.0.254/24 scope global br0
 priority=0 actions=NORMAL

What just happened?

You created your first OVS bridge and explored it from three different perspectives:

  1. Configuration layer (ovs-vsctl show) - Shows the bridge as a managed object in the OVSDB with its ports and interfaces.

  2. OpenFlow layer (ovs-ofctl dump-flows) - Shows the forwarding rules that govern how the bridge handles packets. The default NORMAL action means standard MAC learning.

  3. Datapath layer (ovs-dpctl show) - Shows the kernel-level forwarding plane where packets are actually moved between ports.

Think of these three layers like a building: the OVSDB is the blueprint (what the building should look like), OpenFlow is the floor plan (how traffic flows through rooms), and the datapath is the actual physical structure (where things really happen).

Try it yourself

  • Create a second bridge br-test with sudo ovs-vsctl add-br br-test, then list all bridges with sudo ovs-vsctl list-br

  • Delete the test bridge with sudo ovs-vsctl del-br br-test

  • Run sudo ovs-vsctl list Port br0 to see the port details

  • Run sudo ovs-vsctl list Interface br0 to see the interface details

  • Change the bridge’s datapath ID: sudo ovs-vsctl set Bridge br0 other_config:datapath-id=0000000000000001 and verify with sudo ovs-ofctl show br0

Exercise 3: Connecting VMs/Namespaces

Objective: Create network namespaces that simulate virtual machines, connect them to the OVS bridge using veth pairs, and verify Layer 2 connectivity and MAC learning.

Step 1: Create network namespaces

# Create two namespaces to simulate VMs
sudo ip netns add vm1
sudo ip netns add vm2
# Verify the namespaces exist
ip netns list

Expected output:

vm2
vm1
Key Concept

A Linux network namespace is an isolated copy of the network stack - it has its own interfaces, routing table, and firewall rules. It is a lightweight way to simulate a separate machine without the overhead of a full VM. In production, Docker containers and VMs each have their own network namespace. Think of a namespace as a "virtual machine" for networking purposes.

Step 2: Create veth pairs

# Create a veth pair for vm1
# One end (veth-vm1) stays on the host, the other (eth0-vm1) goes into the namespace
sudo ip link add veth-vm1 type veth peer name eth0-vm1

# Create a veth pair for vm2
sudo ip link add veth-vm2 type veth peer name eth0-vm2
# Verify the veth pairs were created
ip link show type veth

Expected output:

6: eth0-vm1@veth-vm1: <BROADCAST,MULTICAST,M-DOWN> mtu 1500 qdisc noop state DOWN mode DEFAULT group default qlen 1000
    link/ether 3e:5f:7a:9b:1c:2d brd ff:ff:ff:ff:ff:ff
7: veth-vm1@eth0-vm1: <BROADCAST,MULTICAST,M-DOWN> mtu 1500 qdisc noop state DOWN mode DEFAULT group default qlen 1000
    link/ether 4a:6b:8c:0d:2e:3f brd ff:ff:ff:ff:ff:ff
8: eth0-vm2@veth-vm2: <BROADCAST,MULTICAST,M-DOWN> mtu 1500 qdisc noop state DOWN mode DEFAULT group default qlen 1000
    link/ether 5b:7c:9d:1e:3f:4a brd ff:ff:ff:ff:ff:ff
9: veth-vm2@eth0-vm2: <BROADCAST,MULTICAST,M-DOWN> mtu 1500 qdisc noop state DOWN mode DEFAULT group default qlen 1000
    link/ether 6c:8d:0e:2f:4a:5b brd ff:ff:ff:ff:ff:ff
Key Concept

A veth (virtual Ethernet) pair is like a virtual patch cable - anything that goes in one end comes out the other. One end stays on the host and connects to the OVS bridge, while the other end goes inside the namespace to act as the "VM’s" network interface. This is exactly how Docker, libvirt, and OpenStack connect containers and VMs to virtual switches.

Step 3: Move one end into each namespace

# Move eth0-vm1 into the vm1 namespace

# Move eth0-vm2 into the vm2 namespace

# Verify - eth0-vm1 should no longer appear on the host
ip link show eth0-vm1 2>&1

# But it is visible inside the namespace
sudo ip netns exec vm1 ip link show

    link/ether 3e:5f:7a:9b:1c:2d brd ff:ff:ff:ff:ff:ff link-netnsid 0

# Add veth-vm1 and veth-vm2 to the bridge
sudo ovs-vsctl add-port br0 veth-vm1
sudo ovs-vsctl add-port br0 veth-vm2

# Bring the host-side interfaces up
sudo ip link set veth-vm1 up
sudo ip link set veth-vm2 up
# Verify the bridge now has ports

Step 7: Observe MAC learning

# Show the MAC address table (FDB - Forwarding Database)
sudo ovs-appctl fdb/show br0

Expected output:

 port  VLAN  MAC                Age
    1     0  3e:5f:7a:9b:1c:2d    5
    2     0  5b:7c:9d:1e:3f:4a    5
Key Concept

Just like a physical switch, OVS learns MAC addresses. When vm1 sends a packet, OVS sees the source MAC on port 1 and records it in the FDB (Forwarding Database). The next time a packet is destined for that MAC, OVS sends it directly to port 1 instead of flooding it to all ports. The "Age" column shows how many seconds since the MAC was last seen. This is identical to how show mac-address-table works on a Cisco switch.

Step 8: Show datapath flows

# Show the cached flows in the kernel datapath
sudo ovs-dpctl dump-flows

Expected output:

recirc_id(0),in_port(2),eth(src=3e:5f:7a:9b:1c:2d,dst=5b:7c:9d:1e:3f:4a),eth_type(0x0800),ipv4(frag=no), packets:4, bytes:392, used:0.5s, actions:3
recirc_id(0),in_port(3),eth(src=5b:7c:9d:1e:3f:4a,dst=3e:5f:7a:9b:1c:2d),eth_type(0x0800),ipv4(frag=no), packets:4, bytes:392, used:0.5s, actions:2
Key Concept

These are the kernel-level "fast path" flows. After ovs-vswitchd makes a forwarding decision for the first packet, it installs a cached flow in the kernel datapath. Subsequent matching packets are forwarded entirely in the kernel without going to userspace. This is why OVS is so fast - the slow path only handles the first packet. Think of it like GPS navigation: the first time you drive a route, you need directions (userspace), but once you know the way, you drive on autopilot (kernel).

What just happened?

You built a complete virtual network:

  1. Namespaces simulate VMs with isolated network stacks

  2. Veth pairs act as virtual cables connecting VMs to the switch

  3. OVS bridge acts as a Layer 2 switch connecting everything together

  4. MAC learning makes forwarding intelligent - OVS learns where each VM lives and sends traffic directly

This is exactly the same architecture used in production OpenStack and Kubernetes deployments. When a VM or container is created, the orchestrator creates a namespace (or the hypervisor/container runtime does), creates a veth pair, plugs one end into OVS, and assigns an IP. You just did manually what Nova or CRI-O does automatically.

Try it yourself

  • Try to ping a non-existent IP (10.0.0.99) and observe what happens in the MAC table (you will see broadcast ARP entries)

# Add the host-side ends to the bridge

Key Concept

A trunk port carries traffic from multiple VLANs simultaneously. Unlike access ports (which strip the VLAN tag), trunk ports preserve the 802.1Q VLAN tag in the Ethernet header. What just happened?

You learned the essential debugging and monitoring toolkit for OVS:

  1. ofproto/trace - The "X-ray machine" for packets. It shows exactly how a packet would be processed without sending real traffic. This is the first tool to reach for when debugging connectivity issues.

  2. FDB (MAC table) - Shows which MAC addresses have been learned on which ports. Essential for verifying L2 connectivity.

  3. Coverage counters - Internal performance metrics that help identify bottlenecks and unusual behavior.

  4. Log management - How to view, filter, and adjust OVS log levels for detailed troubleshooting.

  5. Port statistics - Traffic counters per port for identifying where packets are going (or being dropped).

In a production support scenario, when a customer reports "VM A cannot reach VM B", your debugging workflow would be: . Check fdb/show - Is the destination MAC known? . Use ofproto/trace - Does the flow pipeline forward the packet correctly? . Check dump-ports - Are packets being received/transmitted on the right ports? . Check dump-flows - Are there drop rules or unexpected matches? . Check logs - Are there errors or warnings?

Try it yourself
