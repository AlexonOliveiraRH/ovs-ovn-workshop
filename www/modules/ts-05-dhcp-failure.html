Scenario 05: VMs Not Getting DHCP Addresses

The Problem

Customer report: "New VMs in RHOSP are not getting IP addresses via DHCP. Existing VMs with static IPs work fine. The issue started after a new subnet was configured."

The customer created a new subnet "app-subnet" on network "app-net" for a new application deployment. VMs launched on this subnet boot successfully but never receive an IP address via DHCP. The VMs' DHCP clients time out after repeated DHCPDISCOVER attempts. VMs on other subnets that were created previously continue to get DHCP addresses without issues.

RHOSP 17.1: Containerized OVN Commands

In RHOSP 17.1, OVN databases run inside Pacemaker-managed containers. All ovn-nbctl and ovn-sbctl commands shown in this scenario must be executed via podman exec on the controller node. For example:

  • ovn-nbctl show becomes sudo podman exec -it ovn_cluster_north_db_server ovn-nbctl --no-leader-only show

  • ovn-sbctl show becomes sudo podman exec -it ovn_cluster_south_db_server ovn-sbctl --no-leader-only show

  • ovn-trace becomes sudo podman exec -it ovn_cluster_north_db_server ovn-trace --no-leader-only

For brevity, this scenario shows the bare commands. Refer to Module 12: RHOSP Product-Specific Troubleshooting for the full containerized command syntax.

How DHCP Works in OVN

Before diving into troubleshooting, it is important to understand how OVN handles DHCP, because it is fundamentally different from the traditional Neutron DHCP agent approach.

Key Concept

In ML2/OVN deployments, there is no DHCP agent and no dnsmasq process. OVN implements DHCP natively in the logical switching pipeline. When a VM sends a DHCP Discover, ovn-controller on the local compute node intercepts it and generates a DHCP Offer directly - the packet never leaves the compute node. This is faster and more scalable than the traditional approach, but it means DHCP troubleshooting requires understanding OVN’s logical flow pipeline rather than checking dnsmasq processes.

OVN DHCP Flow

1. VM sends DHCP Discover (broadcast)
       |
       v
2. Packet enters OVS br-int on the compute node
       |
       v
3. ovn-controller matches the packet against logical flows
   (table 19 in the ingress pipeline - DHCP responder)
       |
       v
4. If DHCP options are configured for the port:
   - OVN constructs a DHCP Offer in the pipeline
   - Sets IP, mask, gateway, DNS, MTU, lease time, etc.
   - Sends the Offer back to the VM on the same port
       |
       v
5. VM sends DHCP Request
       |
       v
6. OVN responds with DHCP Ack (same mechanism as step 3-4)
       |
       v
7. VM configures its interface with the received IP

ALL of this happens locally on the compute node.
No network traffic to controllers or DHCP servers.

How Neutron Configures OVN DHCP

1. Admin creates a subnet with DHCP enabled
       |
       v
2. Neutron ML2/OVN driver creates DHCP options in OVN NB DB:
   - ovn-nbctl dhcp-options-create <cidr>
   - Sets options: server_id, server_mac, lease_time, router, dns_server, mtu
       |
       v
3. When a port is created, Neutron associates the DHCP options with the port:
   - Sets dhcpv4_options on the logical switch port
       |
       v
4. ovn-northd compiles the DHCP options into logical flows
       |
       v
5. ovn-controller receives the logical flows and installs OpenFlow rules
   that implement the DHCP responder for each port

Key Concept

The put_dhcp_opts() action in OVN constructs the DHCP response packet. It sets reg0[3] to 1 if successful. The subsequent ls_in_dhcp_response table checks this register to decide whether to send the response. If put_dhcp_opts() fails (due to missing or invalid options), the DHCP response is never sent and the Discover packet continues through the pipeline as a regular broadcast - which also gets dropped by default ACLs since there is no DHCP server port to receive it.

Step 7: Check the Logical Switch Port Addresses

Why: The DHCP responder uses the logical switch port’s addresses field to determine what IP address to offer. If this field is wrong or uses the "dynamic" keyword incorrectly, DHCP can fail.

[root@controller-0 ~]# ovn-nbctl lsp-get-addresses c4d5e6f7-a8b9-0c1d-2e3f-4a5b6c7d8e9f
fa:16:3e:cc:44:88 192.168.200.10

Finding: The addresses field is correctly set with the MAC and IP. This is not the problem. If it had been set to "dynamic" or was empty, that could also cause DHCP issues.

OVN supports two address modes for logical switch ports: - Static: "fa:16:3e:xx:xx:xx 192.168.x.x" - MAC and IP are specified explicitly - Dynamic: "fa:16:3e:xx:xx:xx dynamic" - MAC is fixed, IP is assigned by OVN’s built-in IPAM Both modes work with DHCP, but the DHCP options must still be correctly configured.

Root Cause

The root cause is a missing DNS nameserver configuration on the Neutron subnet, which resulted in incomplete DHCP options in the OVN Northbound DB:

  1. The subnet app-subnet (192.168.200.0/24) was created with enable_dhcp: True but without specifying DNS nameservers (dns_nameservers was left empty).

  2. The Neutron ML2/OVN driver created DHCP options in the OVN NB DB, but without the dns_server option since no DNS nameservers were configured in Neutron.

  3. When VMs send DHCPDISCOVER packets, ovn-controller processes them through the logical pipeline. The put_dhcp_opts() action attempts to construct a DHCP Offer but fails because the dns_server option is missing.

  4. In this OVN version, certain DHCP options (including dns_server) are required for put_dhcp_opts() to succeed. When they are absent, reg0[3] is not set and the DHCP response is never generated.

  5. The VM’s DHCP client sends repeated Discovers but never receives an Offer, eventually timing out.

Key Concept

The difference between traditional DHCP (dnsmasq) and OVN native DHCP is important here: - dnsmasq (traditional): Acts as a full DHCP server. Can provide default values for missing options. If DNS is not configured, dnsmasq can still send a valid Offer without the DNS option. - OVN native DHCP: Constructs the DHCP response from explicitly configured options in the NB DB. In some versions, missing options that the VM’s DHCP client requested via Option 55 (Parameter Request List) can cause the response construction to fail, especially if the client’s request includes DNS as a required parameter.

Prevention

1. Always Specify DNS Nameservers When Creating Subnets

Make it a standard practice to always include DNS nameservers:

# Correct way to create a subnet:
openstack subnet create \
  --network app-net \
  --subnet-range 192.168.200.0/24 \
  --gateway 192.168.200.1 \
  --allocation-pool start=192.168.200.10,end=192.168.200.250 \
  --dns-nameserver 8.8.8.8 \
  --dns-nameserver 8.8.4.4 \
  --dhcp \
  app-subnet

2. Create a Subnet Configuration Checklist

Subnet Creation Checklist for RHOSP with ML2/OVN:
[ ] Network type and segmentation verified
[ ] CIDR and gateway configured
[ ] Allocation pool defined (avoid using .1-.9 for infrastructure)
[ ] DNS nameservers specified (minimum 1, recommended 2)
[ ] DHCP enabled (if needed)
[ ] MTU set correctly (account for Geneve overhead: 1442 for 1500 physical)
[ ] Host routes added (if needed)
[ ] Verified DHCP options in OVN NB DB after creation
[ ] Test VM launched and DHCP verified

3. Test DHCP on New Subnets Before Scheduling Workloads

After creating a subnet, always test DHCP before deploying production VMs:

# Launch a test VM:
openstack server create --flavor m1.small --image cirros --network app-net dhcp-test-vm

# Wait for it to boot, then check:
openstack server show dhcp-test-vm -c addresses

# Verify the IP was assigned via DHCP:
openstack console log show dhcp-test-vm | grep -i dhcp

# Clean up:
openstack server delete dhcp-test-vm

4. Automate Subnet Creation with Heat or Ansible

Manually Setting DHCP Options in OVN

If Neutron’s automatic DHCP option management is insufficient, you can set options directly in the OVN NB DB:

# List existing DHCP options:
ovn-nbctl dhcp-options-list

# Set a specific option:
ovn-nbctl dhcp-options-set-options <uuid> \
  server_id=192.168.200.1 \
  server_mac=fa:16:3e:00:00:02 \
  lease_time=43200 \
  router=192.168.200.1 \
  dns_server="{8.8.8.8, 8.8.4.4}" \
  mtu=1442 \
  domain_name=example.com

Manually modifying OVN DHCP options bypasses Neutron’s management. If Neutron later updates the subnet, it may overwrite your manual changes. Always prefer making changes through Neutron (openstack subnet set) rather than directly in OVN.

Key Takeaways

  • OVN handles DHCP natively without dnsmasq. There is no separate DHCP agent process to check. DHCP responses are generated locally on each compute node by ovn-controller using options configured in the OVN NB DB.

  • Missing DHCP options can silently break DHCP. Unlike dnsmasq, OVN may not provide default values for missing options. If the VM’s DHCP client requests an option (via Option 55) that is not configured, the DHCP response may fail to be generated.

  • Always configure DNS nameservers when creating subnets. This is the most common omission that breaks OVN DHCP. Even if VMs will not use DNS, configure a placeholder value.

  • ovn-trace is the definitive DHCP diagnostic tool. It shows exactly what happens to a DHCP Discover in the OVN logical pipeline, including whether put_dhcp_opts() succeeds and whether a response is generated.

  • Compare working and broken configurations side by side. When DHCP works on one subnet but not another, a direct comparison of the OVN DHCP options between the two subnets will quickly reveal the difference.
