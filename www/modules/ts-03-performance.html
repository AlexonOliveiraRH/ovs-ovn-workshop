Scenario 03: Severe Performance Degradation Under Load

The Problem

Customer report: "Network throughput between pods dropped from 9 Gbps to under 1 Gbps after deploying new security group rules. CPU usage on compute nodes is very high."

The customer recently deployed over 200 NetworkPolicy objects to meet new compliance requirements. Before the policies were applied, pod-to-pod throughput was consistently around 9.2 Gbps. After applying the policies, throughput dropped to 0.7 Gbps and applications began timing out. The ovs-vswitchd process on worker nodes is consuming near 100% of a CPU core.

Environment

Component Details

Platform

OCP 4.14 with OVN-Kubernetes

Control plane nodes

3 (control-plane-0, control-plane-1, control-plane-2)

Worker nodes

15 (worker-0 through worker-14)

Worker node specs

32 cores, 128 GB RAM, 25GbE Mellanox ConnectX-6

CNI

OVN-Kubernetes (default for OCP 4.14)

Pod network CIDR

10.128.0.0/14

Service CIDR

172.30.0.0/16

Overlay

Geneve

Recent change

200+ NetworkPolicy objects deployed

Before policies

9.2 Gbps pod-to-pod throughput

After policies

0.7 Gbps pod-to-pod throughput

Finding: The handler and revalidator threads are consuming significant CPU. Handler threads process "upcalls" (packets that miss the datapath cache and need userspace processing). Revalidator threads check that cached datapath flows are still valid. Both being heavily loaded means the fast path is not working efficiently.

Key Concept

OVS processes packets in two paths: - Fast path (kernel datapath): Packets matching an existing datapath flow are handled entirely in the kernel, achieving line-rate performance. - Slow path (userspace): Packets that don’t match any datapath flow generate an "upcall" to ovs-vswitchd in userspace. The daemon looks up the correct action in the OpenFlow tables, installs a new datapath flow for future packets, and handles the current packet. This is orders of magnitude slower than the fast path. When most packets take the slow path, performance degrades severely because every packet requires a context switch to userspace and back.

Why: A large number of OpenFlow flows in br-int causes slower flow table lookups and makes it harder for OVS to create efficient wildcard (megaflow) entries in the datapath cache. We need to see how many flows exist and how they changed.

Finding: There are 87,234 OpenFlow flows in br-int. For a typical OCP cluster, a healthy flow count ranges from 2,000 to 5,000 per node. 87,000+ is a flow explosion.

Finding: The problem is cluster-wide, not isolated to a single node. All nodes have similarly inflated flow counts because the NetworkPolicies affect the entire OVN logical topology.

Step 4: Check Datapath Flows

Why: The kernel datapath is where the fast-path processing happens. We need to check whether the datapath is able to create efficient wildcard flows (megaflows) or is being forced into per-packet (microflow) processing.

[user@bastion ~]$ oc debug node/worker-3.ocp.example.com -- chroot /host \
  ovs-appctl dpctl/dump-flows -m | wc -l
124567

Finding: 124,567 datapath flows. This is extremely high. A healthy OVS datapath typically has 5,000-20,000 flows.

Examine the megaflow masks to understand the wildcarding efficiency:

[user@bastion ~]$ oc debug node/worker-3.ocp.example.com -- chroot /host \
  ovs-appctl dpctl/dump-flows -m | head -5

Finding: The datapath flows have exact match masks (/255.255.255.255 for IPs, /0xffff for ports). This means OVS cannot wildcard - each unique 5-tuple (src IP, dst IP, src port, dst port, protocol) creates a separate datapath entry. This is a microflow explosion.

Key Concept

OVS uses megaflows to optimize the datapath. A megaflow is a wildcarded flow entry that matches many packets at once. For example, a megaflow with mask src=10.128.2.0/255.255.255.0 would match all packets from the 10.128.2.0/24 subnet in a single entry. When the OpenFlow table has many specific rules (per-IP matches), OVS cannot create wildcarded megaflows and falls back to microflows (exact match per-connection). With microflows, the datapath grows with the number of active connections, quickly overwhelming the system.

Check megaflow mask statistics:

[user@bastion ~]$ oc debug node/worker-3.ocp.example.com -- chroot /host \
  ovs-appctl dpctl/dump-mega-stats
Mega flow masks:
  Total masks: 2847
  Hit masks: 248923456
  Masks/lookup: 12.47

Finding: There are 2,847 unique masks and the average masks per lookup is 12.47. In a healthy system, you want masks/lookup to be under 4-5. At 12.47, every packet lookup must check an average of 12.47 masks before finding a match, which is extremely slow.

Step 5: Check Conntrack Table

Why: OVN uses connection tracking (conntrack) for stateful ACL enforcement. Every allowed connection gets a conntrack entry. If the conntrack table fills up, new connections are dropped or severely delayed.

[user@bastion ~]$ oc debug node/worker-3.ocp.example.com -- chroot /host \
  cat /proc/sys/net/netfilter/nf_conntrack_max
262144
[user@bastion ~]$ oc debug node/worker-3.ocp.example.com -- chroot /host \
  cat /proc/sys/net/netfilter/nf_conntrack_count
248901

Finding: The conntrack table is at 248,901 / 262,144 entries - that is 95% full. When the table is nearly full, performance degrades because:

  • Hash bucket chains become long, slowing lookups

  • New connections may be dropped if the table fills completely

  • Garbage collection runs more frequently, consuming CPU

Get more detailed conntrack statistics:

[user@bastion ~]$ oc debug node/worker-3.ocp.example.com -- chroot /host \
  ovs-appctl dpctl/ct-stats-show
Total: 248901
TCP: 234567
UDP: 12345
ICMP: 1989
  Entries:
    TCP established: 198765
    TCP time_wait: 23456
    TCP close_wait: 12346
    UDP replied: 10234
    UDP unreplied: 2111
    ICMP replied: 1567
    ICMP unreplied: 422

Finding: Most conntrack entries are TCP established connections (198,765). The "unreplied" counts (UDP: 2,111, ICMP: 422) indicate connections that are waiting for responses that may never come - these consume conntrack slots without being productive.

When the conntrack table is full, Linux silently drops new connections without sending any error message. Applications see connection timeouts with no clear indication that conntrack exhaustion is the cause. This makes the problem extremely difficult to diagnose without explicitly checking the conntrack count.

Step 7: Examine the Problematic NetworkPolicies

Why: We need to understand why the NetworkPolicies generated so many ACLs. Poorly written policies that select individual pods instead of using label selectors are a common cause.

[user@bastion ~]$ oc get networkpolicy -A | wc -l
237

Look at one of the problematic policies:

  egress:

Step 8: Check Flow Revalidation Rate

Why: OVS periodically revalidates datapath flows against the OpenFlow table to ensure they are still correct. With 87,000+ OpenFlow flows, revalidation becomes very expensive.

[user@bastion ~]$ oc debug node/worker-3.ocp.example.com -- chroot /host \
  ovs-appctl coverage/show | grep -E "revalidate|upcall|flow_create|flow_del"
Event                                    last 5s     last 10s    total
-----------------------------------------------------------------------
rev_revalidate                           8234        15678       4567890
rev_flow_table_bypass                    12          23          1234
upcall_flow_limit_hit                    567         1023        234567
upcall_ukeys_skipped                    234         456         98765
flow_create                              3456        6789        1234567
flow_del                                 3234        6432        1198765

Finding:

  • rev_revalidate: 8,234 revalidations in the last 5 seconds - this is extremely high. Revalidation compares each datapath flow against the OpenFlow table, and with 87,000 OpenFlow entries, each comparison is expensive.

  • upcall_flow_limit_hit: 567 in the last 5 seconds - the datapath has hit its flow limit, meaning new flows cannot be installed and packets must take the slow path.

  • flow_create and flow_del rates are nearly equal (~3,400/5s each) - the datapath is in a constant churn of creating and deleting flows, providing no stable fast-path cache.

Key Concept

Revalidation is the process where OVS checks that each cached datapath flow is still consistent with the OpenFlow table. When the OpenFlow table is large, each revalidation is costly. When flows are being added and deleted rapidly, the revalidator threads run constantly, consuming CPU and reducing the time available for actual packet processing.

  avg. packets per output batch: 1.23

Finding: Key metrics:

  • avg. subtable lookups per megaflow hit: 12.47 - each packet that hits the megaflow cache requires checking an average of 12.47 subtables. This should be under 5 for good performance.

  • miss with success upcall: 8,901,234 - nearly 9 million packets had to go to userspace because they missed the datapath cache entirely.

  • miss with failed upcall: 234,567 - over 234,000 packets were DROPPED because the upcall to userspace failed (backlog full).

  • avg. packets per output batch: 1.23 - nearly every packet is processed individually rather than in batches, eliminating any batching efficiency.

Root Cause

The performance degradation was caused by a cascade of effects triggered by the deployment of 200+ overly granular NetworkPolicy objects:

  1. NetworkPolicies used per-pod selectors instead of label-based selectors, causing each policy to generate many individual ACL rules.

  2. 42,367 OVN ACLs were created, which ovn-controller compiled into 87,234 OpenFlow flows in OVS on each node.

  3. The large OpenFlow table prevented efficient megaflow creation. Because the OpenFlow rules matched on specific IP addresses, OVS could not create wildcarded datapath entries. Every unique connection required its own datapath flow (microflow explosion).

  4. The datapath flow table reached its limit (124,567 / 131,072), causing constant flow eviction and recreation (churn).

  5. High upcall rate - most packets took the slow path through userspace because they missed the datapath cache or their cached flow was evicted.

  6. The conntrack table was nearly full (248,901 / 262,144), causing slow hash lookups and dropped new connections.

  7. ovs-vswitchd consumed 97% CPU handling upcalls, leaving no headroom for actual packet forwarding.

Key Concept

The fast path vs slow path distinction is critical for understanding OVS performance: text FAST PATH (kernel): Packet arrives → Datapath flow lookup → Match found → Action executed Latency: ~1 microsecond Throughput: line rate (25 Gbps+) SLOW PATH (userspace): Packet arrives → Datapath flow lookup → No match (MISS) → Upcall to ovs-vswitchd → OpenFlow table lookup → Install datapath flow → Return packet to kernel → Execute action Latency: ~100-1000 microseconds Throughput: < 1 Gbps (CPU limited) When the majority of packets take the slow path, performance drops from line-rate to sub-gigabit levels regardless of the physical network speed.

Resolution

Immediate Mitigation: Increase Conntrack Table Size

Why: This prevents connection drops while we fix the root cause.

    machineconfiguration.openshift.io/role: worker

OVS Tuning

If further optimization is needed, tune OVS handler and revalidator threads:

# Increase handler threads (processes upcalls):
oc debug node/worker-3.ocp.example.com -- chroot /host \
  ovs-vsctl set Open_vSwitch . other_config:n-handler-threads=4

# Increase revalidator threads (validates cached flows):
oc debug node/worker-3.ocp.example.com -- chroot /host \
  ovs-vsctl set Open_vSwitch . other_config:n-revalidator-threads=4

The default handler and revalidator thread counts are calculated based on the number of CPU cores. Increasing them helps with high upcall rates but takes CPU away from other processing. In most cases, fixing the root cause (reducing ACLs) is more effective than tuning threads.

Adjust the datapath flow limit if needed:

oc debug node/worker-3.ocp.example.com -- chroot /host \
  ovs-vsctl set Open_vSwitch . other_config:flow-limit=200000

Long-term: Consolidate and Review NetworkPolicies

  1. Audit existing policies: Identify and merge overlapping or redundant policies.

  2. Use namespaceSelector where possible: Instead of selecting individual pods across namespaces, select entire namespaces:

ingress:

  - namespaceSelector:
      matchLabels:
        purpose: frontend

  1. Leverage OVN port groups: OVN-Kubernetes automatically uses port groups for NetworkPolicy implementation. Ensure your policies work with port groups by using label selectors instead of IP-based rules.

  2. Establish a review process: Require review of NetworkPolicies for performance impact before deployment, just as you would for application resource requests.

Key Takeaways

  • NetworkPolicy granularity directly impacts OVS performance. Per-pod selectors create per-pod ACLs, which create per-pod OpenFlow flows, which prevent efficient megaflow caching. Use broad label selectors wherever possible.

  • Monitor OVS flow count and conntrack table size as key performance indicators. A sudden increase in either after a policy change is a red flag.

  • The fast path / slow path distinction explains most OVS performance issues. When most packets take the slow path through userspace, throughput drops by 10-100x regardless of physical network speed.

  • Conntrack table exhaustion causes silent connection drops. Always size the conntrack table appropriately and monitor its utilization.

  • Always load-test NetworkPolicy changes in a staging environment before deploying to production. A simple iperf3 test before and after can reveal performance regressions before they affect production workloads.
