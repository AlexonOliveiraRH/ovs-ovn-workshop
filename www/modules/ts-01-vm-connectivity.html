Scenario 01: VM Cannot Reach Another VM

The Problem

A customer opens a support case with the following description:

"Two VMs on the same Neutron network cannot ping each other. VM-A is on compute-0 and VM-B is on compute-1. They are both on the tenant-net network (192.168.100.0/24). This was working fine until earlier today. Nothing was changed on the OpenStack side. The VMs can still reach their default gateway and access the metadata service, but direct VM-to-VM communication across the two compute nodes is completely broken."

This is one of the most common classes of issues in OVN-based deployments: cross-node east-west traffic failure. The structured investigation below walks through every layer, from inside the VM all the way down to the physical network, to identify the root cause.

RHOSP 17.1: Containerized OVN Commands

In RHOSP 17.1, OVN databases run inside Pacemaker-managed containers. All ovn-nbctl and ovn-sbctl commands shown in this scenario must be executed via podman exec on the controller node. For example:

  • ovn-nbctl show becomes sudo podman exec -it ovn_cluster_north_db_server ovn-nbctl --no-leader-only show

  • ovn-sbctl show becomes sudo podman exec -it ovn_cluster_south_db_server ovn-sbctl --no-leader-only show

  • ovn-trace becomes sudo podman exec -it ovn_cluster_north_db_server ovn-trace --no-leader-only

Similarly, ovn-controller and ovs-vswitchd commands on compute nodes must be run via sudo podman exec -it ovn_controller or sudo podman exec -it ovs_vswitchd.

For brevity, this scenario shows the bare commands. Refer to Module 12: RHOSP Product-Specific Troubleshooting for the full containerized command syntax.

Key Concept

In ML2/OVN, Neutron translates its network model into OVN northbound database objects (logical switches, logical router, ACLs). The ovn-northd daemon compiles those into the southbound database, and ovn-controller on each compute node programs the local OVS bridge (br-int) with OpenFlow rules that implement the logical topology. East-west traffic between VMs on different compute nodes travels through Geneve tunnels.

Step-by-Step Investigation

Step 1: Verify the Symptoms

Why we do this: Before diving into infrastructure, confirm the reported symptom is real and gather precise failure characteristics. The type of failure (timeout vs. unreachable vs. partial loss) tells us where to look.

Access the VM-A console (via Horizon, virsh console, or openstack console url show) and attempt to ping VM-B:

[root@vm-a ~]# ping -c 5 192.168.100.20
PING 192.168.100.20 (192.168.100.20) 56(84) bytes of data.
From 192.168.100.10 icmp_seq=1 Destination Host Unreachable
From 192.168.100.10 icmp_seq=2 Destination Host Unreachable
From 192.168.100.10 icmp_seq=3 Destination Host Unreachable
From 192.168.100.10 icmp_seq=4 Destination Host Unreachable
From 192.168.100.10 icmp_seq=5 Destination Host Unreachable

--- 192.168.100.20 ping statistics ---
5 packets transmitted, 0 received, +5 errors, 100% packet loss, time 4005ms

Also try from VM-B to VM-A to confirm the failure is bidirectional:

[root@vm-b ~]# ping -c 5 192.168.100.10
PING 192.168.100.10 (192.168.100.10) 56(84) bytes of data.
From 192.168.100.20 icmp_seq=1 Destination Host Unreachable
From 192.168.100.20 icmp_seq=2 Destination Host Unreachable
From 192.168.100.20 icmp_seq=3 Destination Host Unreachable

--- 192.168.100.10 ping statistics ---
5 packets transmitted, 0 received, +5 errors, 100% packet loss, time 4003ms

What this tells us: The failure is 100% packet loss with "Destination Host Unreachable" in both directions. This means the source VM’s ARP resolution for the destination is failing - the VM cannot even build an L2 frame to reach the other VM. This is consistent with a complete communication breakdown between the two compute nodes at the overlay level.

Finding: Confirmed - complete bidirectional failure. This is NOT normal. Proceed with investigation.

Step 2: Check VM Network Configuration

Why we do this: Misconfigured guest networking (wrong IP, wrong subnet mask, missing default route, or a duplicate MAC address) can cause connectivity failures that look like infrastructure problems. Always rule out the obvious before going deeper.

What this tells us: Both VMs have the correct IP addresses, correct subnet masks (/24), correct MAC addresses matching what Neutron assigned, and proper default routes via 192.168.100.1 (the OVN logical router gateway). The interfaces are UP with LOWER_UP (link is good). The MTU of 1442 is expected for Geneve overlay (1500 physical MTU - 58 bytes Geneve overhead).

Key Concept

Geneve encapsulation adds overhead to each packet: 8 bytes UDP header + 8 bytes Geneve fixed header + variable Geneve options (typically 4-42 bytes in OVN for metadata) + 20 bytes outer IP header. OVN typically sets the inner MTU to 1442 to account for this overhead on a 1500-byte physical MTU.

Finding: VM network configuration is correct. This is normal. The problem is not inside the guests.

Step 4: Check OVN Logical Switch and Ports

Why we do this: Even if Neutron shows ports as ACTIVE, the OVN northbound database might not have the corresponding logical switch ports, or they could be in the wrong state. The NB database is the "desired state" for the network - if something is wrong here, ovn-northd cannot compile the correct southbound flows.

On the controller node (or wherever the OVN northbound database is hosted), inspect the logical switch:

If a port binding is missing or bound to the wrong chassis, traffic will not reach the correct destination. The SB database is what ovn-controller actually reads to program OVS flows.

Step 7: Use ovn-trace to Test the Logical Pipeline

Why we do this: ovn-trace simulates packet processing through the OVN logical pipeline without actually sending a packet. It shows how the packet would traverse logical ingress and egress stages, including ACL evaluation. If ovn-trace shows the packet being dropped, the problem is in the OVN logical configuration (ACLs, routing, etc.). If ovn-trace shows the packet being delivered successfully, the problem is in the physical forwarding plane below OVN.

Run an ovn-trace simulating an ICMP ping from VM-A to VM-B:

[root@controller-0 ~]# ovn-trace --detailed neutron-a1b2c3d4-e5f6-7890-abcd-ef1234567890 \
  'inport == "c3d4e5f6-a7b8-9012-cdef-123456789012" &&
   eth.src == fa:16:3e:aa:bb:cc &&
   eth.dst == fa:16:3e:dd:ee:ff &&
   ip4.src == 192.168.100.10 &&
   ip4.dst == 192.168.100.20 &&
   ip.ttl == 64 &&
   icmp4.type == 8'

"The network security team applied a new firewall policy to the data center core switch at 09:00 this morning. The policy was intended to block unauthorized UDP traffic. They did not consult with the OpenStack team."

Ask the network team to check the firewall rule on the core switch. They provide the following output from the Cisco Nexus switch:

switch# show access-lists DATACENTER-SECURITY
IP access list DATACENTER-SECURITY
    10 permit tcp any any established
    20 permit tcp any any eq 22
    30 permit tcp any any eq 443
    40 permit tcp any any eq 8080
    50 permit tcp any any eq 5900-5999
    60 permit icmp any any
    70 permit udp any any eq 4789 (VXLAN)
    80 deny udp any any log
    90 permit ip any any

There it is. Line 80 is a catch-all deny udp any any rule. The network team added rules to allow specific UDP ports they knew about (VXLAN on port 4789 at line 70) but did NOT add a permit rule for Geneve on UDP port 6081. Since line 80 (deny udp any any) comes before line 90 (permit ip any any), ALL UDP traffic that is not VXLAN is being dropped. This includes Geneve.

This is an extremely common issue when network security teams apply firewall rules without understanding the full set of protocols used by the cloud platform. VXLAN (UDP 4789) is widely known, but Geneve (UDP 6081) is often overlooked, especially in environments that recently migrated from ML2/OVS (which used VXLAN) to ML2/OVN (which uses Geneve).

Finding: The physical network firewall is blocking UDP port 6081 between compute nodes. This IS the root cause.

Root Cause

The root cause is a firewall rule on the physical data center network equipment (core switch) that blocks UDP port 6081 between compute nodes.

The network security team applied a new access control list (ACL) to the core switch. This ACL explicitly allows VXLAN traffic (UDP 4789) but denies all other UDP traffic before the general "permit ip any any" rule. Since OVN uses Geneve encapsulation (not VXLAN), and Geneve uses UDP destination port 6081, all overlay tunnel traffic between compute nodes is dropped by the firewall.

What is Geneve and Why Port 6081?

Geneve (Generic Network Virtualization Encapsulation) is defined in RFC 8926. It was designed as a flexible overlay encapsulation protocol that can carry arbitrary metadata in its variable-length options header. OVN chose Geneve over VXLAN because:

  1. Extensible metadata: Geneve options can carry OVN-specific metadata (logical datapath, logical ports, flags) that VXLAN’s fixed 24-bit VNI cannot accommodate.

  2. Protocol evolution: Geneve’s TLV (Type-Length-Value) options allow adding new features without changing the protocol format.

  3. IANA-assigned port: Geneve uses UDP destination port 6081, assigned by IANA.

The Geneve packet structure on the wire:

+--------------------------------------------------+
| Outer Ethernet Header (14 bytes)                  |
+--------------------------------------------------+
| Outer IP Header (20 bytes)                        |
|   src: 10.0.0.11  dst: 10.0.0.12                 |
|   protocol: UDP (17)                              |
+--------------------------------------------------+
| Outer UDP Header (8 bytes)                        |
|   src: <hash-based>  dst: 6081                    |
+--------------------------------------------------+
| Geneve Header (8+ bytes)                          |
|   VNI: <logical datapath ID>                      |
|   Options: <OVN metadata - port keys, flags>      |
+--------------------------------------------------+
| Inner Ethernet Frame                              |
|   src: fa:16:3e:aa:bb:cc  dst: fa:16:3e:dd:ee:ff |
|   Inner IP: 192.168.100.10 -> 192.168.100.20     |
|   ICMP echo request                               |
+--------------------------------------------------+

When the firewall drops the outer UDP packet (because dst port 6081 is denied), the entire inner frame - including the VM’s ICMP ping - is lost.

Resolution

Immediate Fix

Request the network/firewall team to add a permit rule for UDP port 6081 (Geneve) in the ACL on the core switch. The rule must be inserted BEFORE the deny udp any any rule:

For Cisco NX-OS:

switch# configure terminal
switch(config)# ip access-list DATACENTER-SECURITY
switch(config-acl)# 75 permit udp any any eq 6081
switch(config-acl)# end
switch# copy running-config startup-config

The updated ACL should now look like:

switch# show access-lists DATACENTER-SECURITY
IP access list DATACENTER-SECURITY
    10 permit tcp any any established
    20 permit tcp any any eq 22
    30 permit tcp any any eq 443
    40 permit tcp any any eq 8080
    50 permit tcp any any eq 5900-5999
    60 permit icmp any any
    70 permit udp any any eq 4789 (VXLAN)
    75 permit udp any any eq 6081 (Geneve)
    80 deny udp any any log
    90 permit ip any any

For a more restrictive rule, you can limit the permit to only the compute node network: text 75 permit udp 10.0.0.0/24 10.0.0.0/24 eq 6081 This allows Geneve only between hosts on the tunnel network, which is more secure than allowing it from any source.

Alternative Approaches if the Firewall Rule Cannot Be Changed

If the security team insists on blocking UDP 6081 and cannot make an exception:

  1. Use IPsec tunnels: OVN supports IPsec encryption of tunnel traffic. IPsec uses ESP (protocol 50) or AH (protocol 51), which might be permitted by the firewall. Configure with:

[root@controller-0 ~]# ovn-nbctl set nb_global . ipsec=true

  1. Switch to STT encapsulation: OVN can use STT (Stateless Transport Tunneling) which uses TCP instead of UDP. However, STT has limitations and is not widely recommended.

  2. Request a dedicated VLAN for tunnel traffic: Place all compute node tunnel interfaces on a dedicated VLAN that bypasses the UDP firewall rule. This is often the simplest organizational solution.

Never attempt to work around firewall rules by tunneling traffic over allowed ports (e.g., encapsulating Geneve inside an SSH tunnel). This creates fragile, unsupported configurations that will cause future troubleshooting nightmares and may violate security policies.

Set Up BFD Monitoring for Tunnel Connectivity

BFD (Bidirectional Forwarding Detection) can detect tunnel failures within seconds, providing early warning before users report issues. Configure BFD on OVN tunnel interfaces:

[root@compute-0 ~]# ovs-vsctl set interface ovn-f6a7b8-0 bfd:enable=true
[root@compute-0 ~]# ovs-vsctl set interface ovn-f6a7b8-0 bfd:min_tx=1000
[root@compute-0 ~]# ovs-vsctl set interface ovn-f6a7b8-0 bfd:min_rx=1000
[root@compute-0 ~]# ovs-vsctl set interface ovn-f6a7b8-0 bfd:decay_min_rx=5000

Verify BFD status:

[root@compute-0 ~]# ovs-vsctl get interface ovn-f6a7b8-0 bfd_status
{diagnostic="No Diagnostic", flap_count="0", forwarding="true", remote_diagnostic="No Diagnostic", remote_state=up, state=up}

In newer versions of OVN (21.06+), BFD can be configured centrally via the OVN northbound database rather than on each compute node individually. Check your OVN version with ovn-controller --version to determine which method to use.

Include Network Requirements in Deployment Documentation

Add a pre-deployment checklist that includes:

  • Verify all required ports are open between all node roles (controller, compute, networker)

  • Test UDP 6081 connectivity explicitly between compute nodes before deploying workloads

  • Establish a change management process that requires OpenStack team approval before network firewall changes

  • Document the overlay protocol in use (Geneve vs VXLAN) and its port number

A simple pre-deployment connectivity test:

# On compute-1, start a UDP listener on port 6081:
[root@compute-1 ~]# nc -u -l 6081 &

# On compute-0, send a test message:
[root@compute-0 ~]# echo "geneve-test" | nc -u -w 2 10.0.0.12 6081

# On compute-1, check if the message was received:
[root@compute-1 ~]# # If "geneve-test" appeared, UDP 6081 is open.
# Kill the listener:
[root@compute-1 ~]# kill %1

Key Takeaways

  • Always check the physical network. OVN and OVS can be perfectly configured, but if the underlying physical network blocks the overlay protocol’s UDP port, VM traffic will fail. A systematic layer-by-layer investigation is the only reliable way to isolate whether the problem is in the logical layer (OVN), the virtual forwarding layer (OVS), or the physical transport layer.

  • Geneve uses UDP port 6081 - not 4789. Environments migrating from ML2/OVS (VXLAN) to ML2/OVN (Geneve) must update firewall rules to allow UDP 6081 in addition to (or instead of) UDP 4789. Network teams familiar with VXLAN may not know about Geneve.

  • ovn-trace validates logic, not transport. A successful ovn-trace proves that OVN’s logical pipeline would deliver the packet correctly, but it says nothing about whether the Geneve tunnel, OVS flows, or physical network will actually carry it. Always follow ovn-trace with OVS flow inspection and physical-layer verification when the trace looks clean but traffic is failing.

  • tcpdump at multiple layers tells the story. Capturing on genev_sys_6081 (inner/decapsulated), on the physical NIC with udp port 6081 (outer/encapsulated), and verifying basic IP connectivity between nodes (plain ICMP) is the fastest way to determine exactly where packets are being lost. When inner packets exist but outer packets do not arrive at the remote end, the physical network is the suspect.

  • Proactive monitoring prevents outages. BFD on tunnel interfaces detects failures in seconds. Documenting required firewall ports and establishing change management processes between the OpenStack team and the network security team prevents this class of issue entirely.
