OpenShift Networking Overview

Before diving into OVN-Kubernetes, it helps to understand the networking model that all Kubernetes distributions - including OpenShift - follow, and how OpenShift evolved to its current implementation.

The CNI Model

Kubernetes defines a set of networking requirements that any conformant implementation must satisfy:

  1. Every pod gets its own IP address. There is no NAT between pods - they can communicate directly using their pod IPs.

  2. All pods can communicate with all other pods on any node without NAT (the "flat" pod network).

  3. Agents on a node (like kubelet or the system daemons) can communicate with all pods on that node.

  4. Services provide stable virtual IPs (ClusterIPs) that load-balance traffic to a set of backend pods.

  5. Ingress controllers route external HTTP/HTTPS traffic into the cluster.

These requirements define what the networking must do, but not how it is implemented. The how is the job of a CNI plugin (Container Network Interface).

Key Concept

A CNI plugin is the component responsible for setting up networking for each pod. When the kubelet creates a pod, it calls the CNI plugin to assign an IP address, create a network interface inside the pod’s network namespace, and set up the necessary routes. When the pod is deleted, the CNI plugin cleans up. The CNI plugin also handles inter-node pod traffic, services, and network policies.

OpenShift’s Networking Model

OpenShift extends the base Kubernetes networking model with additional enterprise features:

  • Routes: OpenShift’s native ingress resource (predates Kubernetes Ingress), providing HTTP/HTTPS routing with TLS termination.

  • EgressIP: Stable, predictable source IPs for outbound pod traffic.

  • EgressFirewall: Namespace-level controls on outbound traffic destinations.

  • Multus: Support for multiple network interfaces per pod (used in RHOSO, covered in Module 08).

  • Network Observability: Built-in flow collection and dashboards for network traffic analysis.

OpenShift SDN used Open vSwitch as its data plane but implemented its own custom controller to program OVS flows. It supported three network modes: Subnet (flat network), Multitenant (project-level isolation), and NetworkPolicy (Kubernetes NetworkPolicy support). OpenShift SDN was removed in OCP 4.17, making OVN-Kubernetes the sole CNI going forward into OCP 5.x.

OVN-Kubernetes replaced this with a fully OVN-based architecture. Instead of a custom controller, it uses OVN’s standard architecture (NB DB, SB DB, ovn-northd, ovn-controller) with a Kubernetes-specific management layer that translates Kubernetes objects into OVN logical network configurations.

OVN Interconnect (IC) mode is the default since OCP 4.14. In IC mode, each node runs its own independent NB/SB DB, ovn-northd, and ovn-controller. There is no centralized Raft-clustered database. Cross-node traffic uses a transit_switch with remote ports. This is a fundamental architectural change from the pre-4.14 centralized model.

Starting with OCP 4.14, clusters can be migrated from OpenShift SDN to OVN-Kubernetes. This migration is a one-way operation - you cannot migrate back.

The move to OVN-Kubernetes was driven by several factors:

  • Richer feature set: OVN provides native support for distributed routing, ACLs, load balancing, NAT, and IGMP snooping - features that OpenShift SDN had to implement in custom code.

  • Upstream alignment: OVN-Kubernetes is an upstream Kubernetes project with a broad community, reducing Red Hat’s maintenance burden.

  • Dual-stack support: OVN-Kubernetes natively supports IPv4, IPv6, and dual-stack networking.

  • Better scalability: OVN’s distributed architecture (with ovn-controller on each node processing only locally-relevant flows) scales better than centralized flow programming.

  • Feature parity with cloud providers: EgressIP, EgressFirewall, and other enterprise networking features map naturally to OVN constructs.

ovnkube-node

The ovnkube-node component runs on every node as a DaemonSet. In IC mode, it is the central component containing all OVN services:

  • nbdb / sbdb containers: Run the node-local NB and SB databases.

  • northd container: Runs ovn-northd, compiling NB DB into SB DB logical flows for this node.

  • ovn-controller container: Translates SB DB logical flows into OVS OpenFlow rules.

  • ovnkube-controller container: Watches the Kubernetes API and translates K8s objects (pods, services, network policies) into OVN NB DB objects for this node.

  • Pod networking setup: Acts as the CNI plugin - creates veth pairs, assigns IPs, sets up routes.

  • Local OVS configuration: Ensures OVS bridges (br-int, br-ex) are properly configured.

ovnkube-control-plane

The ovnkube-control-plane component runs on control plane nodes (Deployment with multiple replicas). In IC mode, its role is limited to cluster-wide coordination:

  • EgressIP management: Coordinates EgressIP assignment across nodes.

  • EgressFirewall: Manages namespace-level egress rules.

  • Zone management: Coordinates the OVN Interconnect zones.

OVS

Open vSwitch runs on every node, providing:

  • br-int: The integration bridge where all pod traffic passes through

  • br-ex: The external bridge for traffic leaving the cluster (to external networks)

Per-Node Logical Switch

Each node in the cluster gets its own logical switch. All pods on that node are connected to this switch as logical switch ports.

  • Name convention: The logical switch is named after the node (e.g., node1, worker-0).

  • Subnet: Each node is assigned a pod subnet (e.g., 10.128.0.0/23 for node 1, 10.128.2.0/23 for node 2).

  • Ports: One port per pod, plus a router port connecting to the cluster router.

Key Concept

OVN-Kubernetes uses per-node subnet allocation. The cluster is configured with a large pod CIDR (e.g., 10.128.0.0/14), and each node gets a smaller subnet from that range (e.g., /23 giving 510 pod IPs per node). This means you can determine which node a pod is on just by looking at its IP address.

Join Logical Switch

The join switch connects the cluster router to the gateway routers. It acts as the bridge between the internal pod network and the external network.

  • Name: join

  • Ports: One port for the cluster router, one port per gateway router (one per node).

Cluster Router (ovn_cluster_router)

The cluster router is a distributed logical router. It connects all the per-node logical switches, enabling pod-to-pod communication across nodes.

  • Distributed: The router logic runs on every node via ovn-controller. A pod sending traffic to a pod on another node does not need to go through a centralized router.

  • Ports: One logical router port per node, connecting to that node’s logical switch.

  • Load Balancers: ClusterIP services are implemented as load balancers on this router.

Gateway Router (GR_node-x)

Each node that can serve as a gateway gets a gateway router. The gateway router handles:

  • SNAT for egress traffic: Pod traffic going to external destinations is SNATed to the node’s IP (or an EgressIP).

  • DNAT for ingress traffic: NodePort and LoadBalancer service traffic is DNATed to the appropriate backend pod.

  • External connectivity: Connects to the physical network through br-ex.

By default, every node has a gateway router, but only worker nodes typically handle pod egress traffic. The ovnkube-controller (in IC mode, running inside each ovnkube-node pod) manages which nodes serve as active gateways based on configuration and health.

Transit Switch (IC Mode)

Since OCP 4.14, every cluster uses OVN Interconnect mode with a zone-per-node architecture. Each node is its own zone with an independent OVN control plane. A transit_switch connects all zones, using remote ports to route cross-node traffic.

When a pod on Node A communicates with a pod on Node B, the packet passes through the transit_switch as an intermediate hop. The transit_switch uses Geneve tunnels between nodes, just like the pre-IC architecture, but the logical path includes the transit_switch routing step.

Pod IP Assignment

When a new node joins the cluster:

  1. ovnkube-controller (in IC mode, running inside each ovnkube-node pod) allocates a pod subnet from the cluster CIDR (e.g., 10.129.0.0/23).

  2. It creates a logical switch for that node.

  3. It connects the logical switch to the cluster router.

When a pod is scheduled to a node:

  1. ovnkube-node allocates an IP from the node’s pod subnet.

  2. It creates a logical switch port on the node’s logical switch.

  3. It creates a veth pair: one end in the pod’s network namespace, one end connected to br-int.

  4. It assigns the pod IP and sets up routes (default gateway is the cluster router’s port IP).

Packet Flows in OVN-Kubernetes

Understanding how packets flow through the OVN-Kubernetes stack is critical for troubleshooting. This section walks through the most common scenarios.

Pod to Pod - Same Node

When two pods on the same node communicate, all traffic stays local within that node’s OVS instance.

Pod A (10.128.0.5)            Pod B (10.128.0.8)
   |                              |
   vethA                       vethB
   |                              |
   +-- port on node1 LS --+-- port on node1 LS --+
                |
            br-int (OVS)
         (local switching)

What happens:

  1. Pod A sends a packet to 10.128.0.8 (Pod B).

  2. The packet exits Pod A’s network namespace through the veth pair into br-int.

  3. OVS processes the packet through the OVN logical switch pipeline:

    • Ingress port security: Verifies the source MAC and IP match the port binding.

    • Ingress ACLs: Checks network policies (if any) for the source pod.

    • L2 lookup: Finds the destination MAC in the logical switch’s FDB.

    • Egress ACLs: Checks network policies for the destination pod.

    • Egress port security: Verifies the destination port accepts this traffic.

  4. The packet is delivered to Pod B through its veth pair.

No tunneling is involved - the packet never leaves the node.

Pod to Pod - Different Nodes

When pods on different nodes communicate, the traffic must be encapsulated in a Geneve tunnel.

Node 1 (192.168.1.10)                    Node 2 (192.168.1.11)
+----------------------------+            +----------------------------+
| Pod A (10.128.0.5)        |            | Pod C (10.128.2.3)        |
|    |                       |            |    |                       |
|  vethA                     |            |  vethC                     |
|    |                       |            |    |                       |
| node1 LS -- cluster router |            | node2 LS -- cluster router |
|    |          |             |            |    |          |             |
|  br-int    geneve port     |            |  br-int    geneve port     |
|              |             |            |              |             |
+--------------+-------------+            +--------------+-------------+
               |                                         |
               +--------Physical Network-----------------+
                         (Geneve tunnel)

What happens:

  1. Pod A sends a packet to 10.128.2.3 (Pod C on Node 2).

  2. The packet enters br-int on Node 1.

  3. OVS processes the logical switch pipeline (port security, ACLs, L2 lookup).

  4. The L2 lookup does not find 10.128.2.3 on the local switch (different subnet). The packet is forwarded to the cluster router.

  5. The cluster router performs L3 routing: the destination 10.128.2.3 matches the route for Node 2’s subnet (10.128.2.0/23).

  6. OVN determines the destination port is on Node 2’s chassis. The packet is encapsulated in a Geneve tunnel destined for Node 2.

  7. The Geneve packet traverses the physical network from Node 1 to Node 2.

  8. On Node 2, the Geneve tunnel is decapsulated.

  9. OVS on Node 2 processes the packet through Node 2’s logical switch pipeline and delivers it to Pod C.

Key Concept

The cluster router is distributed - its routing logic runs on every node. When Pod A sends a packet to Pod C, the routing decision happens locally on Node 1 (inside OVS, programmed by ovn-controller). There is no centralized router that the packet must traverse. This is a key scalability advantage of OVN’s distributed architecture.

Pod to Service (ClusterIP)

When a pod accesses a Kubernetes Service by its ClusterIP, OVN handles the load balancing.

Pod A (10.128.0.5)
   |
   | dst: 172.30.100.50:80 (Service ClusterIP)
   |
br-int (OVS)
   |
   | OVN Load Balancer (DNAT)
   | 172.30.100.50:80 -> 10.128.0.8:8080 (backend 1)
   |                  -> 10.128.2.3:8080 (backend 2)
   |                  -> 10.128.4.5:8080 (backend 3)
   |
   | Selected: 10.128.2.3:8080
   |
   | (packet now has dst: 10.128.2.3:8080)
   | (follows pod-to-pod path from here)

What happens:

  1. Pod A sends a packet to 172.30.100.50:80 (the Service ClusterIP).

  2. The packet enters br-int.

  3. OVN Load Balancer (on the cluster router or logical switch): OVN matches the destination IP:port against its load balancer rules. It selects a backend pod and performs DNAT - rewriting the destination IP and port to the selected backend.

  4. From this point, the packet follows the normal pod-to-pod path (same node or cross-node).

  5. The return traffic is un-DNATed (the source is rewritten back to the Service ClusterIP) so Pod A sees responses from the Service IP.

OVN load balancers are stateful - once a backend is selected for a connection, all packets in that connection go to the same backend. This is tracked using connection tracking (conntrack) in OVS.

Pod to External

When a pod sends traffic to an external destination (outside the cluster), it must go through a gateway router.

Pod A (10.128.0.5)
   |
   | dst: 8.8.8.8
   |
br-int on Node 1
   |
   | cluster router (routing decision)
   | -> next hop: gateway router on this node (or another node)
   |
   | join switch
   |
   | Gateway Router (GR_node1)
   | SNAT: src 10.128.0.5 -> src 192.168.1.10 (node IP)
   |
   | br-ex
   |
   | Physical NIC
   |
External Network -> 8.8.8.8

What happens:

  1. Pod A sends a packet to 8.8.8.8.

  2. The packet enters br-int, goes through the logical switch pipeline.

  3. The cluster router receives the packet. The destination 8.8.8.8 does not match any pod subnet, so it matches the default route pointing to the gateway router.

  4. The packet traverses the join switch to reach the gateway router.

  5. The gateway router performs SNAT: It rewrites the source IP from the pod IP (10.128.0.5) to the node’s external IP (192.168.1.10). This is necessary because external hosts do not know how to route to pod IPs.

  6. The packet exits through br-ex and the physical NIC to the external network.

  7. Return traffic arrives at the node’s external IP, the gateway router un-SNATs it (restoring the pod IP as the destination), and forwards it back to the pod.

External to NodePort/LoadBalancer

When external traffic arrives at a NodePort or LoadBalancer service:

External Client
   |
   | dst: 192.168.1.10:30080 (NodePort)
   |
Physical NIC on Node 1
   |
br-ex
   |
Gateway Router (GR_node1)
   |
   | OVN Load Balancer (DNAT)
   | 192.168.1.10:30080 -> 10.128.2.3:8080 (backend pod)
   |
   | (if backend is on another node, Geneve tunnel)
   |
Pod C (10.128.2.3:8080)

What happens:

  1. External traffic arrives at the node’s IP on the NodePort (e.g., 192.168.1.10:30080).

  2. The packet enters through br-ex into the gateway router.

  3. The gateway router’s OVN Load Balancer matches the NodePort and performs DNAT to a backend pod.

  4. If the backend pod is on the same node, the packet is forwarded locally. If it is on a different node, the packet is sent through a Geneve tunnel.

  5. The return traffic follows the reverse path.

Ingress Traffic Flow

OpenShift Ingress (via the HAProxy-based Ingress Controller) adds another layer:

External Client
   |
   | dst: app.example.com (DNS -> LoadBalancer/NodePort IP)
   |
Physical NIC -> br-ex -> Gateway Router
   |
   | DNAT to Ingress Controller pod (e.g., 10.128.0.20:443)
   |
Ingress Controller Pod (HAProxy)
   |
   | HTTP routing based on Host header / path
   | Proxies to backend service
   |
   | dst: 172.30.100.50:80 (Service ClusterIP)
   |
   | OVN Load Balancer (DNAT to backend pod)
   |
Backend Pod (10.128.2.3:8080)

The Ingress Controller pod itself is a regular pod running HAProxy. It receives the external traffic (via a LoadBalancer or NodePort Service), makes HTTP-level routing decisions, and proxies to the backend Service. From OVN’s perspective, this is just pod-to-service traffic.

Key Features in OVN-Kubernetes

Network Policies

Kubernetes NetworkPolicies allow you to control which pods can communicate with each other. OVN-Kubernetes implements these using OVN ACLs and Address Sets.

How NetworkPolicies Map to OVN

When you create a NetworkPolicy, ovnkube-controller (in IC mode, running inside each ovnkube-node pod) translates it into:

  1. Address Sets: Collections of IP addresses representing the pods matched by selectors. For example, all pods with label app=web in namespace production get their IPs added to an address set.

  2. ACLs: Rules on the logical switch that allow or deny traffic based on address sets, ports, and protocols.

Kubernetes NetworkPolicy              OVN Implementation
+---------------------------+          +---------------------------+
| spec:                     |          | Address Set:              |
|   podSelector:            |          |   name: production.web    |
|     matchLabels:          |   --->   |   addresses: [10.128.0.5, |
|       app: web            |          |               10.128.2.3] |
|   ingress:                |          |                           |
|   - from:                 |          | ACL (on logical switch):  |
|     - podSelector:        |          |   match: ip4.src ==       |
|         matchLabels:      |   --->   |     @production.api &&    |
|           app: api        |          |     outport == @prod.web  |
|     ports:                |          |   action: allow-related   |
|     - port: 8080          |          |   priority: 1001          |
|       protocol: TCP       |          |                           |
+---------------------------+          +---------------------------+

Default Behavior

Key Concept

In Kubernetes, the default network behavior is allow all. Without any NetworkPolicy, all pods can communicate with all other pods. Once you apply a NetworkPolicy to a pod (by matching its podSelector), that pod’s traffic is restricted to only what the policy explicitly allows. This is called default deny for the selected pods.

Ingress policies control incoming traffic to the selected pods. Egress policies control outgoing traffic from the selected pods.

Efficiency Through Address Sets

Address sets are the key to OVN’s efficient implementation of NetworkPolicies:

  • Instead of creating one ACL per source-destination pod pair, OVN creates address sets that group pods by selector.

  • When pods are added or removed, only the address set is updated (adding or removing an IP), not the ACL itself.

  • This means NetworkPolicy changes scale with the number of policies, not the number of pods.

Admin Network Policies (OCP 4.16+)

Admin Network Policies (ANP) are cluster-scoped, non-overridable network policies that give cluster administrators priority control over network traffic. They are GA since OCP 4.16.

User-Defined Networks (OCP 4.17+)

User-Defined Networks (UDN) allow creating additional, isolated network topologies beyond the default cluster network. They are GA since OCP 4.17.

Each UDN gets its own set of OVN logical objects: gateway routers, logical switches, and transit switches. This means ovn-nbctl show output is richer and contains per-network topology. When troubleshooting UDN, identify which network the pod belongs to before tracing.

EgressIP

EgressIP allows you to assign a specific, stable IP address to all outbound traffic from pods in a namespace. This is critical for environments where external systems use IP-based allowlists.

What It Is and Why It Matters

Without EgressIP, outbound pod traffic is SNATed to the node’s IP. Since pods can be rescheduled to different nodes, the source IP of outbound traffic is unpredictable. EgressIP solves this by assigning a dedicated external IP.

Without EgressIP:                    With EgressIP:
Pod on Node 1 -> SNAT 192.168.1.10   Pod on Node 1 -> SNAT 10.0.0.50
Pod on Node 2 -> SNAT 192.168.1.11   Pod on Node 2 -> SNAT 10.0.0.50
(source IP changes if pod moves)     (source IP is stable)

How OVN Implements EgressIP

  1. The ovnkube-controller (in IC mode, running inside each ovnkube-node pod) watches for EgressIP custom resources.

  2. It selects a node to host the EgressIP (based on node labels and availability).

  3. It configures an OVN SNAT rule on the gateway router of the selected node, SNATing traffic from the namespace’s pods to the EgressIP.

  4. The EgressIP is added as a secondary IP on the selected node’s external interface.

  5. If the hosting node goes down, the EgressIP is automatically reassigned to another eligible node (failover).

EgressIP failover requires at least two nodes labeled as eligible for the EgressIP. The ovnkube-controller (in IC mode, running inside each ovnkube-node pod) monitors node health and reassigns the EgressIP if the hosting node becomes unreachable.

EgressFirewall

EgressFirewall (also known as EgressNetworkPolicy in older versions) controls what external destinations pods in a namespace can access.

How It Works

  • Defined per namespace.

  • Rules specify Allow or Deny for traffic to specific CIDR ranges or DNS names.

  • Implemented as OVN ACLs on the logical switch.

Example EgressFirewall resource:

apiVersion: k8s.ovn.org/v1
kind: EgressFirewall
metadata:
  name: default
  namespace: production
spec:
  egress:
  - type: Allow
    to:
      cidrSelector: 10.0.0.0/8
  - type: Allow
    to:
      dnsName: "*.example.com"
  - type: Deny
    to:
      cidrSelector: 0.0.0.0/0

This policy allows pods in production to reach 10.0.0.0/8 and *.example.com, but blocks all other external traffic.

DNS-Based Egress Rules

OVN-Kubernetes supports DNS-based egress rules. When a DNS name is specified:

  1. ovnkube-controller (in IC mode, running inside each ovnkube-node pod) resolves the DNS name periodically.

  2. It updates the corresponding address set with the resolved IPs.

  3. The ACL references the address set, so it automatically picks up DNS changes.

DNS-based egress rules depend on DNS resolution working correctly from the control plane. If DNS is unreliable, the address sets may contain stale IPs, leading to unexpected allow/deny behavior. Also, DNS resolution happens at the controller level, not at the pod level, so TTL-based load balancing may behave differently than expected.

Multicast

OVN-Kubernetes supports multicast traffic within the cluster using OVN’s IGMP snooping capability.

  • IGMP snooping is enabled per logical switch.

  • When a pod joins a multicast group (sends an IGMP join), OVN tracks the membership.

  • Multicast traffic is only forwarded to ports that have joined the group, preventing unnecessary flooding.

  • Multicast must be explicitly enabled in the cluster network configuration.

IPsec

OVN-Kubernetes supports encrypting all pod-to-pod traffic that traverses Geneve tunnels using IPsec.

How It Works

  • IPsec encrypts the outer Geneve packets as they travel between nodes.

  • Uses IKE (Internet Key Exchange) for key negotiation, with certificates managed by the OpenShift certificate infrastructure.

  • Provides confidentiality and integrity for all inter-node pod traffic.

Without IPsec:
Node 1 ---[Geneve(plaintext)]---> Node 2

With IPsec:
Node 1 ---[IPsec(Geneve(encrypted))]---> Node 2

IPsec adds CPU overhead for encryption/decryption on every node. This can impact throughput and latency, especially for high-bandwidth workloads. Test performance in your environment before enabling in production.

To check if IPsec is enabled:

oc get network.operator cluster -o jsonpath='{.spec.defaultNetwork.ovnKubernetesConfig.ipsecConfig}'

OCP (Self-Managed)

In self-managed OCP, you have full control over the network infrastructure:

  • You configure the physical switches, VLANs, and IP addressing.

  • OVN-Kubernetes Geneve tunnels run over whatever network you provide between nodes.

  • You can configure custom br-ex mappings for external network connectivity.

  • MTU considerations are your responsibility (Geneve overhead is typically 100 bytes; ensure the physical network MTU accommodates this).

ROSA (Red Hat OpenShift Service on AWS)

On ROSA, OVN-Kubernetes runs on top of AWS VPC networking:

  • Geneve tunnels between nodes run over the VPC network.

  • Each node is an EC2 instance with one or more Elastic Network Interfaces (ENIs).

  • AWS Security Groups operate at the EC2/ENI level, while OVN ACLs operate at the pod level. Both must be considered during troubleshooting.

  • The VPC CNI is not used - OVN-Kubernetes handles all pod networking.

  • Pod IPs are from the cluster pod CIDR, not from the VPC CIDR (pods are not directly routable from the VPC without additional configuration).

On ROSA, if AWS Security Groups block Geneve traffic (UDP port 6081) between nodes, pod-to-pod communication across nodes will fail. This is a common misconfiguration when custom security groups are applied.

ARO (Azure Red Hat OpenShift)

On ARO, OVN-Kubernetes runs on top of Azure VNet networking:

  • Geneve tunnels between nodes run over the VNet.

  • Azure Network Security Groups (NSGs) operate at the subnet or NIC level, alongside OVN ACLs.

  • Azure’s network policies and OVN’s network policies operate at different layers and do not conflict, but both must allow the required traffic.

ROKS (Red Hat OpenShift on IBM Cloud)

ROKS uses IBM Cloud VPC as the underlay:

  • Similar model to AWS and Azure - Geneve tunnels over VPC networking.

  • IBM Cloud-specific security groups and ACLs at the VPC level.

Network Policies

Create a NetworkPolicy

cat <<EOF | oc apply -f -
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-from-same-namespace
  namespace: ovn-trace-test
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  ingress:
  - from:
    - podSelector: {}
EOF

This policy allows ingress only from pods in the same namespace and denies all other ingress.

Verify Corresponding OVN ACLs

# Check ACLs on the logical switch where the pods are
oc exec -n openshift-ovn-kubernetes ovnkube-node-<pod> \
  -c nbdb -- ovn-nbctl acl-list worker-0
from-lport  1001 (inport == @a16382154715504756660 && ip) allow-related
  to-lport  1001 (outport == @a16382154715504756660 && ip4 && ip4.src == @a16382154715504756660) allow-related
  to-lport  1000 (outport == @a16382154715504756660 && ip) drop

The ACLs show:

  • from-lport 1001: Allow all outbound traffic from matched pods (egress is not restricted by this policy).

  • to-lport 1001: Allow inbound traffic from the same address set (same namespace pods).

  • to-lport 1000: Drop all other inbound traffic (default deny for selected pods).

Troubleshooting OVN-Kubernetes

This section covers common OVN-Kubernetes issues and how to diagnose them systematically.

Pod Cannot Reach Another Pod

Symptoms: Pod-to-pod communication fails (ping, curl timeouts).

Diagnostic Steps:

# Step 1: Verify both pods are running and get their IPs and nodes
oc get pods -n <namespace> -o wide
# Step 2: Check if both pods are on the same node or different nodes
# Same node -> issue is in the logical switch pipeline
# Different nodes -> could also be a tunnel issue
# Step 3: Check if there are NetworkPolicies blocking traffic
oc get networkpolicy -n <namespace>
# Step 4: Check if the OVN logical switch ports exist and are up
oc exec -n openshift-ovn-kubernetes ovnkube-node-<pod> \
  -c nbdb -- ovn-nbctl find Logical_Switch_Port name=<namespace>_<pod-name>

Look for up: [true]. If the port is down, the pod’s networking may not have been set up correctly.

# Step 5: Check the OVS port on the node
oc debug node/<node> -- chroot /host ovs-vsctl list-ports br-int | grep <port-id>
# Step 6: Use ovn-trace to simulate the packet path
oc exec -n openshift-ovn-kubernetes ovnkube-node-<pod> \
  -c nbdb -- ovn-trace --detailed <source-switch> \
  'inport == "<source-port>" && eth.src == <src-mac> && eth.dst == <gw-mac> && ip4.src == <src-ip> && ip4.dst == <dst-ip> && ip.ttl == 64'
# Step 7: For cross-node issues, check Geneve tunnel status
oc debug node/<source-node> -- chroot /host ovs-vsctl find Interface type=geneve | grep -E "name|link_state|remote_ip"

Service Not Load Balancing Correctly

Symptoms: Traffic to a Service always goes to the same backend, or some backends never receive traffic.

Diagnostic Steps:

# Step 1: Verify the Service and Endpoints
oc get svc <service-name> -n <namespace>
oc get endpoints <service-name> -n <namespace>
# Step 2: Check the OVN Load Balancer
oc exec -n openshift-ovn-kubernetes ovnkube-node-<pod> \
  -c nbdb -- ovn-nbctl lb-list | grep <service-clusterip>

Verify that all backend pod IPs appear in the load balancer VIP mapping. If a backend is missing, check if the pod is healthy and if its endpoint is registered.

# Step 3: Check which routers/switches the LB is attached to
oc exec -n openshift-ovn-kubernetes ovnkube-node-<pod> \
  -c nbdb -- ovn-nbctl ls-lb-list <switch-name>
oc exec -n openshift-ovn-kubernetes ovnkube-node-<pod> \
  -c nbdb -- ovn-nbctl lr-lb-list ovn_cluster_router

NetworkPolicy Not Being Enforced

Symptoms: Traffic that should be blocked by a NetworkPolicy is getting through (or vice versa).

Diagnostic Steps:

# Step 1: Verify the NetworkPolicy is applied
oc get networkpolicy -n <namespace> -o yaml
# Step 2: Check the corresponding OVN ACLs
oc exec -n openshift-ovn-kubernetes ovnkube-node-<pod> \
  -c nbdb -- ovn-nbctl acl-list <switch-name>
# Step 3: Check address sets - ensure the correct pod IPs are included
oc exec -n openshift-ovn-kubernetes ovnkube-node-<pod> \
  -c nbdb -- ovn-nbctl list Address_Set | grep -A 5 <namespace>

A common mistake is creating a NetworkPolicy with an empty podSelector: {} (matches all pods in the namespace) but forgetting that this makes the default behavior deny all for the selected pods. Any pod in the namespace will only be able to receive traffic that matches an explicit ingress rule in the policy.

 
# Step 4: Use ovn-trace to verify the ACLs are working as expected
# Trace from a source that should be allowed
# Trace from a source that should be denied
# Compare the ACL decisions in the trace output

EgressIP Not Working

Symptoms: Outbound traffic is not using the configured EgressIP; it is still using the node’s IP.

Diagnostic Steps:

# Step 1: Check the EgressIP resource status
oc get egressip <name> -o yaml

Look for status.items - each EgressIP should have an assigned node. If no node is assigned, check node labels.

# Step 2: Verify node labels
oc get nodes -l k8s.ovn.org/egress-assignable

If no nodes have this label, the EgressIP cannot be assigned.

# Step 3: Check the NAT rules on the assigned node's gateway router
oc exec -n openshift-ovn-kubernetes ovnkube-node-<pod> \
  -c nbdb -- ovn-nbctl lr-nat-list GR_<assigned-node>
# Step 4: Verify the EgressIP is configured on the node's interface
oc debug node/<assigned-node> -- chroot /host ip addr show br-ex | grep <egress-ip>

Node Network Issues

Symptoms: All pods on a specific node lose connectivity.

Diagnostic Steps:

# Step 1: Check if the ovnkube-node pod is running
oc get pods -n openshift-ovn-kubernetes -o wide | grep <node-name>
# Step 2: Check ovnkube-node pod logs
oc logs -n openshift-ovn-kubernetes ovnkube-node-<id> -c ovnkube-controller --tail=50
# Step 3: Check if OVS is running
oc debug node/<node-name> -- chroot /host systemctl status ovs-vswitchd
# Step 4: Check if ovn-controller is running and connected
oc debug node/<node-name> -- chroot /host ovs-appctl -t ovn-controller connection-status
# Step 5: Check the node's chassis registration in the SB DB
oc exec -n openshift-ovn-kubernetes ovnkube-node-<pod> \
  -c sbdb -- ovn-sbctl show | grep -A 5 <node-name>

If the chassis is missing, the node is not connected to the OVN SB DB.

OVN Database Issues

Symptoms: Cluster-wide networking issues, new pods not getting IPs, services not updating.

In IC mode (OCP 4.14+), each node runs standalone NB/SB databases - there is no Raft cluster. The Raft commands below apply only to pre-4.14 clusters or to RHOSP/RHOSO centralized deployments. For IC mode, check individual node database health using ovn-appctl -t /var/run/ovn/ovnnb_db.ctl ovsdb-server/get-db-storage-status OVN_Northbound from the respective ovnkube-node pod.

Diagnostic Steps:

# Step 1: Check the OVN database pods
oc get pods -n openshift-ovn-kubernetes | grep -E "control-plane|ovnkube-node" | head -5
# Step 2: Check database health on a node (IC mode, OCP 4.14+)
oc exec -n openshift-ovn-kubernetes ovnkube-node-<pod> \
  -c nbdb -- ovn-appctl -t /var/run/ovn/ovnnb_db.ctl \
  ovsdb-server/get-db-storage-status OVN_Northbound
# Step 3 (pre-4.14 only): Check Raft cluster health
# These commands return errors in IC mode where standalone DBs are used
oc exec -n openshift-ovn-kubernetes ovnkube-node-<pod> \
  -c nbdb -- ovn-appctl -t /var/run/ovn/ovnnb_db.ctl \
  cluster/status OVN_Northbound

For pre-4.14 Raft clusters, look for:

  • Role: Should be leader on one pod and follower on others.

  • Entries not yet committed: Should be 0 or very small.

  • Servers: All three servers should be listed and active.

Pre-4.14 clusters only: If the Raft cluster loses quorum (2 of 3 members down), the database becomes read-only. No new networking configurations can be applied. Existing pod connectivity continues to work because ovn-controller on each node continues to enforce the last known flows, but no changes can be made until quorum is restored. In IC mode (4.14+), database failure is isolated to a single node.

Summary

This module covered OVN-Kubernetes, the default CNI for OpenShift. Key takeaways:

  • OVN-Kubernetes maps Kubernetes concepts to OVN: Pods become logical switch ports, Services become load balancers, NetworkPolicies become ACLs with address sets, and EgressIPs become NAT rules.

  • The topology consists of per-node logical switches, a distributed cluster router, a join switch, and per-node gateway routers. This architecture provides distributed routing and local-first packet processing.

  • Packet flows follow predictable paths: Same-node traffic stays local in OVS, cross-node traffic uses Geneve tunnels, service traffic is handled by OVN load balancers, and external traffic goes through gateway routers with SNAT.

  • Network Policies are efficient thanks to address sets - pod membership changes update address sets without modifying ACLs.

  • EgressIP provides stable outbound IPs with automatic failover between eligible nodes.

  • Troubleshooting follows a systematic approach: Check pod status, verify OVN logical state (NB DB), check physical state (OVS flows, tunnels), and use ovn-trace to simulate packet paths.

  • oc debug node and oc exec into OVN-K pods are your primary tools for inspecting the networking stack without direct node access.

This module, combined with Module 08 on RHOSO, gives you a complete picture of how OVN is used across the Red Hat portfolio - from OpenStack VM networking to Kubernetes pod networking.
