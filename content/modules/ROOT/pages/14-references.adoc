= Module 14: References and Further Reading

== Overview

No workshop can cover everything. OVS and OVN are actively developed projects with deep technical surfaces - the kernel datapath alone has hundreds of tunable parameters, and OVN's logical flow pipeline grows with every release. This module collects the most important references, learning resources, and community channels so you can continue building expertise long after this workshop ends.

The references are organized by type: official documentation first, then man pages you will use daily, conference talks that explain design decisions you will not find in any man page, blog posts that walk through real-world problems, troubleshooting resources for when things break in production, training and certification paths, tools that make your life easier, community contribution guides, and finally a glossary of every term used throughout this workshop.


[NOTE]
.Key Concept
====
The upstream documentation for OVS and OVN is the single source of truth. Red Hat product documentation layers enterprise context on top, but when you need to understand how a feature actually works at the code level, upstream docs and man pages are where you go.
====

=== Red Hat Knowledgebase

The Red Hat Knowledgebase (https://access.redhat.com/search/) is the most important resource for troubleshooting production issues. Here is how to search it effectively:

*Effective search strategies:*

----
Search by component:
  "OVN" "ovn-controller" crash
  "OVS" "ovs-vswitchd" high CPU
  "neutron" "ML2/OVN" port binding

Search by error message (quote the exact message):
  "Unreasonably long 123456ms poll interval"
  "Error: cannot create a+bridge named br-int"
  "Resource not found"

Search by Red Hat version:
  RHOSP 17.1 OVN database cluster
  OpenShift 4.16 OVN-Kubernetes EgressIP

Filter results:
  - Use "Solutions" type for actionable fixes
  - Use "Articles" type for explanations and best practices
  - Filter by product and version for relevance
----


[NOTE]
.Key Concept
====
When you open a support case, always search the Knowledgebase first. About 60% of cases have an existing solution. Include the KB article number in your case if you found something relevant but it did not fully resolve the issue.

== 2. Essential Man Pages

Man pages are the most reliable reference for command syntax and options. They are maintained alongside the source code and are always accurate for the installed version.

=== OVS Management Commands


[cols="1,1,1",options="header"]
|===
|Man Page
|Section
|Description

|`ovs-vsctl(8)`
|8
|The primary tool for configuring OVS bridges, ports, and interfaces. Communicates with ovsdb-server to modify the Open_vSwitch database.

|`ovs-ofctl(8)`
|8
|Manage OpenFlow entries in OVS bridges. Use this to dump, add, modify, and delete flow rules. Essential for debugging packet forwarding.

|`ovs-appctl(8)`
|8
|Send commands to running OVS daemons (ovs-vswitchd, ovsdb-server). Use this for runtime debugging, coverage counters, and memory reports.

|`ovs-dpctl(8)`
|8
|Manage OVS datapaths. Inspect and manage kernel datapath flows. Useful for understanding what the kernel fast path is doing.

|`ovs-vswitchd(8)`
|8
|The OVS daemon man page. Documents startup options, logging, and runtime behavior of the switch daemon.

=== How to Access Man Pages

*On a standard RHEL/CentOS system:*

[source,bash]
----
# View the man page directly
man ovs-vsctl

# View a specific section
man 5 ovs-vswitchd.conf.db

# Search for man pages related to OVS
man -k ovs

# Search for man pages related to OVN
man -k ovn
----

*In containerized environments (RHOSP, RHOSO):*

[source,bash]
----
# RHOSP 17.1 - access man pages inside the OVS container
sudo podman exec -it ovs_vswitchd man ovs-vsctl

# RHOSP 17.1 - access man pages inside the OVN container
sudo podman exec -it ovn_controller man ovn-controller

# RHOSO - access man pages on an edpm node
ssh edpm-compute-0
sudo podman exec -it ovn_controller man ovn-controller
----

*In OpenShift (OVN-Kubernetes):*

[source,bash]
----
# Find the ovnkube-node pod
oc get pods -n openshift-ovn-kubernetes -l app=ovnkube-node

# Access man pages inside the container
oc exec -n openshift-ovn-kubernetes <pod-name> -c ovn-controller -- man ovn-controller

# Alternative: use oc debug to get a shell on a node
oc debug node/<node-name>
chroot /host
man ovs-vsctl
----


[NOTE]
====
If man pages are not installed in the container, you can access the same content online at https://docs.openvswitch.org/en/latest/ref/ and https://docs.ovn.org/en/latest/ref/. The online versions match the upstream releases, so verify the version matches what is deployed.
====

== 7. Tools and Utilities

=== Debugging Scripts and One-Liners

The following commands and scripts are useful for quick debugging in production. Keep them in your toolkit.

*OVS Debugging One-Liners:*

[source,bash]
----
# Show all bridges and their ports in a compact format
sudo ovs-vsctl show | grep -E '(Bridge|Port|Interface|type:)'

# List all OpenFlow rules with packet/byte counters (shows active flows)
sudo ovs-ofctl dump-flows br-int --no-stats=false | sort -t',' -k1 -n

# Watch for flow table changes in real time
sudo ovs-ofctl monitor br-int watch:

# Show datapath flows with statistics (kernel fast-path entries)
sudo ovs-dpctl dump-flows

# Show coverage counters (useful for identifying hot paths)
sudo ovs-appctl coverage/show

# Show memory usage of ovs-vswitchd
sudo ovs-appctl memory/show

# Check for unreasonably long poll intervals (performance issue indicator)
sudo journalctl -u ovs-vswitchd --since "1 hour ago" | grep "Unreasonably long"

# Show connection tracking entries
sudo ovs-appctl dpctl/dump-conntrack

# Show the number of flows per table
sudo ovs-ofctl dump-flows br-int | awk -F'table=' '{print $2}' | awk -F',' '{print $1}' | sort -n | uniq -c | sort -rn
----

*OVN Debugging One-Liners:*

[source,bash]
----
# Show OVN cluster status (run on a controller node)
sudo ovn-appctl -t /var/run/ovn/ovnnb_db.ctl cluster/status OVN_Northbound
sudo ovn-appctl -t /var/run/ovn/ovnsb_db.ctl cluster/status OVN_Southbound

# Show all logical switches and their ports
sudo ovn-nbctl show

# Show all chassis registrations
sudo ovn-sbctl show

# List port bindings and their chassis assignment
sudo ovn-sbctl list Port_Binding | grep -E '(logical_port|chassis|type)'

# Show logical flows for a specific logical switch
sudo ovn-sbctl lflow-list <switch-name>

# Trace a packet through OVN
sudo ovn-trace <switch-name> 'inport=="<port>" && eth.src==<mac> && eth.dst==<mac> && ip4.src==<src-ip> && ip4.dst==<dst-ip>'

# Show OVN connection status on a compute node
sudo ovn-appctl -t ovn-controller connection-status

# Check if ovn-controller is connected to the Southbound DB
sudo ovs-vsctl get open_vswitch . external_ids:ovn-remote

# Show the OVN version on this node
sudo ovn-controller --version
----

*Combined OVS/OVN debugging script:*

[source,bash]
----
#!/bin/bash
# quick-diag.sh - Quick OVS/OVN diagnostic script
# Usage: sudo bash quick-diag.sh

echo "=== OVS Version ==="
ovs-vsctl --version | head -1

echo ""
echo "=== OVN Version ==="
ovn-controller --version 2>/dev/null || echo "OVN controller not installed"

echo ""
echo "=== OVS Bridges ==="
ovs-vsctl list-br

echo ""
echo "=== OVS Daemon Status ==="
systemctl is-active ovs-vswitchd ovsdb-server 2>/dev/null || \
  pidof ovs-vswitchd ovsdb-server

echo ""
echo "=== OVN Controller Status ==="
ovn-appctl -t ovn-controller connection-status 2>/dev/null || \
  echo "OVN controller not running"

echo ""
echo "=== OpenFlow Flow Count per Table ==="
ovs-ofctl dump-flows br-int 2>/dev/null | \
  awk -F'table=' '{print $2}' | awk -F',' '{print $1}' | \
  sort -n | uniq -c | sort -rn

echo ""
echo "=== Datapath Flow Count ==="
ovs-dpctl dump-flows 2>/dev/null | wc -l

echo ""
echo "=== Recent Errors (last 30 min) ==="
journalctl -u ovs-vswitchd -u ovsdb-server -u ovn-controller \
  --since "30 min ago" -p err --no-pager 2>/dev/null | tail -20
----

== 8. Community and Contribution

=== How to Contribute to OVS Upstream

Contributing to OVS is done via email using `git send-email`. The project does not use GitHub pull requests for code contributions (though issues are tracked on GitHub).

*Setting up your environment:*

[source,bash]
----
# Clone the repository
git clone https://github.com/openvswitch/ovs.git
cd ovs

# Configure git for sending patches
git config sendemail.to ovs-dev@openvswitch.org
git config sendemail.smtpserver smtp.example.com
git config sendemail.smtpserverport 587
git config sendemail.smtpencryption tls
git config sendemail.smtpuser you@example.com

# Build OVS from source
./boot.sh
./configure
make -j$(nproc)
----

*Submitting a patch:*

[source,bash]
----
# Create a branch for your change
git checkout -b fix-something

# Make your changes and commit
git add <files>
git commit -s   # -s adds Signed-off-by

# Send the patch to the mailing list
git send-email --to=ovs-dev@openvswitch.org HEAD~1

# For a patch series
git send-email --to=ovs-dev@openvswitch.org --cover-letter HEAD~3
----

*Patch formatting requirements:*

----
1. Subject line: Start with the component name followed by a colon
   Example: "ofproto: Fix flow deletion with wildcards"
   Example: "ovn-controller: Handle missing chassis gracefully"

2. Commit message body:
   - Explain what the patch does and why
   - Reference any related bugs or discussions
   - Keep lines under 72 characters

3. Sign-off: Every patch must include a Signed-off-by line
   Signed-off-by: Your Name <your.email@example.com>

4. Testing: Mention what tests you ran
   - make check (unit tests)
   - make check-system-userspace (system tests in userspace)

5. Updates: When submitting a revised patch, include version information
   Subject: [PATCH v2] ofproto: Fix flow deletion with wildcards
   Add a changelog below the "---" line in the commit message
----

=== How to Contribute to OVN Upstream

OVN follows the same contribution process as OVS since it was originally part of the same project.

[source,bash]
----
# Clone OVN
git clone https://github.com/ovn-org/ovn.git
cd ovn

# OVN depends on OVS - you need the OVS source tree
git clone https://github.com/openvswitch/ovs.git

# Build OVN
cd ovn
./boot.sh
./configure --with-ovs-source=../ovs
make -j$(nproc)

# Run the test suite
make check TESTSUITEFLAGS="-j$(nproc)"

# Send patches to the mailing list
git send-email --to=ovs-dev@openvswitch.org HEAD~1
----


[NOTE]
====
OVN patches go to the same `ovs-dev@openvswitch.org` mailing list as OVS patches. Prefix your patch subjects with `ovn-` to distinguish them from OVS patches.
====


=== Code Review Process

----
1. Submit your patch to the mailing list
2. Automated CI will test your patch (results posted to the mailing list)
3. Community members review your patch:
   - Reviewed-by: Reviewer approves the patch
   - Acked-by: Reviewer acknowledges the patch is correct
   - Nacked-by: Reviewer objects to the patch (must be addressed)
   - Comment: Reviewer has questions or suggestions
4. Address review comments by sending a revised patch (v2, v3, etc.)
5. A committer merges the patch when it has sufficient reviews

Typical review cycle: 1-2 weeks for straightforward patches.
Complex patches may take multiple revision cycles.
----

=== How to Report Bugs Effectively

Whether reporting upstream or to Red Hat, an effective bug report dramatically speeds up resolution.

----
A good bug report includes:

1. Environment:
   - OVS version (ovs-vsctl --version)
   - OVN version (ovn-controller --version)
   - OS version (cat /etc/redhat-release)
   - Kernel version (uname -r)
   - Product version (RHOSP 17.1, OpenShift 4.16, etc.)

2. Problem description:
   - What you expected to happen
   - What actually happened
   - When it started (date/time, after an upgrade, etc.)

3. Steps to reproduce:
   - Exact commands or API calls
   - Configuration files (sanitized of credentials)
   - Network topology

4. Diagnostic data:
   - sosreport (RHOSP/RHEL) or must-gather (OpenShift)
   - Relevant log snippets
   - ovs-vsctl show output
   - ovn-nbctl show / ovn-sbctl show output
   - Flow dumps if relevant

5. Impact:
   - How many systems/tenants are affected
   - Is there a workaround
   - Is the issue intermittent or consistent
----


[NOTE]
.Key Concept
====
The fastest way to get a bug fixed is to provide a minimal reproducer. If you can reduce the issue to a simple test case (for example, "create two VMs on different computes, send traffic between them, observe packet loss"), the developer can reproduce and fix it much faster than working from logs alone.

== 9. Glossary

This glossary defines every essential term used throughout this workshop. Terms are listed alphabetically. Refer back to this section whenever you encounter an unfamiliar term.


[cols="1,1",options="header"]
|===
|Term
|Definition

|*ACL (Access Control List)*
|An OVN construct that filters traffic on logical switch ports. ACLs are applied to ingress or egress traffic and support connection tracking for stateful filtering. In OpenStack, security groups are translated into OVN ACLs.

|*BFD (Bidirectional Forwarding Detection)*
|A lightweight protocol used by OVN to detect link failures between chassis. BFD runs over the Geneve tunnels and enables fast failover of gateway chassis when a link goes down. Operates at sub-second detection intervals.

|*Bridge*
|An OVS construct that acts as a virtual Ethernet switch. A bridge has ports, processes traffic using OpenFlow rules, and can forward, drop, or modify packets. The most important bridge in OVS/OVN deployments is `br-int` (the integration bridge).

|*Chassis*
|An OVN term for a physical or virtual host running `ovn-controller`. Each chassis registers itself in the OVN Southbound database and is identified by a unique name. Chassis can be compute nodes, gateway nodes, or network nodes.

|*Cluster (OVN/Raft)*
|A group of three or more OVN database servers (northbound or southbound) running the Raft consensus protocol for high availability. The cluster elects a leader that handles all writes, while followers replicate the data.

|*Conntrack (Connection Tracking)*
|A mechanism in the Linux kernel (and OVS) that tracks the state of network connections (new, established, related, invalid). OVN uses conntrack to implement stateful ACLs and NAT. Conntrack zones isolate tracking domains.

|*Datapath*
|The component of OVS that performs the actual packet forwarding. The kernel datapath uses kernel modules for fast forwarding. The userspace datapath (used with DPDK) runs entirely in user space for even higher performance.

|*DHCP*
|Dynamic Host Configuration Protocol. OVN includes a native DHCP responder that handles DHCP requests directly in the logical pipeline without requiring an external DHCP server or agent. Configured via DHCP_Options in the NB DB.

|*DPDK (Data Plane Development Kit)*
|A set of libraries and drivers for fast packet processing in user space, bypassing the kernel network stack. OVS can use DPDK for its datapath, achieving significantly higher throughput and lower latency than the kernel datapath.

|*Encapsulation*
|The process of wrapping a packet inside another packet for transport across a physical network. OVN uses Geneve encapsulation by default to carry logical network traffic between chassis. The encapsulation header carries metadata including the logical datapath and logical port identifiers.

|*Flow*
|A set of match criteria and actions that define how a packet should be processed. In OVS, flows are OpenFlow rules installed in bridge flow tables. Flows match on packet headers and specify actions like output, drop, modify, or send to controller.

|*Gateway Chassis*
|A chassis designated to handle north-south traffic (traffic entering or leaving the OVN logical network). Gateway chassis host the logical router gateway ports and perform SNAT/DNAT. Multiple gateway chassis can be configured for high availability.

|*Geneve (Generic Network Virtualization Encapsulation)*
|The tunneling protocol used by OVN for overlay traffic between chassis. Geneve is preferred over VXLAN because it supports variable-length metadata in TLV (Type-Length-Value) format, which OVN uses to carry logical flow information. Defined in RFC 8926.

|*Logical Datapath*
|An OVN abstraction representing a logical switch or logical router in the Southbound database. Each logical datapath has a unique tunnel key used in Geneve encapsulation to identify which logical network a packet belongs to.

|*Logical Flow*
|A flow rule in the OVN Southbound database that represents processing logic for a logical datapath. Logical flows are generated by `ovn-northd` and consumed by `ovn-controller`, which translates them into OpenFlow rules for the local OVS instance.

|*Logical Port*
|A port on an OVN logical switch or logical router. Logical ports are virtual constructs that can be bound to physical ports on chassis. Types include VIF (virtual interface), localnet (connection to a physical network), router (connection to a logical router), and others.

|*Logical Router*
|An OVN abstraction for Layer 3 routing between logical switches. Logical routers support static routes, NAT, load balancing, and gateway functionality. They can be distributed (processing on every chassis) or centralized (processing on a gateway chassis).

|*Logical Switch*
|An OVN abstraction for a Layer 2 broadcast domain. Logical switches connect logical ports and provide switching, DHCP, ARP handling, and ACL enforcement. Each logical switch is isolated from others unless connected through a logical router.

|*Match*
|The criteria portion of a flow rule that determines which packets the flow applies to. Matches can specify values for any packet header field (MAC addresses, IP addresses, TCP/UDP ports, VLAN tags, etc.) and support wildcards and masks.

|*Megaflow*
|An OVS optimization that combines multiple microflows (exact-match flows) into a single wildcard flow in the kernel datapath cache. Megaflows reduce the number of cache entries needed and the frequency of upcalls to the userspace daemon. The megaflow cache is also called the datapath classifier (dpcls).

|*NAT (Network Address Translation)*
|The process of modifying source or destination IP addresses as packets traverse a router. OVN supports both SNAT (source NAT, for outbound traffic) and DNAT (destination NAT, for inbound traffic such as floating IPs).

|*Northbound Database (NB DB)*
|The OVN database that stores the logical network configuration as defined by the cloud management system (OpenStack Neutron, Kubernetes, etc.). Contains tables for logical switches, routers, ports, ACLs, NAT rules, and load balancers. This is the "desired state" database.

|*OpenFlow*
|The protocol used to program the forwarding behavior of OVS bridges. OpenFlow defines match-action rules organized in numbered tables. OVS supports OpenFlow versions up to 1.5. OVN generates OpenFlow rules automatically; you rarely need to write them manually.

|*OVN Controller*
|The local daemon (`ovn-controller`) running on each chassis (hypervisor/node). It connects to the OVN Southbound database, receives logical flows, translates them into OpenFlow rules, and installs them in the local OVS instance. It also manages tunnel endpoints and port bindings.

|*OVN Northd*
|The central daemon (`ovn-northd`) that translates the high-level logical network configuration from the Northbound database into low-level logical flows in the Southbound database. It runs the "compilation" step of OVN's pipeline.

|*OVS (Open vSwitch)*
|A production-quality, multilayer virtual switch. OVS provides the data plane for OVN and is used to forward packets using OpenFlow rules. It supports kernel and userspace (DPDK) datapaths, VLAN tagging, tunneling, QoS, and connection tracking.

|*OVSDB*
|The database protocol and server used by OVS and OVN to store configuration and state. OVSDB is defined in RFC 7047 and supports transactions, monitoring, and clustering (via Raft). The OVS database (`conf.db`) and OVN databases (NB DB, SB DB) all use OVSDB.

|*Physical Flow*
|An OpenFlow rule installed in the local OVS instance on a specific chassis. Physical flows are the result of `ovn-controller` translating logical flows into concrete forwarding rules that reference physical ports, tunnel endpoints, and real MAC/IP addresses.

|*Pipeline (Ingress/Egress)*
|The ordered sequence of logical flow tables that a packet traverses in OVN. The ingress pipeline processes packets entering a logical port; the egress pipeline processes packets leaving a logical port. Each pipeline consists of numbered tables with specific functions (ACL, LB, routing, etc.).

|*PMD (Poll Mode Driver)*
|A DPDK concept where dedicated CPU cores continuously poll network interfaces for packets, eliminating interrupt overhead. In OVS-DPDK, PMD threads are pinned to specific CPU cores and are responsible for packet processing in the userspace datapath.

|*Port Binding*
|The process by which an OVN logical port is associated with a specific chassis. When a VM or container starts, `ovn-controller` on that chassis claims the port binding in the Southbound database, telling other chassis where to send traffic for that port.

|*Port Security*
|An OVN feature that restricts traffic on a logical port to only the configured MAC and IP addresses. Prevents MAC spoofing and IP spoofing. In OpenStack, port security is enabled by default and enforced through OVN logical flows.

|*Raft*
|A distributed consensus protocol used by OVSDB for database clustering. Raft ensures that all database replicas agree on the same data, tolerates the failure of a minority of nodes, and automatically elects a new leader when the current leader fails. OVN uses Raft for both the NB DB and SB DB clusters.

|*SNAT/DNAT*
|Source NAT and Destination NAT. SNAT modifies the source IP address of outbound packets (used for tenant network egress to external networks). DNAT modifies the destination IP address of inbound packets (used for floating IPs and load balancing). Both are implemented in OVN using conntrack.

|*Southbound Database (SB DB)*
|The OVN database that stores the runtime state of the logical network. Contains logical flows (generated by `ovn-northd`), chassis registrations, port bindings, MAC bindings, and other state. This is the "compiled state" database that `ovn-controller` reads.

|*Table (OpenFlow)*
|A numbered stage in the OpenFlow pipeline of an OVS bridge. Each table contains flow rules. Packets enter at table 0 and can be sent to subsequent tables using the `resubmit` action. OVN uses specific table numbers for specific functions (e.g., table 0 for ingress port classification).

|*Tunnel*
|A network path that encapsulates packets for transport across an underlay network. OVN creates Geneve tunnels between chassis automatically. Each tunnel carries traffic for all logical networks, using metadata in the Geneve header to demultiplex packets to the correct logical datapath and port.

|*Userspace Datapath*
|An OVS datapath that processes packets entirely in user space instead of the kernel. Used with DPDK for high-performance networking. The userspace datapath bypasses the kernel network stack and accesses NICs directly through DPDK poll mode drivers.

|*VXLAN (Virtual Extensible LAN)*
|A tunneling protocol that encapsulates Layer 2 Ethernet frames in UDP packets. OVN supports VXLAN for communication with hardware VTEPs (physical switches) but prefers Geneve for chassis-to-chassis traffic because VXLAN's 24-bit VNI cannot carry the metadata that OVN needs.

|*Zone (Conntrack)*
|A conntrack zone is a namespace that isolates connection tracking state. OVN assigns different zones to different logical datapaths so that connection tracking state for one logical network does not interfere with another. Zones are identified by numeric IDs and are managed by `ovn-controller`.

|===


[NOTE]
.Key Concept
====
Understanding these terms is essential for reading OVN documentation, interpreting OVS/OVN command output, and communicating effectively with the development team and Red Hat support. When in doubt, refer back to this glossary.
