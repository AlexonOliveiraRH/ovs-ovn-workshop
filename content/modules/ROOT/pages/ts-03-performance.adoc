= Scenario 03: Severe Performance Degradation Under Load

== The Problem

*Customer report:* "Network throughput between pods dropped from 9 Gbps to under 1 Gbps
after deploying new security group rules. CPU usage on compute nodes is very high."

The customer recently deployed over 200 NetworkPolicy objects to meet new compliance
requirements. Before the policies were applied, pod-to-pod throughput was consistently
around 9.2 Gbps. After applying the policies, throughput dropped to 0.7 Gbps and
applications began timing out. The `ovs-vswitchd` process on worker nodes is consuming
near 100% of a CPU core.

*Finding:* The handler and revalidator threads are consuming significant CPU. Handler

being heavily loaded means the fast path is not working efficiently.


[NOTE]
.Key Concept
====
OVS processes packets in two paths: - *Fast path (kernel datapath):* Packets matching an existing datapath flow are handled entirely in the kernel, achieving line-rate performance. - *Slow path (userspace):* Packets that don't match any datapath flow generate an "upcall" to `ovs-vswitchd` in userspace. The daemon looks up the correct action in the OpenFlow tables, installs a new datapath flow for future packets, and handles the current packet. This is orders of magnitude slower than the fast path.  When most packets take the slow path, performance degrades severely because every packet requires a context switch to userspace and back.
====

----

*Finding:* The datapath flows have *exact match masks* (`/255.255.255.255` for IPs,
`/0xffff` for ports). This means OVS cannot wildcard - each unique 5-tuple (src IP, dst IP,
src port, dst port, protocol) creates a separate datapath entry. This is a **microflow
explosion**.


[NOTE]
.Key Concept
====
OVS uses *megaflows* to optimize the datapath. A megaflow is a wildcarded flow entry that matches many packets at once. For example, a megaflow with mask `src=10.128.2.0/255.255.255.0` would match all packets from the 10.128.2.0/24 subnet in a single entry. When the OpenFlow table has many specific rules (per-IP matches), OVS cannot create wildcarded megaflows and falls back to microflows (exact match per-connection). With microflows, the datapath grows with the number of active connections, quickly overwhelming the system.
====


Check megaflow mask statistics:

[source,bash]
----
[user@bastion ~]$ oc debug node/worker-3.ocp.example.com -- chroot /host \
  ovs-appctl dpctl/dump-mega-stats

----

*Finding:* There are *2,847 unique masks* and the average *masks per lookup is 12.47*.
In a healthy system, you want masks/lookup to be under 4-5. At 12.47, every packet lookup
must check an average of 12.47 masks before finding a match, which is extremely slow.

=== Step 5: Check Conntrack Table

*Why:* OVN uses connection tracking (conntrack) for stateful ACL enforcement. Every allowed
connection gets a conntrack entry. If the conntrack table fills up, new connections are
dropped or severely delayed.

[source,bash]
----
[user@bastion ~]$ oc debug node/worker-3.ocp.example.com -- chroot /host \
  cat /proc/sys/net/netfilter/nf_conntrack_max
----

----
262144
----

[source,bash]
----
[user@bastion ~]$ oc debug node/worker-3.ocp.example.com -- chroot /host \
  cat /proc/sys/net/netfilter/nf_conntrack_count
----

----
248901
----

*Finding:* The conntrack table is at *248,901 / 262,144* entries - that is **95%
full**. When the table is nearly full, performance degrades because:

* Hash bucket chains become long, slowing lookups
* New connections may be dropped if the table fills completely
* Garbage collection runs more frequently, consuming CPU

[WARNING]
====
Never write NetworkPolicies that select individual pod instances. Use broad label selectors that match groups of pods. A single rule `from: [{podSelector: {matchLabels: {app: api-gateway}}}]` replaces 50 individual instance rules and generates ONE ACL instead of 50.

flow_del                                 3234        6432        1198765
----

*Finding:*

* `rev_revalidate`: *8,234 revalidations in the last 5 seconds* - this is extremely high.
  Revalidation compares each datapath flow against the OpenFlow table, and with 87,000
  OpenFlow entries, each comparison is expensive.

* `upcall_flow_limit_hit`: *567 in the last 5 seconds* - the datapath has hit its flow
  limit, meaning new flows cannot be installed and packets must take the slow path.

* `flow_create` and `flow_del` rates are nearly equal (~3,400/5s each) - the datapath is
  in a constant churn of creating and deleting flows, providing no stable fast-path cache.


[NOTE]
.Key Concept
====
Revalidation is the process where OVS checks that each cached datapath flow is still consistent with the OpenFlow table. When the OpenFlow table is large, each revalidation is costly. When flows are being added and deleted rapidly, the revalidator threads run constantly, consuming CPU and reducing the time available for actual packet processing.
====

== Root Cause

The performance degradation was caused by a cascade of effects triggered by the deployment
of 200+ overly granular NetworkPolicy objects:

. *NetworkPolicies used per-pod selectors* instead of label-based selectors, causing
   each policy to generate many individual ACL rules.

. *42,367 OVN ACLs* were created, which ovn-controller compiled into **87,234 OpenFlow
   flows** in OVS on each node.

. *The large OpenFlow table prevented efficient megaflow creation.* Because the OpenFlow
   rules matched on specific IP addresses, OVS could not create wildcarded datapath entries.
   Every unique connection required its own datapath flow (microflow explosion).

. *The datapath flow table reached its limit* (124,567 / 131,072), causing constant
   flow eviction and recreation (churn).

. *High upcall rate* - most packets took the slow path through userspace because they
   missed the datapath cache or their cached flow was evicted.

. *The conntrack table was nearly full* (248,901 / 262,144), causing slow hash lookups
   and dropped new connections.

. *ovs-vswitchd consumed 97% CPU* handling upcalls, leaving no headroom for actual
   packet forwarding.


[NOTE]
.Key Concept
====
The fast path vs slow path distinction is critical for understanding OVS performance:  ```text FAST PATH (kernel): Packet arrives -> Datapath flow lookup -> Match found -> Action executed Latency: ~1 microsecond Throughput: line rate (25 Gbps+)  SLOW PATH (userspace): Packet arrives -> Datapath flow lookup -> No match (MISS) -> Upcall to ovs-vswitchd -> OpenFlow table lookup -> Install datapath flow -> Return packet to kernel -> Execute action Latency: ~100-1000 microseconds Throughput: < 1 Gbps (CPU limited) ```  When the majority of packets take the slow path, performance drops from line-rate to sub-gigabit levels regardless of the physical network speed.
====

== Prevention

=== 1. Monitor Flow Count and Conntrack Table Size

Set up Prometheus monitoring and alerts:

----
# Alert if OpenFlow flow count exceeds 10,000:
- alert: OVSHighFlowCount
  expr: ovs_flow_count > 10000
  for: 5m
  labels:
    severity: warning
  annotations:
    summary: "OVS flow count is high on {{ $labels.instance }}"
    description: "Flow count is {{ $value }}, which may indicate NetworkPolicy explosion."

# Alert if conntrack table is over 80% full:
- alert: ConntrackTableNearFull
  expr: node_nf_conntrack_entries / node_nf_conntrack_entries_limit > 0.8
  for: 5m
  labels:
    severity: critical
  annotations:
    summary: "Conntrack table nearly full on {{ $labels.instance }}"

=== 2. Establish NetworkPolicy Best Practices

Document and enforce these guidelines:

----
NetworkPolicy Best Practices:
1. Use label selectors, NEVER per-pod/per-instance selectors
2. Use namespaceSelector for cross-namespace policies
3. Combine ingress rules with the same ports into a single rule
4. Prefer fewer, broader policies over many narrow ones
5. Test policy impact in staging before production deployment
6. Monitor OVS flow count after applying new policies
7. Review policies quarterly for consolidation opportunities
----

== Key Takeaways

* *NetworkPolicy granularity directly impacts OVS performance.* Per-pod selectors create
  per-pod ACLs, which create per-pod OpenFlow flows, which prevent efficient megaflow
  caching. Use broad label selectors wherever possible.

* *Monitor OVS flow count and conntrack table size* as key performance indicators. A
  sudden increase in either after a policy change is a red flag.

* *The fast path / slow path distinction explains most OVS performance issues.* When
  most packets take the slow path through userspace, throughput drops by 10-100x regardless
  of physical network speed.

* *Conntrack table exhaustion causes silent connection drops.* Always size the conntrack
  table appropriately and monitor its utilization.

* *Always load-test NetworkPolicy changes* in a staging environment before deploying to
  production. A simple iperf3 test before and after can reveal performance regressions
  before they affect production workloads.
