== What is RHOSO

Red Hat OpenStack Services on OpenShift (RHOSO) represents a fundamental shift in how OpenStack is deployed and managed. Instead of running OpenStack services as traditional systemd services on dedicated controller nodes (as in RHOSP), RHOSO runs the OpenStack control plane as containerized workloads managed by Kubernetes operators on an OpenShift cluster.


[NOTE]
.Key Concept
====
RHOSO splits the OpenStack deployment into two distinct domains: the *control plane* (OpenStack services running as pods on OpenShift) and the *data plane* (compute, networking, and storage services running on bare-metal nodes or VMs outside the OpenShift cluster).
====


=== The High-Level Architecture

----
+---------------------------------------------------------------+
|                   OpenShift Cluster (Control Plane)            |
|                                                                |
|  +------------------+  +------------------+  +---------------+ |
|  | Neutron API Pod  |  | Nova API Pod     |  | Glance Pod    | |
|  +------------------+  +------------------+  +---------------+ |
|  +------------------+  +------------------+  +---------------+ |
|  | OVN NB DB Pod    |  | OVN SB DB Pod    |  | ovn-northd    | |
|  |                  |  |                  |  | Pod           | |
|  +------------------+  +------------------+  +---------------+ |
|  +------------------+  +------------------+                    |
|  | Keystone Pod     |  | MariaDB/Galera   |                    |
|  +------------------+  +------------------+                    |
|                                                                |
+-------------------------------+--------------------------------+
                                |
                    Control Network (API, OVN SB)
                                |
        +-----------------------+-----------------------+
        |                       |                       |
+-------+--------+    +--------+-------+    +-----------+----+
| Data Plane     |    | Data Plane     |    | Data Plane     |
| Node 1         |    | Node 2         |    | Node 3         |
| (Compute)      |    | (Compute)      |    | (Compute/Net)  |
|                |    |                |    |                |
| ovn-controller |    | ovn-controller |    | ovn-controller |
| OVS (br-int)   |    | OVS (br-int)   |    | OVS (br-int)   |
| nova-compute   |    | nova-compute   |    | nova-compute   |
+----------------+    +----------------+    +----------------+
----

=== Why the Shift from RHOSP to RHOSO

The move to RHOSO brings several operational advantages:


[cols="1,1,1",options="header"]
|===
|Aspect
|RHOSP (Traditional)
|RHOSO (Operator-Based)

|Control plane hosting
|Dedicated controller nodes (bare metal or VMs)
|OpenShift pods managed by operators

|Lifecycle management
|Director (TripleO), manual upgrades
|Kubernetes operators, declarative CRDs

|Scaling control plane
|Complex, requires re-deployment
|Scale pods horizontally via OpenShift

|High availability
|Pacemaker/HAProxy clusters
|Kubernetes native HA (replicas, liveness probes)

|Configuration management
|Puppet, Heat templates
|Kubernetes CRDs, operator reconciliation

|Data plane management
|TripleO-managed overcloud nodes
|edpm-ansible via OpenStackDataPlaneNodeSet CRDs

|===


[NOTE]
====
RHOSO 18.0 is the first major release following this new architecture. It replaces RHOSP 17.1 as the forward-looking deployment model for Red Hat OpenStack.
====

== Networking Architecture in RHOSO

Networking in RHOSO involves two fundamentally different domains that must work together seamlessly: the OpenShift cluster networking (for the control plane) and the traditional OVS/OVN networking (for the data plane where VMs actually run).

=== Control Plane Networking

The OpenShift cluster uses its own networking stack (OVN-Kubernetes, covered in Module 09) for communication between the OpenStack service pods. However, OpenStack services often need connectivity to networks that exist outside the OpenShift pod network - for example, the OVN southbound database must be reachable by ovn-controller instances running on data plane nodes.

This is where *NetworkAttachmentDefinitions (NADs)* come in.


[NOTE]
.Key Concept
====
A NetworkAttachmentDefinition is a Kubernetes Custom Resource that defines an additional network interface for pods. In RHOSO, NADs are used to give OpenStack service pods connectivity to external networks - such as the internal API network, the tenant tunnel network, or the storage network - that exist outside the OpenShift pod network.
====


----
+---------------------------------------------------------------+
|                    OpenShift Cluster                           |
|                                                                |
|  Default Pod Network (OVN-Kubernetes CNI)                      |
|  +---------+  +---------+  +---------+                        |
|  | Pod A   |  | Pod B   |  | Pod C   |  <-- Standard pod IPs  |
|  +---------+  +---------+  +---------+                        |
|                                                                |
|  Additional Networks via NADs (Multus CNI)                     |
|  +---------+  +---------+                                      |
|  | OVN DB  |  | Neutron |                                      |
|  | Pod     |  | Pod     |                                      |
|  | net1:   |  | net1:   |  <-- Additional NICs from NADs       |
|  | 172.17. |  | 172.17. |      (internal API, tenant, etc.)    |
|  +---------+  +---------+                                      |
|                                                                |
+---------------------------------------------------------------+
----

=== How NADs Work in RHOSO

Multus is a meta-CNI plugin that runs on OpenShift and allows pods to have multiple network interfaces. The primary interface uses the cluster's default CNI (OVN-Kubernetes), while additional interfaces are configured through NADs.

In a RHOSO deployment, you will typically find NADs for:


[cols="1,1,1",options="header"]
|===
|NAD Name
|Purpose
|Example Subnet

|internalapi
|Communication between OpenStack services
|172.17.0.0/24

|tenant
|Tenant/tunnel network for Geneve overlay traffic
|172.19.0.0/24

|storage
|Storage network (Ceph, NFS)
|172.18.0.0/24

|storagemgmt
|Storage management network
|172.20.0.0/24

|ctlplane
|Control plane provisioning network
|192.168.122.0/24

|external
|External/public API access
|10.0.0.0/24

=== Data Plane Networking

The data plane nodes are where the actual VM workloads run. These nodes have:

* *OVS (Open vSwitch):* The virtual switch that provides the data plane forwarding
* *ovn-controller:* The local OVN agent that programs OVS based on instructions from the OVN southbound database
* *nova-compute:* The compute service that manages VM lifecycle
* *os-net-config:* Network configuration tool for the data plane node interfaces

Data plane nodes require connectivity to several networks:


[cols="1,1,1",options="header"]
|===
|Network
|Purpose
|Used By

|Control plane
|Communication with OpenShift for provisioning
|edpm-ansible, SSH

|Internal API
|OpenStack service API calls
|nova-compute, ovn-controller

|Tenant
|Geneve tunnel traffic between compute nodes
|OVS, ovn-controller

|Storage
|VM disk I/O to storage backends
|nova-compute, cinder

|Provider/External
|VM external network access (floating IPs, provider nets)
|OVS, neutron-ovn-metadata-agent

|===


=== The OpenStack Operator

The OpenStack Operator is the top-level Kubernetes operator that manages the entire RHOSO deployment. It is responsible for:

. Deploying and configuring all OpenStack service operators (Nova, Neutron, Glance, etc.)
. Managing the OVN control plane components (OVN NB/SB databases, ovn-northd)
. Coordinating with the data plane operator for compute node management

== OVN in RHOSO

OVN is the default and only supported networking backend in RHOSO. Unlike RHOSP, which historically supported both ML2/OVS and ML2/OVN, RHOSO standardizes entirely on OVN.

=== OVN Architecture in RHOSO

The OVN deployment in RHOSO splits across the two domains:

*On OpenShift (Control Plane Pods):*


[cols="1,1,1",options="header"]
|===
|Component
|Runs As
|Purpose

|OVN Northbound Database (NB DB)
|StatefulSet pod
|Stores the logical network configuration (logical switches, routers, ACLs)

|OVN Southbound Database (SB DB)
|StatefulSet pod
|Stores the physical-logical bindings (chassis, port bindings, tunnel endpoints)

|ovn-northd
|Deployment pod
|Translates NB DB entries into SB DB logical flows

|===


*On Data Plane Nodes:*


[cols="1,1,1",options="header"]
|===
|Component
|Runs As
|Purpose

|ovn-controller
|systemd service
|Reads SB DB logical flows and programs OVS accordingly

|OVS (ovs-vswitchd)
|systemd service
|Performs the actual packet forwarding in the data path

|ovsdb-server
|systemd service
|Manages the local OVS configuration database

|===


----

=== How the Distributed Model Works

The flow of network configuration in RHOSO follows this path:

. *A user or Neutron creates a network resource* (e.g., a new network, subnet, or port) via the Neutron API running in an OpenShift pod.

. *Neutron writes to the OVN Northbound Database.* The Neutron ML2/OVN driver translates Neutron API objects into OVN logical network objects and writes them to the NB DB pod.

. *ovn-northd translates logical configuration to logical flows.* The ovn-northd pod reads the NB DB and generates logical flow entries in the SB DB.

. *ovn-controller on each data plane node reads the SB DB.* Each ovn-controller connects to the OVN SB DB pod over the internal API network. It reads only the logical flows relevant to its chassis (the ports bound locally) and programs OVS accordingly.

. *OVS forwards packets.* The programmed OpenFlow rules in OVS handle the actual packet switching, routing, NAT, and ACL enforcement on the data plane node.


[NOTE]
.Key Concept
====
The OVN SB DB pod must be reachable from all data plane nodes over the internal API network. This connectivity is typically provided through a NAD that connects the SB DB pod to a VLAN or physical network shared with the data plane nodes. If this connectivity breaks, ovn-controller on the data plane nodes loses its ability to receive flow updates, which can lead to stale flows and eventual connectivity failures.
====


=== OVN Database Clustering in RHOSO

For high availability, the OVN NB and SB databases can run as clustered instances using the Raft consensus protocol. In RHOSO, this is configured through the OpenStack operator:

[source,bash]
----
# Check OVN DB cluster status
oc get pods -n openstack | grep ovn
----

----
ovsdbserver-nb-0                          1/1     Running   0   3d
ovsdbserver-nb-1                          1/1     Running   0   3d
ovsdbserver-nb-2                          1/1     Running   0   3d
ovsdbserver-sb-0                          1/1     Running   0   3d
ovsdbserver-sb-1                          1/1     Running   0   3d
ovsdbserver-sb-2                          1/1     Running   0   3d
ovn-northd-6b8d7f9c4d-abc12              1/1     Running   0   3d
----

[WARNING]
====
In a Raft cluster, if a majority of nodes become unavailable (e.g., 2 out of 3 pods go down), the cluster loses quorum and becomes read-only. No new writes can be committed until quorum is restored. This means that no new logical network configurations can be applied, and ovn-controller instances cannot register or update their chassis information. Existing flows on data plane nodes continue to work, but no changes can be made.
====

== Key Differences from RHOSP

Understanding the differences between RHOSP and RHOSO is critical for engineers who are transitioning between the two platforms or supporting both.

=== Control Plane Location and Access


[cols="1,1,1",options="header"]
|===
|Aspect
|RHOSP 17.x
|RHOSO 18.0

|OVN NB/SB databases
|Run on controller nodes as systemd services
|Run as pods on OpenShift

|ovn-northd
|Runs on controller nodes as systemd service
|Runs as pod on OpenShift

|Access to OVN databases
|SSH to controller, run `ovn-nbctl` directly
|`oc exec` into pod, then run `ovn-nbctl`

|Configuration files
|`/etc/neutron/`, `/etc/openvswitch/` on controllers
|ConfigMaps and Secrets in OpenShift

|Logs for control plane
|`journalctl` or `/var/log/` on controllers
|`oc logs` for pod logs

|HA mechanism
|Pacemaker manages OVN DB failover
|Kubernetes manages pod scheduling and restart

|===


=== Accessing OVN Databases: RHOSP vs RHOSO

*In RHOSP:*

[source,bash]
----
# SSH to a controller node
ssh tripleo-admin@controller-0

# Run OVN commands directly
sudo ovn-nbctl show
sudo ovn-sbctl show
sudo ovn-sbctl list Chassis
----

*In RHOSO:*

[source,bash]
----
# Find the OVN NB DB pod
oc get pods -n openstack | grep ovsdbserver-nb

# Exec into the pod to run ovn-nbctl
oc exec -n openstack ovsdbserver-nb-0 -c ovsdbserver-nb -- ovn-nbctl show

# Or for the SB DB
oc exec -n openstack ovsdbserver-sb-0 -c ovsdbserver-sb -- ovn-sbctl show
----


[NOTE]
====
In RHOSO, you do not need to SSH into any node to access the OVN control plane. All control plane operations are done through `oc exec` into the appropriate pod. However, for data plane operations (checking OVS on compute nodes), you still SSH into the data plane nodes.
====

[NOTE]
.Key Concept
====
In RHOSO, the logging split mirrors the architectural split. Control plane component logs are accessed through OpenShift (`oc logs`), while data plane component logs are accessed through traditional Linux tools (`journalctl`) on the data plane nodes. This means a complete troubleshooting session often involves both `oc` commands and SSH sessions.
====


=== Upgrade Model


[cols="1,1,1",options="header"]
|===
|Aspect
|RHOSP
|RHOSO

|Control plane upgrade
|Major undertaking: stack update via Director, often requires maintenance window
|Operator-driven: update the OpenStack operator, it rolls out new pod versions

|Data plane upgrade
|Part of stack update, nodes rebooted in sequence
|Separate step: create OpenStackDataPlaneDeployment CR to trigger edpm-ansible on nodes

|Rollback
|Complex, often requires re-deployment
|Operator can revert pod versions; data plane rollback still complex

|Downtime
|Often significant for control plane
|Minimal for control plane (rolling pod updates)

|===

=== Scenario 3: VM to External Network

`vm-a` (192.168.1.10) sends traffic to an external host (8.8.8.8) via a floating IP (10.0.0.50). A logical router handles the NAT.

----
edpm-compute-0                    edpm-compute-2 (gateway)
+-----------------+               +-----------------------+
| VM-A            |               | OVN Gateway Chassis   |
| 192.168.1.10    |               |                       |
| FIP: 10.0.0.50  |               | Logical Router        |
|       |         |               | (DNAT/SNAT)           |

|       |         |               |       |               |
| geneve tunnel   |               |   br-ex               |

        |                         |  enp8s0 (external)    |

                                          |
                                     External Network
                                      10.0.0.0/24

[source,bash]

snat             lrp-a1b2c3d4-5678...  10.0.0.1                                  192.168.1.0/24

*Step 2: Identify the gateway chassis for the logical router.*

[source,bash]
----
oc exec -n openstack ovsdbserver-nb-0 -c ovsdbserver-nb -- ovn-nbctl lrp-get-gateway-chassis \
  lrp-a1b2c3d4-5678-90ab-cdef-1234567890ef

----

lrp-a1b2c3d4-5678-90ab-cdef-1234567890ef_e1f2a3b4-5678-90ab-cdef-111111111111    1

*Step 3: Trace the full path with ovn-trace.*

[source,bash]

----

The trace will show:

. The packet enters the logical switch pipeline (ingress ACL, port security)
. The packet is forwarded to the logical router port

== Troubleshooting RHOSO-Specific Issues

This section covers common problems specific to the RHOSO architecture and how to diagnose them.

=== Issue 1: ovn-controller Cannot Connect to SB DB

*Symptoms:*

* VMs cannot get network connectivity
* New VMs fail to get DHCP addresses
* `ovn-appctl -t ovn-controller connection-status` returns `not connected`

*Diagnosis:*

[source,bash]
----
# Step 1: On the data plane node, check connection status
sudo ovn-appctl -t ovn-controller connection-status
----

----
not connected
----

[source,bash]
----
# Step 2: Check where ovn-controller is trying to connect
sudo ovs-vsctl get Open_vSwitch . external_ids:ovn-remote
----

----
"tcp:172.17.0.30:6642,tcp:172.17.0.31:6642,tcp:172.17.0.32:6642"
----

[source,bash]
----
# Step 3: Test connectivity to the SB DB IPs
ping -c 3 172.17.0.30
----

----

3 packets transmitted, 0 received, 100% packet loss, time 2003ms
----

[source,bash]

*Common Causes:*

. VLAN or network misconfiguration on the data plane node (wrong VLAN tag, wrong interface)
. NAD misconfiguration on the OpenShift side (wrong master interface, wrong VLAN)
. Firewall rules blocking port 6642 between data plane nodes and OpenShift nodes
. SB DB pods were rescheduled and got new IPs (check if ovn-remote needs updating)


[WARNING]
====
If the SB DB pods are rescheduled to different OpenShift nodes, their NAD-assigned IPs may change (depending on IPAM configuration). If ovn-controller on data plane nodes has stale IP addresses in `ovn-remote`, it will fail to connect. In production, use stable IPs via the `whereabouts` IPAM plugin with fixed ranges, or use DNS names.
====


*Resolution:*

[source,bash]
----
# If IPs changed, update ovn-remote on the data plane node
sudo ovs-vsctl set Open_vSwitch . \
  external_ids:ovn-remote="tcp:172.17.0.30:6642,tcp:172.17.0.31:6642,tcp:172.17.0.32:6642"

# Restart ovn-controller to reconnect
sudo systemctl restart ovn-controller

# Verify connection
sudo ovn-appctl -t ovn-controller connection-status
----

----
connected
----

What to look for:

* *Role:* Should be `leader` for one pod and `follower` for the others
* *Status:* Should be `cluster member` for all pods
* *Entries not yet committed:* Should be 0 or very small; large numbers indicate replication issues
* *Connections:* All peer addresses should show recent `last msg` times


[WARNING]
====
If a Raft cluster loses quorum (e.g., 2 of 3 pods down), the surviving pod will show `Status: cluster member` but `Role: candidate` because it cannot elect a leader alone. The database becomes read-only. Existing network configurations continue to work, but no new changes can be applied.
====


=== Issue 5: Pod Restart Scenarios and Impact on OVN

Understanding what happens when OVN pods restart is critical for operations:


[cols="1,1,1",options="header"]
|===
|Pod Restarted
|Impact
|Recovery

|ovsdbserver-nb (one of three)
|Minimal - remaining pods maintain quorum
|Automatic - pod rejoins Raft cluster

|ovsdbserver-nb (two of three)
|Critical - loss of quorum, NB DB read-only
|Manual intervention may be needed

|ovsdbserver-sb (one of three)
|Minimal - ovn-controllers reconnect to remaining pods
|Automatic - ovn-controllers have all SB endpoints configured

|ovsdbserver-sb (two of three)
|Critical - ovn-controllers cannot update chassis or receive flows
|Urgent - restore quorum

|ovn-northd
|Temporary - no NB to SB translation
|Automatic - Kubernetes restarts the pod

|Neutron pods
|Temporary - API unavailable, no new network changes
|Automatic - existing networks unaffected

|===

== Summary

This module covered the architecture and operation of OVS and OVN in Red Hat OpenStack Services on OpenShift (RHOSO). Key takeaways:

* *RHOSO splits the deployment* into an OpenShift-hosted control plane (OVN databases, ovn-northd, Neutron) and bare-metal data plane nodes (ovn-controller, OVS, nova-compute).

* *NetworkAttachmentDefinitions* bridge the gap between the OpenShift pod network and the physical networks required by OpenStack services.

* *OVN is the sole networking backend* in RHOSO. The NB/SB databases run as Raft-clustered StatefulSet pods, providing high availability.

* *Troubleshooting requires working across both domains:* `oc exec` and `oc logs` for control plane components, SSH and `journalctl` for data plane components.

* *The connectivity between data plane nodes and the SB DB pods* is the most critical network path. If it breaks, ovn-controller cannot receive flow updates.

In the next module, we will explore how OVN is used in a completely different context: as the CNI (Container Network Interface) for OpenShift itself, powering pod-to-pod networking in OVN-Kubernetes.
