= Module 01 - Networking Fundamentals


== Introduction

Before diving into OVS and OVN, you need a solid foundation in the networking concepts they build upon. This module is a refresher - not a full networking course, but a focused review of the specific topics that come up repeatedly when working with virtual networking in Red Hat environments.

If you already have strong networking fundamentals, you can skim this module and use it as a reference. If some of these topics are fuzzy, take the time to work through them carefully - everything in subsequent modules assumes you understand this material.

We will focus on:

* *Layer 2 and Layer 3* - because OVS operates at L2-L4 and OVN builds logical L2 and L3 networks
* *VLANs and overlays* - because these are the mechanisms used to isolate tenant traffic
* *SDN concepts* - because OVS is fundamentally an SDN switch controlled via OpenFlow
* *Linux networking primitives* - because OVS, OVN, and the platforms that use them all build on these

== The OSI Model - A Quick Recap

The OSI (Open Systems Interconnection) model divides network communication into seven layers. You do not need to memorize all seven for this workshop, but you do need to know which layers are relevant to virtual switching.


[cols="1,1,1,1",options="header"]
|===
|Layer
|Name
|What It Does
|Relevant to OVS/OVN?

|7
|Application
|End-user protocols (HTTP, SSH, DNS)
|Rarely - OVS/OVN generally do not inspect application data

|6
|Presentation
|Data encoding and encryption
|No

|5

|No

|4

|===


=== The Layers That Matter Most

For this workshop, you need to be comfortable with three layers:

*Layer 2 (Data Link)* - This is where Ethernet switching happens. Devices are identified by MAC addresses, and switches forward frames based on MAC learning. OVS is fundamentally a Layer 2 switch, though it can also inspect higher layers.

*Layer 3 (Network)* - This is where IP routing happens. Devices are identified by IP addresses, and routers forward packets based on routing tables. OVN provides virtual L3 routing on top of OVS.

*Layer 4 (Transport)* - This is where TCP and UDP live. OVS can match on transport-layer ports (e.g., "if the destination port is 80, do X"), and OVN uses L4 information for load balancing and ACL matching.


[NOTE]
.Key Concept
====
When you hear "L2 connectivity issue" in a support case, it means the problem is at the Ethernet/MAC layer - frames are not being delivered between devices on the same network segment. An "L3 connectivity issue" means the problem is at the IP routing layer - packets cannot be routed between different network segments. Knowing which layer the problem lives at immediately tells you where to look.
====

== Ethernet Switching Fundamentals

=== MAC Addresses

Every network interface has a *MAC address* (Media Access Control) - a 48-bit identifier that is supposed to be globally unique. MAC addresses are written as six pairs of hexadecimal digits:

----
fa:16:3e:aa:bb:cc
----

In virtual environments, MAC addresses are generated by the hypervisor or orchestration platform:

* OpenStack Neutron generates MACs with the `fa:16:3e` prefix by default
* OVN can generate MACs for logical ports
* Kubernetes/OVN-Kubernetes assigns MACs to pod interfaces


[NOTE]
====
Unlike IP addresses, which are assigned by administrators and can change, MAC addresses are typically fixed for the lifetime of a virtual interface. However, in virtual environments, MACs are software-generated and can be duplicated if the generation mechanism is flawed - this is a real (though rare) source of networking issues.
====


=== How a Switch Learns

A traditional Ethernet switch (and OVS when operating in "normal" switching mode) learns where devices are by watching incoming traffic:

. A frame arrives on port 1 with source MAC `aa:bb:cc:dd:ee:01`.
. The switch records: "MAC `aa:bb:cc:dd:ee:01` is reachable via port 1."
. The switch looks at the destination MAC of the frame.
. If the switch has seen the destination MAC before, it forwards the frame out the port where it learned that MAC.
. If the switch has *not* seen the destination MAC before, it *floods* the frame out all ports except the one it arrived on.
. When the destination device responds, the switch learns its MAC-to-port mapping too.

This process is called *MAC learning*, and the table that stores the mappings is called the *forwarding database* (FDB) or *MAC address table*.

----
Frame arrives:  src=aa:bb:cc:dd:ee:01  dst=aa:bb:cc:dd:ee:02  port=1

Switch FDB before:
  (empty)

Switch action:
  1. Learn: aa:bb:cc:dd:ee:01 -> port 1
  2. Lookup dst aa:bb:cc:dd:ee:02 -> not found
  3. Flood frame to all ports except port 1

Frame arrives:  src=aa:bb:cc:dd:ee:02  dst=aa:bb:cc:dd:ee:01  port=3

Switch FDB after:
  aa:bb:cc:dd:ee:01 -> port 1
  aa:bb:cc:dd:ee:02 -> port 3

Switch action:
  1. Learn: aa:bb:cc:dd:ee:02 -> port 3
  2. Lookup dst aa:bb:cc:dd:ee:01 -> port 1
  3. Forward frame to port 1 only (unicast)
----


[NOTE]
.Key Concept
====
MAC learning is fundamental to how OVS handles "normal" switching. However, when OVS is programmed with explicit OpenFlow rules (as OVN does), it typically does not rely on MAC learning - instead, the flows explicitly specify which port to send traffic to based on match criteria. This is a key difference between traditional switching and SDN-based switching.
====


=== Broadcast Domains

A *broadcast domain* is the set of devices that will receive a broadcast frame (a frame with destination MAC `ff:ff:ff:ff:ff:ff`). On a traditional switch, all ports on the same VLAN are in the same broadcast domain.

Why this matters:

* ARP requests are broadcasts - every device in the broadcast domain sees them
* DHCP discovery is a broadcast
* Large broadcast domains create noise and can cause performance issues
* VLANs exist primarily to subdivide broadcast domains

In OVN, each *logical switch* is its own broadcast domain. OVN also optimizes broadcast traffic by handling ARP and DHCP directly in the pipeline without flooding.

=== The Forwarding Database (FDB)

The FDB is the data structure a switch uses to map MAC addresses to ports. You can inspect it on a Linux system:

[source,bash]
----
# View the FDB of a Linux bridge
bridge fdb show

# View the MAC table of an OVS bridge
ovs-appctl fdb/show br-int
----

Example output from OVS:

----
 port  VLAN  MAC                Age
    3     0  fa:16:3e:aa:bb:cc    1
    5     0  fa:16:3e:dd:ee:ff   10
----

This tells you that the switch has learned MAC `fa:16:3e:aa:bb:cc` on port 3 and MAC `fa:16:3e:dd:ee:ff` on port 5.


[NOTE]
====
In OVN-managed environments, the FDB is less important for troubleshooting because traffic forwarding is determined by explicit OpenFlow rules rather than MAC learning. However, for standalone OVS or the "normal" action in OVS flows, the FDB remains relevant.
====

== IP Routing Fundamentals

=== IP Addresses and CIDR

An IPv4 address is a 32-bit number, written as four octets in dotted-decimal notation:

----
192.168.1.100
----

*CIDR* (Classless Inter-Domain Routing) notation combines an IP address with a prefix length that indicates how many bits identify the network:

----
192.168.1.0/24

Network bits: 192.168.1   (first 24 bits)
Host bits:    .0           (last 8 bits)
Usable hosts: 192.168.1.1 through 192.168.1.254
Broadcast:    192.168.1.255
----

Common prefix lengths:


[cols="1,1,1,1",options="header"]
|===
|CIDR
|Subnet Mask
|Hosts
|Typical Use

|/8
|255.0.0.0
|~16 million
|Large enterprise, cloud provider

|/16
|255.255.0.0
|~65,000
|Large internal networks

|/24
|255.255.255.0
|254
|Standard subnet, most common

|/30
|255.255.255.252
|2
|Point-to-point links

|/32
|255.255.255.255
|1
|Host route (single address)

|===


[NOTE]
.Key Concept
====
In cloud environments, you will frequently encounter /24 subnets for tenant networks and /32 routes for specific host or floating IP routes. Understanding CIDR is essential for interpreting routing tables and OVN logical router configurations.
====


=== Routing Tables

A routing table tells a device (host, router, or virtual router) where to send packets based on the destination IP address:

[source,bash]
----
# View the routing table on a Linux host
ip route show
----

----
default via 192.168.1.1 dev eth0
192.168.1.0/24 dev eth0 proto kernel scope link src 192.168.1.100
10.0.0.0/16 via 192.168.1.254 dev eth0
172.16.0.0/12 via 192.168.1.253 dev eth0
----

How to read this:

* *default via 192.168.1.1* - if no other route matches, send the packet to 192.168.1.1 (the default gateway)
* *192.168.1.0/24 dev eth0* - for destinations in 192.168.1.0/24, send directly out eth0 (local subnet, no gateway needed)
* *10.0.0.0/16 via 192.168.1.254* - for destinations in 10.0.0.0/16, send to gateway 192.168.1.254
* *172.16.0.0/12 via 192.168.1.253* - for destinations in 172.16.0.0/12, send to gateway 192.168.1.253

=== Longest Prefix Match

When a packet arrives and the device needs to decide where to send it, it uses *longest prefix match* - it finds the route with the longest (most specific) prefix that matches the destination IP.

Example: Where does a packet to `10.0.5.20` go?

----
Routes:
  default via 192.168.1.1           -> prefix length /0  (matches everything)
  10.0.0.0/8 via 192.168.1.254      -> prefix length /8  (matches)
  10.0.5.0/24 via 192.168.1.253     -> prefix length /24 (matches)
  10.0.5.16/28 via 192.168.1.252    -> prefix length /28 (matches - LONGEST)

Winner: 10.0.5.16/28 via 192.168.1.252
----

The `/28` route wins because it is the most specific match. This is how all IP routing works, including OVN logical routers.


[NOTE]
.Key Concept
====
Longest prefix match is how OVN logical routers decide where to forward traffic. When you configure static routes on an OVN router, the most specific route always wins. This is also how Kubernetes service routing works - a `/32` route to a specific pod IP is more specific than a `/24` route to a subnet.
====

== VLANs

=== What VLANs Are and Why They Matter

A *VLAN* (Virtual Local Area Network) is a way to divide a single physical switch into multiple logical switches. Devices on the same VLAN can communicate at Layer 2 as if they were on the same physical switch, even if they are physically connected to different ports. Devices on different VLANs cannot communicate without a router.

Think of VLANs as invisible walls inside a switch. All the ports are physically part of the same switch, but the VLAN configuration creates separate broadcast domains:

----
Physical Switch:
+--------------------------------------------------+
|                                                  |
|  VLAN 10 (Sales)        VLAN 20 (Engineering)   |
|  +-----------+          +-----------+            |
|  | Port 1    |          | Port 5    |            |
|  | Port 2    |          | Port 6    |            |
|  | Port 3    |          | Port 7    |            |
|  +-----------+          +-----------+            |
|                                                  |
|  Traffic between VLANs requires a router         |
+--------------------------------------------------+
----

Why VLANs matter for OVS/OVN:

* OVS uses VLANs internally as a tagging mechanism to identify which logical network a packet belongs to (even in overlay networks)
* RHOSP provider networks often map to physical VLANs
* OVN can work with VLAN-backed networks in addition to overlay networks

=== 802.1Q Tagging

*IEEE 802.1Q* is the standard that defines how VLAN information is embedded in Ethernet frames. A 4-byte tag is inserted into the Ethernet header between the source MAC address and the EtherType field:

----
Standard Ethernet Frame:
+--------+--------+-----------+----------+-----+
| Dst MAC| Src MAC| EtherType | Payload  | FCS |
| 6 bytes| 6 bytes|  2 bytes  | 46-1500  |  4  |
+--------+--------+-----------+----------+-----+

802.1Q Tagged Frame:
+--------+--------+------+------+-----------+----------+-----+
| Dst MAC| Src MAC| TPID | TCI  | EtherType | Payload  | FCS |
| 6 bytes| 6 bytes|0x8100| 2 B  |  2 bytes  | 46-1500  |  4  |
+--------+--------+------+------+-----------+----------+-----+

TCI (Tag Control Information):
  - PCP: 3 bits (priority)
  - DEI: 1 bit (drop eligible)
  - VID: 12 bits (VLAN ID, 0-4095)
----

The *VLAN ID (VID)* field is 12 bits, giving a range of 0-4095. VLAN 0 and 4095 are reserved, leaving 4094 usable VLANs.

=== Access Ports vs Trunk Ports

*Access port:* Carries traffic for a single VLAN. Frames on an access port are untagged - the switch adds/removes the VLAN tag when traffic enters/leaves the port. End devices (VMs, servers) are typically connected to access ports.

*Trunk port:* Carries traffic for multiple VLANs simultaneously. Frames on a trunk port are tagged with their VLAN ID so the receiving switch knows which VLAN each frame belongs to. Switch-to-switch links are typically trunks.

[source,bash]
----
# OVS: Create an access port on VLAN 100
ovs-vsctl add-port br0 eth1 tag=100

# OVS: Create a trunk port allowing VLANs 100, 200, and 300
ovs-vsctl add-port br0 eth2 trunks=100,200,300

# OVS: Create a trunk port allowing all VLANs (default behavior for trunk)
ovs-vsctl add-port br0 eth3
----


[NOTE]
====
In OVS, a port without a `tag` or `trunks` setting behaves as a trunk port carrying all VLANs by default. This is different from many physical switches where ports default to access mode on VLAN 1.
====


=== VLAN Scalability Limits

The 12-bit VLAN ID field limits you to *4094 usable VLANs*. In a cloud environment with hundreds or thousands of tenants, each potentially needing multiple isolated networks, 4094 VLANs is not enough.

This is the primary reason *overlay networks* were invented - they provide a much larger address space for network segmentation.


[cols="1,1,1",options="header"]
|===
|Segmentation Method
|ID Size
|Max Segments

|VLAN (802.1Q)
|12 bits
|4,094

|VXLAN (VNI)
|24 bits
|~16.7 million

|Geneve (VNI)
|24 bits
|~16.7 million

|===


[NOTE]
.Key Concept
====
VLANs work well for small-scale network segmentation, but they cannot scale to cloud-level multi-tenancy. This scalability limitation is one of the primary reasons overlays like VXLAN and Geneve were developed, and why OVN uses Geneve tunnels by default rather than VLANs for tenant isolation.
====

== Network Overlays

=== Why Overlays Exist

An *overlay network* is a virtual network built on top of an existing physical network (the *underlay*). Overlay packets are encapsulated inside underlay packets, creating a "tunnel" between endpoints.

Three key problems that overlays solve:

. *Scalability* - As discussed above, VLANs are limited to 4094 segments. Overlays provide millions of segments using a 24-bit identifier.

. *Multi-tenancy* - Each tenant in a cloud environment needs isolated networks. Overlays allow complete isolation without requiring the physical network to know anything about the tenant networks.

. *Decoupling physical from logical* - Overlays allow virtual machines or containers to move between physical hosts while keeping their network identity (IP address, subnet membership) intact. The physical network only needs to provide IP connectivity between hypervisors - it does not need to be reconfigured when workloads move.

----
Without overlays (physical network must support every tenant network):

  Physical Switch
  +-------------------------------------------------+
  |  VLAN 10  |  VLAN 11  |  VLAN 12  |  ... 4094  |
  +-------------------------------------------------+
  Limit: 4094 networks, physical switches must be configured

With overlays (physical network just provides IP connectivity):

  Overlay (Geneve/VXLAN tunnels)
  +-----------------------------------------------------+
  |  VNI 1  |  VNI 2  |  VNI 3  |  ...  |  VNI 16M+   |
  +-----------------------------------------------------+
           |              |              |
  +-----------------------------------------------------+
  |           Physical IP Network (underlay)             |
  |     Just needs IP reachability between hosts         |
  +-----------------------------------------------------+
----


[NOTE]
.Key Concept
====
Overlays are the fundamental mechanism that makes cloud-scale networking possible. Every OVN deployment uses overlay tunnels (typically Geneve) to connect logical networks across physical hosts. Understanding how overlays work is essential for troubleshooting connectivity issues - when traffic between two VMs on different hosts fails, the overlay tunnel is one of the first things to check.
====


=== VXLAN

*VXLAN* (Virtual Extensible LAN) was the first widely adopted overlay protocol for data center use. Defined in RFC 7348, it encapsulates Layer 2 Ethernet frames inside UDP packets.

*How VXLAN works:*

. A VM on Host A sends a frame to a VM on Host B.
. The VXLAN Tunnel Endpoint (VTEP) on Host A - which is typically OVS - encapsulates the original frame inside a new UDP packet.
. The outer packet has Host A's IP as source, Host B's IP as destination, and UDP destination port 4789.
. The physical network routes the outer packet to Host B using standard IP routing.
. The VTEP on Host B decapsulates the packet, extracting the original frame, and delivers it to the destination VM.

*VXLAN header format:*

----
+-----------------------------------------------+
| Outer Ethernet Header                         |
|  Dst MAC | Src MAC | EtherType (0x0800 = IP)  |
+-----------------------------------------------+
| Outer IP Header                               |
|  Src IP: Host A    | Dst IP: Host B           |
|  Protocol: UDP (17)                            |
+-----------------------------------------------+
| Outer UDP Header                              |
|  Src Port: hash-based | Dst Port: 4789        |
+-----------------------------------------------+
| VXLAN Header (8 bytes)                        |
|  Flags | Reserved | VNI (24 bits) | Reserved  |
+-----------------------------------------------+
| Original (Inner) Ethernet Frame               |
|  Dst MAC | Src MAC | EtherType | Payload | FCS|
+-----------------------------------------------+
----

*Key VXLAN concepts:*

* *VNI (VXLAN Network Identifier):* A 24-bit identifier that labels which virtual network the encapsulated frame belongs to. This is the overlay equivalent of a VLAN ID, but with ~16.7 million possible values instead of 4094.
* *VTEP (VXLAN Tunnel Endpoint):* The device that performs encapsulation and decapsulation. In our context, OVS acts as the VTEP.
* *UDP port 4789:* The standard VXLAN port. The outer source port is typically a hash of the inner frame's headers, providing ECMP load distribution across multiple physical paths.

*Detailed packet walk:*

----
VM-A (10.0.0.10) on Host-A wants to reach VM-B (10.0.0.20) on Host-B.
Both VMs are on VNI 100.

Step 1: VM-A sends frame
  Src MAC: fa:16:3e:aa:aa:aa    Dst MAC: fa:16:3e:bb:bb:bb
  Src IP:  10.0.0.10            Dst IP:  10.0.0.20

Step 2: OVS on Host-A (VTEP) encapsulates
  Outer Src IP: 172.16.0.1 (Host-A tunnel IP)
  Outer Dst IP: 172.16.0.2 (Host-B tunnel IP)
  Outer UDP:    src=<hash> dst=4789
  VXLAN VNI:    100
  Inner frame:  (original frame from VM-A)

Step 3: Physical network routes outer packet
  172.16.0.1 -> 172.16.0.2 (standard IP routing)

Step 4: OVS on Host-B (VTEP) decapsulates
  Strips outer headers
  Identifies VNI 100 -> delivers to correct virtual network
  Delivers inner frame to VM-B
----


[NOTE]
====
VXLAN was used in earlier OVS-based OpenStack deployments. While OVN can technically use VXLAN tunnels, it strongly prefers Geneve because VXLAN's fixed header does not carry enough metadata for OVN's logical pipeline. If you encounter a VXLAN-based deployment, it is likely a standalone OVS (ML2/OVS) setup.
====


=== Geneve

*Geneve* (Generic Network Virtualization Encapsulation) is the evolution of VXLAN. Defined in RFC 8926, it was designed to overcome the limitations of VXLAN and other overlay protocols by providing an extensible header format.

*Why Geneve over VXLAN?*

The key limitation of VXLAN is its *fixed header format*. The VXLAN header has room for the VNI and a few flags, but nothing else. If you need to carry additional metadata in the tunnel - and OVN does - VXLAN cannot accommodate it.

Geneve solves this with *Type-Length-Value (TLV) options* - variable-length metadata fields that can carry arbitrary information in the tunnel header.

*Geneve header format:*

----
+-----------------------------------------------+
| Outer Ethernet Header                         |
+-----------------------------------------------+
| Outer IP Header                               |
|  Src IP: Host A    | Dst IP: Host B           |
|  Protocol: UDP (17)                            |
+-----------------------------------------------+
| Outer UDP Header                              |
|  Src Port: hash-based | Dst Port: 6081        |
+-----------------------------------------------+
| Geneve Header                                 |
|  Version | Opt Len | Flags | Protocol Type    |
|  VNI (24 bits)     | Reserved                 |
|  +-- TLV Options (variable length) ----------+|
|  | Class | Type | Length | Value              ||
|  | Class | Type | Length | Value              ||
|  | (as many as needed)                        ||
|  +--------------------------------------------+|
+-----------------------------------------------+
| Original (Inner) Ethernet Frame               |
+-----------------------------------------------+
----

*What OVN puts in Geneve TLV options:*

OVN uses Geneve TLV options to carry logical metadata through the tunnel:


[cols="1,1",options="header"]
|===
|TLV Option
|Purpose

|Logical Datapath (VNI field)
|Identifies which logical switch or router the packet belongs to

|Logical Input Port
|The logical port where the packet entered the OVN pipeline

|Logical Output Port
|The logical port where the packet should exit

|Connection Tracking State
|Conntrack state for stateful ACL processing

|===


This metadata is critical: it allows the receiving hypervisor's ovn-controller to continue processing the packet through the correct logical pipeline without re-doing the entire classification from scratch.


[NOTE]
.Key Concept
====
OVN uses Geneve instead of VXLAN because Geneve's extensible TLV options allow OVN to carry logical pipeline metadata (input port, output port, datapath) inside the tunnel header. This metadata is essential for OVN's distributed processing model. When VXLAN is used with OVN (which is possible but not recommended), OVN loses the ability to carry this metadata efficiently, and some features may not work correctly.
====


=== GRE

*GRE* (Generic Routing Encapsulation) is an older tunneling protocol (RFC 2784) that predates both VXLAN and Geneve. It encapsulates packets inside IP packets (protocol 47) without using UDP.

----
+-----------------------------------------------+
| Outer IP Header (Protocol 47 = GRE)          |
+-----------------------------------------------+
| GRE Header                                   |
|  Flags | Protocol Type | Key (optional, 32b) |
+-----------------------------------------------+
| Original Packet                               |
+-----------------------------------------------+
----

GRE is mentioned here for completeness because:

* Some older OVS deployments use GRE tunnels
* It appears as a tunnel type option in `ovs-vsctl`
* You may encounter it in legacy configurations

However, GRE has significant disadvantages compared to VXLAN and Geneve:

* No UDP encapsulation means no ECMP load balancing based on UDP ports (unless GRE-over-UDP is used)
* The key field is 32 bits, which is sufficient for segmentation but not standardized in the same way as VNI
* No extensible metadata support
* OVN does not use GRE


[NOTE]
====
If you encounter GRE tunnels in a customer environment, it is almost certainly a legacy standalone OVS configuration. Modern deployments should use Geneve (OVN) or VXLAN (standalone OVS).
====

== Software-Defined Networking (SDN)

=== Control Plane vs Data Plane

In traditional networking, the *control plane* and *data plane* are tightly integrated within each network device:

* The *control plane* makes forwarding decisions - it runs routing protocols, builds forwarding tables, and decides where packets should go.
* The *data plane* (also called the forwarding plane) actually moves packets - it looks up the forwarding table and sends each packet out the correct port.

*SDN separates these two functions.* The control plane is moved to a centralized controller (or distributed control system), and the data plane remains on the switches. The controller programs the switches with forwarding rules, and the switches execute them.

----
Traditional Networking:
+-------------+    +-------------+    +-------------+
| Switch A    |    | Switch B    |    | Switch C    |
| Control  +-+|    | Control  +-+|    | Control  +-+|
| Plane    | ||    | Plane    | ||    | Plane    | ||
+----------+ +|    +----------+ +|    +----------+ +|
| Data     | ||    | Data     | ||    | Data     | ||
| Plane    | ||    | Plane    | ||    | Plane    | ||
+----------+-++    +----------+-++    +----------+-++
  Each switch makes its own decisions independently

SDN:
          +------------------+
          |  SDN Controller  |
          |  (Control Plane) |
          +--------+---------+
          OpenFlow |
     +-------------+-------------+
     |             |             |
+----+----+  +----+----+  +----+----+
| Switch A|  | Switch B|  | Switch C|
| (Data   |  | (Data   |  | (Data   |
|  Plane) |  |  Plane) |  |  Plane) |
+---------+  +---------+  +---------+
  Controller programs all switches centrally
----

*How this maps to OVS and OVN:*


[cols="1,1,1",options="header"]
|===
|SDN Role
|OVS Standalone
|OVN

|Data plane
|OVS (ovs-vswitchd + kernel datapath)
|OVS (ovs-vswitchd + kernel datapath)

|Control plane
|External controller or manual configuration
|OVN (ovn-northd + ovn-controller)

|Protocol
|OpenFlow (between controller and OVS)
|OpenFlow (between ovn-controller and OVS)

|Management
|OVSDB (for switch configuration)
|OVSDB (NB DB, SB DB, and local OVS DB)

|===


[NOTE]
.Key Concept
====
OVS is an SDN switch. It does not make forwarding decisions on its own (except when using the "normal" action, which falls back to traditional MAC learning). Instead, it relies on OpenFlow rules provided by a controller. In OVN deployments, ovn-controller is that controller - it runs on every hypervisor and programs the local OVS instance.
====


=== OpenFlow Protocol

*OpenFlow* is the protocol used to communicate between an SDN controller and an SDN switch. It allows the controller to:

* *Add flow rules* to the switch's flow tables
* *Modify or delete* existing flow rules
* *Query* the switch for its current state (statistics, capabilities, flow tables)
* *Receive notifications* when certain events occur (new device connected, flow expired)

OVS implements OpenFlow and exposes it through the `ovs-ofctl` command-line tool:

[source,bash]
----
# Connect to the OVS bridge and dump all flow rules
ovs-ofctl dump-flows br-int

# Add a flow rule: match packets with destination IP 10.0.0.1, output on port 5
ovs-ofctl add-flow br-int "ip,nw_dst=10.0.0.1,actions=output:5"

# Delete a specific flow rule
ovs-ofctl del-flows br-int "ip,nw_dst=10.0.0.1"
----

In OVN deployments, you should almost never manually add or modify OpenFlow rules in OVS - OVN manages all flows through ovn-controller. However, `ovs-ofctl dump-flows` is an essential troubleshooting tool for inspecting what OVN has programmed.

=== Flow Tables and Flow Matching

OpenFlow uses a *multi-table pipeline* to process packets. A packet entering the switch starts at table 0 and can be sent to higher-numbered tables for further processing.

Each flow rule in a table has three parts:

. *Match fields* - criteria the packet must meet (e.g., source MAC, destination IP, input port)
. *Priority* - when multiple rules match, the highest-priority rule wins
. *Actions* - what to do with the packet (e.g., output to a port, modify headers, send to another table)

----
Table 0 (Ingress Classification):
  priority=100, in_port=1, dl_vlan=100  -> resubmit(,10)
  priority=100, in_port=2, dl_vlan=200  -> resubmit(,10)
  priority=0                             -> drop

Table 10 (ACL Check):
  priority=100, ip, nw_src=10.0.0.0/24  -> resubmit(,20)
  priority=50,  ip                       -> drop
  priority=0                             -> drop

Table 20 (Forwarding):
  priority=100, dl_dst=fa:16:3e:aa:bb:cc -> output:3
  priority=100, dl_dst=fa:16:3e:dd:ee:ff -> output:5
  priority=0                              -> drop
----

*How a packet traverses this pipeline:*

----
Packet: in_port=1, VLAN 100, src IP 10.0.0.5, dst MAC fa:16:3e:aa:bb:cc

Table 0: Match "in_port=1, dl_vlan=100" (priority 100) -> resubmit to table 10
Table 10: Match "ip, nw_src=10.0.0.0/24" (priority 100) -> resubmit to table 20
Table 20: Match "dl_dst=fa:16:3e:aa:bb:cc" (priority 100) -> output to port 3

Result: Packet is sent out port 3
----


[NOTE]
.Key Concept
====
OVN generates a complex multi-table pipeline in OVS, often using tables 0 through 65+ with dozens or hundreds of rules. Understanding the concept of multi-table processing is essential for interpreting `ovs-ofctl dump-flows` output when troubleshooting. You do not need to memorize every table OVN uses, but you need to understand that a packet flows through multiple tables and can be dropped at any stage.
====


=== SDN Controllers

An *SDN controller* is the software that programs the data plane switches. Different controllers exist for different purposes:


[cols="1,1,1",options="header"]
|===
|Controller
|Purpose
|Used With

|ovn-controller
|Programs OVS based on OVN logical flows
|OVN (RHOSP, RHOSO, OCP)

|Neutron OVS agent
|Programs OVS based on Neutron network model
|ML2/OVS (legacy RHOSP)

|OpenDaylight
|General-purpose SDN controller
|Various (not common in Red Hat products)

|Manual (ovs-ofctl)
|Human-driven flow programming
|Lab/testing environments

|===


In OVN deployments, *ovn-controller* is the SDN controller. It runs on every node (hypervisor, compute node, Kubernetes node) and:
. Reads the OVN Southbound Database to get the logical flow rules relevant to its node
. Translates those logical flows into physical OpenFlow rules
. Programs those OpenFlow rules into the local OVS instance


[NOTE]
====
When you see "SDN" in the context of Red Hat products, it almost always means OVS + OVN. The older OpenShift SDN plugin (which was not based on OVN) was removed in OCP 4.17. OVN-Kubernetes is the sole CNI going forward.

== Linux Networking Building Blocks

OVS, OVN, and the platforms that use them all rely on standard Linux networking primitives. Understanding these building blocks will help you make sense of what you see when you inspect a compute node or Kubernetes worker.

=== Network Namespaces

A *network namespace* is an isolated copy of the network stack. Each namespace has its own interfaces, routing table, firewall rules, and ARP table. Processes in one namespace cannot see or interact with the network interfaces of another namespace (unless explicitly connected).

Network namespaces are the foundation of container and VM network isolation on Linux:

* *OpenStack* uses namespaces for DHCP agents, L3 routers, and metadata proxies (in ML2/OVS deployments)
* *Kubernetes/OVN-Kubernetes* uses namespaces for pod networking - each pod gets its own namespace
* *OVN standalone labs* use namespaces to simulate multiple hosts on a single machine

[source,bash]
----
# List all network namespaces
ip netns list

# Create a namespace
ip netns add ns-red

# Run a command inside a namespace
ip netns exec ns-red ip addr show

# View interfaces inside a namespace
ip netns exec ns-red ip link show

# Delete a namespace
ip netns del ns-red
----

*Practical example - creating two isolated namespaces:*

[source,bash]
----
# Create two namespaces
ip netns add ns-red
ip netns add ns-blue

# Each has its own loopback and nothing else
ip netns exec ns-red ip link show
# Output:
# 1: lo: <LOOPBACK> mtu 65536 qdisc noop state DOWN
#     link/loopback 00:00:00:00:00:00 brd 00:00:00:00:00:00

# They are completely isolated from each other and from the host
ip netns exec ns-red ping 127.0.0.1
# ping: connect: Network is unreachable   (loopback is down by default)

ip netns exec ns-red ip link set lo up
ip netns exec ns-red ping -c 1 127.0.0.1
# PING 127.0.0.1 (127.0.0.1) 56(84) bytes of data.
# 64 bytes from 127.0.0.1: icmp_seq=1 ttl=64 time=0.019 ms
----


[NOTE]
.Key Concept
====
Network namespaces are the building block for all network isolation in Linux. When you SSH into a compute node and run `ip addr`, you only see the host's namespace. To see the interfaces inside a VM's or pod's network namespace, you need to use `ip netns exec`. This is a common source of confusion - "I cannot see the interface" often means "I am looking in the wrong namespace."
====


=== veth Pairs

A *veth pair* (virtual Ethernet pair) is a pair of virtual network interfaces connected to each other. Whatever goes in one end comes out the other. They are like a virtual Ethernet cable.

veth pairs are used to connect network namespaces to each other or to a bridge:

[source,bash]
----
# Create a veth pair
ip link add veth-red type veth peer name veth-red-br

# Move one end into a namespace
ip link set veth-red netns ns-red

# The other end stays in the host namespace (or gets added to a bridge)
# Now ns-red can communicate with the host (or through the bridge)
----

*Practical example - connecting two namespaces via a bridge:*

[source,bash]
----
# Create namespaces
ip netns add ns-red
ip netns add ns-blue

# Create veth pairs
ip link add veth-red type veth peer name veth-red-br
ip link add veth-blue type veth peer name veth-blue-br

# Move namespace ends into their namespaces
ip link set veth-red netns ns-red
ip link set veth-blue netns ns-blue

# Create a bridge and attach the host ends
ip link add br0 type bridge
ip link set veth-red-br master br0
ip link set veth-blue-br master br0

# Bring everything up
ip link set br0 up
ip link set veth-red-br up
ip link set veth-blue-br up
ip netns exec ns-red ip link set veth-red up
ip netns exec ns-blue ip link set veth-blue up

# Assign IPs inside the namespaces
ip netns exec ns-red ip addr add 10.0.0.1/24 dev veth-red
ip netns exec ns-blue ip addr add 10.0.0.2/24 dev veth-blue

# Test connectivity
ip netns exec ns-red ping -c 2 10.0.0.2
# PING 10.0.0.2 (10.0.0.2) 56(84) bytes of data.
# 64 bytes from 10.0.0.2: icmp_seq=1 ttl=64 time=0.038 ms
# 64 bytes from 10.0.0.2: icmp_seq=2 ttl=64 time=0.031 ms
----


[NOTE]
====
In OVN-Kubernetes, each pod's network namespace is connected to the OVS bridge (br-int) via a veth pair. One end is inside the pod, the other is an OVS port on br-int. When you see a port like `aaaa1234_h` on br-int, the other end of that veth pair is inside a pod's namespace.
====


=== Linux Bridges vs OVS Bridges

Linux has two types of virtual bridges: the native *Linux bridge* and *Open vSwitch (OVS)*. Both connect virtual interfaces at Layer 2, but they have very different capabilities.


[cols="1,1,1",options="header"]
|===
|Feature
|Linux Bridge
|OVS Bridge

|Configuration tool
|`ip link`, `bridge`
|`ovs-vsctl`

|Flow programming
|Not supported
|OpenFlow (full SDN capability)

|Tunnel support
|Limited (no built-in overlay)
|VXLAN, Geneve, GRE, STT

|QoS
|Basic (tc)
|Integrated QoS with queues

|Monitoring
|Basic statistics
|sFlow, NetFlow, IPFIX

|Multi-table pipeline
|No
|Yes (OpenFlow tables)

|Connection tracking
|Via iptables/nftables
|Native conntrack integration

|DPDK support
|No
|Yes (userspace datapath)

|LACP
|No
|Yes

|Spanning tree
|STP only
|STP, RSTP

|Performance overhead
|Very low
|Slightly higher (but kernel datapath helps)

|Programmability
|Low
|Very high

|Typical use
|Simple VM bridging, libvirt default
|Cloud platforms, SDN, OVN

|===


[source,bash]
----
# Linux bridge commands
ip link add br0 type bridge               # Create bridge
ip link set eth0 master br0                # Add port
bridge link show                           # Show ports
bridge fdb show                            # Show FDB

# OVS bridge commands
ovs-vsctl add-br br-int                    # Create bridge
ovs-vsctl add-port br-int eth0             # Add port
ovs-vsctl show                             # Show configuration
ovs-ofctl dump-flows br-int                # Show flow rules
----


[NOTE]
.Key Concept
====
OVS exists because the Linux bridge cannot be programmed with SDN flow rules. Cloud platforms need a switch that can be told exactly how to handle each packet based on complex match criteria - something only OVS (via OpenFlow) can provide. The Linux bridge is fine for simple scenarios (like connecting a VM to the host network), but it cannot implement the sophisticated forwarding pipelines that OVN requires.
====


=== iptables and nftables

*iptables* (and its successor *nftables*) are the Linux kernel's packet filtering frameworks. They are relevant to OVS/OVN for a few reasons:

* In *ML2/OVS* deployments, security groups were historically implemented using iptables rules on the bridge ports (iptables-based security groups). Later versions moved to OVS conntrack-based security groups.
* In *OVN* deployments, security groups are implemented as OVN ACLs, which translate to OVS conntrack flows - iptables is *not* involved.
* *Kubernetes* uses iptables or nftables for service routing (kube-proxy) and NetworkPolicy enforcement in some CNI plugins, but OVN-Kubernetes handles both through OVN/OVS.

[source,bash]
----
# View iptables rules (legacy)
iptables -L -n -v

# View nftables rules (modern)
nft list ruleset

# In OVN-Kubernetes environments, check if kube-proxy is running
# (it should NOT be - OVN handles service routing)
ps aux | grep kube-proxy
----


[WARNING]
====
A common troubleshooting mistake is looking at iptables rules when the environment uses OVN. In OVN-based deployments (RHOSP ML2/OVN, RHOSO, OCP with OVN-Kubernetes), security filtering is done inside OVS via conntrack flows, NOT via iptables. If you are checking iptables and finding nothing, you are looking in the wrong place - check OVS flows and OVN ACLs instead.
====


=== TAP and TUN Devices

*TAP* and *TUN* are virtual network interfaces that allow userspace programs to interact with the network stack:

* *TAP devices* operate at Layer 2 (Ethernet frames). A program can read and write raw Ethernet frames from/to a TAP device.
* *TUN devices* operate at Layer 3 (IP packets). A program can read and write raw IP packets from/to a TUN device.

In the context of OVS/OVN:

* *QEMU/KVM* uses TAP devices to connect virtual machines to OVS. When a VM is created, a TAP device (e.g., `tap1234abcd-01`) is created and added as a port on the OVS bridge `br-int`. The VM sees a virtual NIC; on the host side, the other end is a TAP device plugged into OVS.
* *OVN-Kubernetes* uses veth pairs rather than TAP devices for pods, but the concept is similar - one end is inside the container's network namespace, the other is on the OVS bridge.

----
Virtual Machine Connectivity (TAP):

  +--------+        +--------+
  |  VM    |        |  OVS   |
  | (QEMU) |<------>| br-int |<----> Network
  | vNIC   |  TAP   |        |
  +--------+        +--------+
      tap1234abcd-01

Pod Connectivity (veth):

  +--------+        +--------+
  |  Pod   |        |  OVS   |
  | (ctnr) |<------>| br-int |<----> Network
  | eth0   |  veth  |        |
  +--------+  pair  +--------+
      abc123_h (host end)
----


[NOTE]
====
When listing OVS ports with `ovs-vsctl show`, you will see TAP devices for VMs (in OpenStack) and veth devices for pods (in Kubernetes). The naming convention helps identify what each port connects to. In OpenStack, port names typically match the first 11 characters of the Neutron port UUID with a `tap` prefix.

== Why Virtual Switching Matters

Having covered the building blocks, let us step back and consider why virtual switching - and OVS in particular - is necessary.

In a physical data center, servers connect to physical switches via cables. The switch forwards traffic based on MAC addresses (L2) or VLAN tags. This is straightforward when each server runs a single workload.

In a virtualized or containerized environment, a single physical server may run *dozens or hundreds* of virtual machines or containers, each with its own network identity (MAC address, IP address, network membership). These workloads need to:

. *Communicate with each other* on the same host (without traffic leaving the server)
. *Communicate with workloads on other hosts* (via the physical network)
. *Be isolated from each other* (tenant A cannot see tenant B's traffic)
. *Be subject to security policies* (firewalls, access controls)
. *Support dynamic placement* (VMs and containers move between hosts)
. *Scale to thousands of networks* (far beyond VLAN limits)

A virtual switch inside the hypervisor or container host handles all of this. And OVS - with its OpenFlow programmability, overlay tunnel support, and kernel datapath performance - is the virtual switch that the industry settled on for production cloud workloads.

----
Physical Server (Compute Node):
+--------------------------------------------------------+
|                                                        |
|  +------+  +------+  +------+  +------+  +------+     |
|  | VM-1 |  | VM-2 |  | VM-3 |  | Pod-1|  | Pod-2|     |
|  |Net-A |  |Net-B |  |Net-A |  |Net-C |  |Net-D |     |
|  +--+---+  +--+---+  +--+---+  +--+---+  +--+---+     |
|     |         |         |         |         |          |
|  +--+---------+---------+---------+---------+------+   |
|  |             OVS (br-int)                        |   |
|  |  Handles all virtual switching, isolation,      |   |
|  |  security, and tunnel encapsulation             |   |
|  +---------------------+--+-----------------------+   |
|                        |  |                            |
|                   Physical NICs                        |
+------------------------+--+----------------------------+
                         |  |
                    Physical Network
----


[NOTE]
.Key Concept
====
Virtual switching is not optional in cloud environments - it is the fundamental building block that makes multi-tenant networking possible. OVS is the virtual switch that Red Hat products use because it provides the programmability (OpenFlow), scalability (overlay tunnels), and performance (kernel datapath, DPDK) that cloud-scale networking demands.
====
