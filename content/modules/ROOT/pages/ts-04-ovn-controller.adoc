= Scenario 04: Pods Lose Network After Node Maintenance

== The Problem

*Customer report:* "After a node was rebooted for maintenance, pods scheduled on that node
have no network connectivity. Other nodes work fine."

The customer performed a routine kernel update on worker-3. They followed the standard
procedure: cordon, drain, reboot, uncordon. The node came back as Ready, pods were
rescheduled, but none of the pods on worker-3 can reach the network. Pods on all other
worker nodes are working normally.

'''

*Finding:* This is the critical evidence. ovn-controller is trying to connect to the
OVN Southbound DB on all three control plane nodes (10.0.0.10, 10.0.0.11, 10.0.0.12 on
port 9642) but *TLS certificate validation is failing* every time. The error
`certificate verify failed` means the SSL/TLS handshake cannot be completed because
ovn-controller considers the server's certificate invalid.


[NOTE]
.Key Concept
====
OVN-Kubernetes uses mutual TLS (mTLS) for all communications between ovn-controller (on worker nodes) and the Southbound DB (on control plane nodes). Both sides present certificates, and both sides validate the other's certificate. TLS certificate validation checks several things:

* Is the certificate signed by a trusted CA?
* Is the certificate within its validity period (not expired, not "not yet valid")?
* Does the certificate's subject match the expected identity?

If the system clock is wrong, a perfectly valid certificate may appear expired (clock too far in the future) or not yet valid (clock too far in the past).
====


Look for more specific error messages:

[source,bash]
----
[user@bastion ~]$ oc logs -n openshift-ovn-kubernetes ovnkube-node-r5t8y -c ovn-controller --tail=200 | grep -i "certificate\|time\|clock\|valid"
----

----

2025-04-15T14:15:23.458Z|00002|stream_ssl|ERR|Certificate verification error: certificate is not yet valid
2025-04-15T14:15:24.461Z|00006|stream_ssl|ERR|SSL_connect: error:0A000086:SSL routines::certificate verify failed (SSL_ERROR_SSL)
2025-04-15T14:15:24.461Z|00006|stream_ssl|ERR|Certificate verification error: certificate is not yet valid
----

*Finding:* The specific error is "*certificate is not yet valid*." This means the
node's system clock is set to a time BEFORE the certificate's "Not Before" timestamp.
The certificate appears to be from the future from the node's perspective.

====

=== Step 11: Check System Clock (THE KEY STEP)

*Why:* TLS certificate validation requires an accurate system clock because certificates
have validity windows ("Not Before" and "Not After" timestamps). If the system clock is
wrong, valid certificates will fail validation. This is our leading hypothesis based on the
"certificate is not yet valid" error.

Check the clock on worker-3:

[source,bash]

Check a healthy node for comparison:

[source,bash]

----

----
Tue Apr 15 14:28:12 UTC 2025
----

*Finding:* Worker-3's clock shows *March 12, 2024* while the actual date is **April 15,
2025*. The clock is over *13 months in the past**. This explains the "certificate is not
yet valid" error - the SB DB's TLS certificate was issued (or renewed) after March 2024,
so from worker-3's perspective, the certificate is from the future and therefore "not yet
valid."

*Finding:* NTP service is *inactive* and system clock is *not synchronized*. This
confirms the root cause.

Check chronyd:

*Finding:* chronyd is *disabled and not running*. After the reboot, chronyd did not
start because it was disabled. Without NTP, the system clock fell back to the hardware
RTC clock, which was significantly wrong (possibly the CMOS battery is low, or the RTC
was never set correctly).

Verify the certificate validity window to confirm the mismatch:

[source,bash]
----
[user@bastion ~]$ oc exec -n openshift-ovn-kubernetes ovnkube-node-r5t8y -c ovn-controller -- \
  openssl s_client -connect 10.0.0.10:9642 -servername 10.0.0.10 </dev/null 2>/dev/null | \
  openssl x509 -noout -dates

notAfter=Jan 15 00:00:00 2026 GMT
----

*Finding:* The SB DB's TLS certificate is valid from *January 15, 2025* to **January 15,
2026*. Worker-3's clock is set to *March 12, 2024**, which is BEFORE the certificate's
"notBefore" date. This is exactly why the validation fails with "certificate is not yet
valid."

----
Timeline:

  worker-3 clock thinks it is here
  |
  v
  Mar 2024 -------- Jan 2025 -------- Apr 2025 -------- Jan 2026
                    |                  |                  |
                    Certificate        Actual date        Certificate
                    Not Before                            Not After
                    
  Worker-3 sees a certificate "from the future" -> REJECTS IT
----


[NOTE]
.Key Concept
====
TLS certificate validation is time-dependent. Every TLS certificate has a validity window defined by `notBefore` and `notAfter` timestamps. The client (here, ovn-controller) checks its local system clock against these timestamps. If the local clock is before `notBefore`, the certificate appears "not yet valid." If the clock is after `notAfter`, the certificate appears "expired." In both cases, the TLS handshake fails. This is a critical security feature - it prevents the use of compromised or retired certificates - but it requires accurate clocks on all systems.
====

== Root Cause

The root cause is a *system clock skew on worker-3* caused by a missing NTP configuration:

. Worker-3 was rebooted for a kernel update.

. chronyd (NTP daemon) was *disabled* on worker-3 and did not start after reboot.

. Without NTP synchronization, the system clock fell back to the *hardware RTC clock*,
   which was set to March 12, 2024 - over 13 months in the past (likely due to a depleted
   CMOS battery or the RTC was never properly configured).

. OVN-Kubernetes uses *mutual TLS* for communication between ovn-controller and the
   Southbound DB. The SB DB's TLS certificate was valid from January 2025 to January 2026.

. With worker-3's clock reading March 2024, the SB DB certificate appeared **"not yet
   valid"** (its `notBefore` is January 2025, which is "in the future" from worker-3's
   perspective).

. ovn-controller correctly rejected the certificate and *refused to connect* to the
   SB DB.

. Without a connection to the SB DB, ovn-controller could not:
** Receive logical flow updates from ovn-northd
** Program OpenFlow rules into OVS br-int
** Claim port bindings for pods on the node

. br-int had only default drop rules (`fail_mode: secure`), causing **all pod traffic to
   be dropped**.

=== 4. Consider Adding a Pre-check Script

Create a script that runs before uncordoning a node:

[source,bash]
----
#!/bin/bash
# pre-uncordon-check.sh
NODE=$1

echo "=== Checking node: $NODE ==="

# Check clock
NODE_DATE=$(oc debug node/$NODE -- chroot /host date +%s 2>/dev/null)
LOCAL_DATE=$(date +%s)
DIFF=$((NODE_DATE - LOCAL_DATE))
ABS_DIFF=${DIFF#-}

if [ "$ABS_DIFF" -gt 60 ]; then
    echo "FAIL: Clock skew detected: ${DIFF} seconds"
    echo "  Fix: oc debug node/$NODE -- chroot /host chronyc makestep"
    exit 1
else
    echo "PASS: Clock skew within tolerance: ${DIFF} seconds"
fi

# Check NTP
NTP_STATUS=$(oc debug node/$NODE -- chroot /host chronyc tracking 2>/dev/null | grep "Leap status" | awk '{print $4}')
if [ "$NTP_STATUS" != "Normal" ]; then
    echo "FAIL: NTP not synchronized (status: $NTP_STATUS)"
    exit 1
else
    echo "PASS: NTP synchronized"
fi

echo "=== All checks passed. Safe to uncordon. ==="
----

== Key Takeaways

* *System clock accuracy is critical for TLS-based systems.* OVN-Kubernetes uses mutual
  TLS for all control plane communications. A clock skew of even a few hours can break
  certificate validation and completely disconnect ovn-controller from the SB DB.

* *"Node Ready" does not mean "node networking is functional."* Kubernetes node readiness
  checks verify kubelet connectivity but do not check OVN-K components. A node can be
  Ready with zero network connectivity for pods.

* *Always verify NTP after a node reboot.* NTP configuration can be disabled, misconfigured,
  or fail to start after a reboot. Include NTP verification in every post-maintenance checklist.

* *br-int with fail_mode: secure drops ALL traffic when ovn-controller is disconnected.*
  This is a safety feature, but it means any ovn-controller connection failure results in
  complete network isolation for all pods on the node.

* *Check ovn-controller connection-status as the first networking diagnostic* on any node
  with pod connectivity issues. If it says "not connected," all other networking
  diagnostics are secondary to fixing the connection.
