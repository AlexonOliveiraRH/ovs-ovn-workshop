= Module 06 - OVS vs OVN: A Comprehensive Comparison


== Introduction

This is one of the most important modules in the workshop. Engineers frequently encounter both OVS and OVN in Red Hat products, and one of the most common points of confusion is how they relate to each other. Some think OVN replaces OVS. Others believe they are completely independent projects. Neither is correct.

This module lays out exactly what each technology does, how they fit together, when you would use one versus the other, and what the practical differences are in day-to-day operations. By the end, you will be able to clearly explain the OVS/OVN relationship to a customer and make informed decisions about which architecture fits a given scenario.

'''

== The Relationship Between OVS and OVN

=== The Single Most Important Point

*OVN is NOT a replacement for OVS. OVN is built ON TOP of OVS.*

This distinction is fundamental. Every deployment that runs OVN also runs OVS underneath it. OVN does not contain its own data plane - it relies entirely on OVS to forward packets. What OVN provides is an intelligent control plane and management layer that programs OVS automatically based on high-level intent.

Think of it this way:

* *OVS = the data plane* - the virtual switch itself that moves packets from port to port based on flow rules.
* *OVN = the control plane + management layer* - the brain that decides what flow rules OVS should have and programs them automatically.


[NOTE]
.Key Concept
====
When you run OVN, you are still running OVS. OVN adds components on top of OVS but never removes or replaces the OVS components. Every `ovs-vsctl show` command, every `ovs-ofctl dump-flows` command, every kernel datapath operation - all of that still exists and still works when OVN is in the picture. OVN simply takes over the job of writing the OpenFlow rules that OVS enforces.
====


=== The Traffic Light Analogy

Imagine a city-wide traffic light system:

* *OVS standalone* is like a set of programmable traffic lights at an intersection. Each light can be configured to change based on specific rules. But someone - either a traffic engineer or an automated system - must go to each intersection and program each light individually. If the city has a thousand intersections, that is a thousand individual configurations to write and maintain.

* *OVN on top of OVS* is like adding a central traffic management system. Instead of programming each intersection individually, you describe your desired traffic patterns at a high level: "I want northbound traffic on Main Street to have priority during morning rush hour." The management system figures out which lights at which intersections need which timings and programs them all automatically. The traffic lights themselves (OVS) have not changed - they still do the same job of controlling traffic. But now there is an intelligent system (OVN) deciding how to configure them.

This analogy captures the key properties:

. The traffic lights (OVS) still do all the actual work of directing traffic (forwarding packets).
. The management system (OVN) does not replace the traffic lights - it programs them.
. You can run traffic lights without the management system (standalone OVS), but you need to program them yourself.
. With the management system, you describe what you want rather than how to achieve it.
. The management system handles coordination across all intersections (multi-node).

=== How OVN Programs OVS

When OVN is running, it takes high-level network descriptions (logical switches, routers, ACLs) and translates them into OpenFlow rules that get installed in OVS. The chain looks like this:

----
Administrator / CMS (e.g., OpenStack, Kubernetes)
         |
         v
   OVN Northbound DB    <-- High-level intent (logical switches, routers, ACLs)
         |
         v
     ovn-northd          <-- Translates logical config into logical flows
         |
         v
   OVN Southbound DB    <-- Logical flows + chassis bindings
         |
         v
   ovn-controller        <-- On each hypervisor, translates logical flows
         |                    into physical OpenFlow rules
         v
   OVS (ovs-vswitchd)   <-- Executes OpenFlow rules, forwards packets
         |
         v
   OVS kernel datapath   <-- Fast path for packet forwarding
----

Every step in this chain is important:

. A Cloud Management System (CMS) like OpenStack or Kubernetes tells OVN what it wants: "Create a logical switch with these ports, a logical router connecting these networks, ACLs blocking this traffic."
. OVN stores this in the Northbound Database as a logical network topology.
. `ovn-northd` reads the Northbound DB and generates logical flows - forwarding rules expressed in terms of logical entities (logical ports, logical switches) rather than physical entities (specific OVS ports on specific hosts).
. These logical flows are stored in the Southbound Database along with information about which chassis (hypervisor) hosts which logical ports.
. `ovn-controller` on each hypervisor reads the Southbound DB, takes the logical flows relevant to its chassis, and translates them into physical OpenFlow rules that reference actual OVS ports, tunnel ports, and MAC/IP addresses.
. These OpenFlow rules are installed in OVS's `br-int` bridge.
. OVS forwards packets according to those rules, using the kernel datapath for performance.


[NOTE]
====
You never need to write OpenFlow rules manually when OVN is managing OVS. In fact, manually inserting flows into an OVN-managed bridge is dangerous because `ovn-controller` periodically reconciles the flows and will remove anything it did not program. If you need to change network behavior, change it in OVN (via `ovn-nbctl` or the CMS), not in OVS directly.
====

=== Understanding the Implications

*L2 Switching* - With standalone OVS, you create bridges, add ports, and either rely on MAC learning (which has scale limitations) or write explicit flow rules. With OVN, you create a logical switch in the Northbound DB and OVN handles all the flow programming, including across multiple hypervisors with automatic tunneling.

*L3 Routing* - OVS can execute IP matches, TTL updates and MAC rewrites, but the administrator or controller must supply routing policy. OVN provides logical routers and generates those flows. ML2/OVS can use either centralized routing or DVR; centralized network-node traversal is not inherent to OVS.

*Security / ACLs* - With standalone OVS, implementing a stateful firewall requires writing complex OpenFlow rules that use connection tracking (conntrack) actions and matches. You need to handle new connections, established connections, related connections, and invalid connections with separate flow entries. With OVN, you write a simple ACL like "allow TCP to port 80 from this address set" and OVN generates all the necessary conntrack flows.

*DHCP* - Standalone OVS deployments normally use a separate DHCP server. OVN integrates this service through logical actions and the local `ovn-controller` packet-in handler; it does not generate the whole response solely in the kernel (https://github.com/ovn-org/ovn/blob/v24.03.0/controller/pinctrl.c[OVN 24.03 implementation]).

== Architecture Comparison

=== OVS Standalone Architecture

A standalone OVS deployment on a single node has three core components:

----
+-------------------------------------------------------+
|                    User Space                          |
|                                                        |
|  +------------------+     +------------------------+   |
|  |  ovsdb-server    |<--->|    ovs-vswitchd        |   |
|  |                  |     |                        |   |
|  | Stores config:   |     | OpenFlow processing    |   |
|  | - bridges        |     | Flow table management  |   |
|  | - ports          |     | Userspace slow path    |   |
|  | - interfaces     |     |                        |   |
|  | - QoS            |     | Communicates with      |   |
|  +------------------+     | kernel datapath        |   |
|                           +------------------------+   |
|                                    |                   |
+-------------------------------------------------------+
                                     |  Netlink
+-------------------------------------------------------+
|                   Kernel Space                         |
|                                                        |
|  +--------------------------------------------------+ |
|  |              OVS Kernel Datapath                  | |
|  |                                                   | |
|  | Fast-path packet forwarding                       | |
|  | Flow cache (megaflow table)                       | |
|  | Cache miss -> upcall to ovs-vswitchd              | |
|  +--------------------------------------------------+ |
+-------------------------------------------------------+
----

* *ovsdb-server* - Stores the OVS configuration in a JSON-based database. This includes bridge definitions, port configurations, interface settings, and other persistent state.
* *ovs-vswitchd* - The main switching daemon. It reads configuration from ovsdb-server, manages OpenFlow tables, and communicates with the kernel datapath. When a packet hits a flow that only exists in the userspace tables (a "cache miss" in the kernel), it gets sent up to ovs-vswitchd for classification.
* *OVS kernel datapath* - A kernel module that performs fast-path packet forwarding using cached flow patterns (megaflows). In the common forwarding fast path, a cache hit executes actions in the kernel without userspace classification. A cached flow can still explicitly send a packet to userspace; a hit alone does not guarantee kernel-only processing (see `OVS_ACTION_ATTR_USERSPACE` in the https://raw.githubusercontent.com/torvalds/linux/v6.6/net/openvswitch/actions.c[Linux 6.6 OVS action implementation]).

In this architecture, someone (or something) must program the OpenFlow tables in ovs-vswitchd. That "someone" could be:

* A human using `ovs-ofctl`
* An SDN controller (like OpenDaylight) speaking OpenFlow
* A Neutron agent (like `neutron-openvswitch-agent`)
* A script or automation tool

=== OVN Architecture (Built on OVS)

When OVN is deployed, it adds several components while keeping all of the OVS components intact:

----
+------------------------------------------------------------------+

|                                                                   |

|  | Logical switches  |            | Logical flows     |           |

|  | Load balancers    |            | MAC/IP bindings   |           |
|  | DHCP options      |            |                   |           |
|  +-------------------+            +-------------------+           |
|                                           |                       |
+------------------------------------------------------------------+
                                            |
            +-------------------------------+-------- ...
            |  OVSDB protocol               |
            v                               v
+---------------------------+   +---------------------------+
|     Hypervisor Node 1     |   |     Hypervisor Node 2     |
|                           |   |                           |
| +---------------------+  |   | +---------------------+   |
| |  ovn-controller     |  |   | |  ovn-controller     |   |
| |                     |  |   | |                     |   |
| | Reads SB DB         |  |   | | Reads SB DB         |   |

| | flows to physical   |  |   | | flows to physical   |   |
| | OpenFlow rules      |  |   | | OpenFlow rules      |   |
| +----------+----------+  |   | +----------+----------+   |
|            |              |   |            |              |
|            v              |   |            v              |
| +---------------------+  |   | +---------------------+   |
| |  ovs-vswitchd       |  |   | |  ovs-vswitchd       |   |
| |  ovsdb-server       |  |   | |  ovsdb-server       |   |
| |  kernel datapath    |  |   | |  kernel datapath    |   |
| +---------------------+  |   | +---------------------+   |
|                           |   |                           |
| VM-A     VM-B             |   | VM-C     VM-D            |
+---------------------------+   +---------------------------+
----

The additional OVN components are:

* *OVN Northbound Database (NB DB)* - Stores the logical network topology as defined by the administrator or CMS. This is the "desired state." Contains logical switches, logical routers, logical switch ports, ACLs, NAT rules, load balancers, and DHCP options.

* *OVN Southbound Database (SB DB)* - Stores the physical-logical mappings and the compiled logical flows. This is the "implementation state." Contains logical flows, chassis registrations, port bindings, datapath bindings, and MAC/IP bindings.

* *ovn-northd* - A centralized daemon that reads the Northbound DB and writes to the Southbound DB. It compiles high-level logical network definitions into lower-level logical flows.

* *ovn-controller* - A daemon running on every hypervisor. It reads the Southbound DB, takes the logical flows relevant to its chassis, and translates them into physical OpenFlow rules that it installs in the local OVS instance.


[NOTE]
.Key Concept
====
The OVS components (ovs-vswitchd, ovsdb-server, kernel datapath) are still present and doing the same job they always did. OVN adds a layer above them. The relationship is additive, not substitutive.
====

== When to Use Which

=== Use OVS Standalone When...

*You need a simple virtual switch on a single host.*
If your use case is straightforward - connecting VMs or containers on a single host with basic L2 switching - standalone OVS is simpler and has less overhead.

*You have an external SDN controller.*
If you are using an SDN controller like OpenDaylight, ONOS, or a commercial controller that speaks OpenFlow, that controller takes OVN's role of programming OVS.

*You need maximum performance with minimal overhead.*
In highly performance-sensitive scenarios (such as network function virtualization with DPDK), you might want the thinnest possible stack between packets and forwarding decisions.

*You are building custom network solutions.*
If you are developing specialized networking applications that need fine-grained control over every flow rule, standalone OVS gives you that direct access.

*You are experimenting or learning.*
For understanding how virtual switching works at the fundamental level, starting with standalone OVS is the right approach.

=== Use OVN When...

*You need multi-tenant virtual networking.*
OVN was designed for multi-tenant environments where different tenants need isolated networks.

*You want built-in L2, L3, security, NAT, and load balancing.*
OVN provides all of these out of the box.

*You are integrating with a Cloud Management System.*
OpenStack (via ML2/OVN), Kubernetes (via OVN-Kubernetes), and other platforms have OVN integration.

*You need distributed routing.*
OVN's distributed logical routers route traffic locally on the hypervisor rather than hairpinning through a centralized network node.

*You want automatic tunnel management.*
OVN automatically establishes and manages Geneve tunnels between all hypervisors.

*You want declarative network configuration.*
With OVN, you describe what you want and OVN figures out the implementation.

== The Migration Path: OVS to OVN

=== Historical Context

*The ML2/OVS Era*

In the early days of OpenStack networking (roughly 2012-2018 as the dominant architecture), the Neutron ML2/OVS plugin was the standard way to use OVS with OpenStack:

----
+------------------+
| Neutron Server   |
| (API + ML2/OVS)  |
+--------+---------+
         |  RPC (RabbitMQ)
         |
+--------+----------------------------+--------- ...
|                                     |
v                                     v
+----------------------------+   +----------------------------+
| Controller / Network Node  |   |       Compute Node         |
|                            |   |                            |
| neutron-l3-agent           |   | neutron-openvswitch-agent  |
| neutron-dhcp-agent         |   |                            |
| neutron-metadata-agent     |   | OVS: br-int, br-tun        |
| neutron-openvswitch-agent  |   |                            |
|                            |   | VM-A       VM-B            |
| OVS: br-int, br-tun, br-ex|   +----------------------------+
| Router namespaces          |
| DHCP namespaces            |
+----------------------------+
----

*Problems with ML2/OVS at Scale:*

. *Network node bottleneck* - All north-south traffic and (without DVR) all east-west routing traffic funneled through network nodes.
. *RabbitMQ dependency* - Message bus congestion, partitions, or failures could cause networking state to become inconsistent.
. *Agent coordination* - Multiple agents on multiple nodes needed to stay in sync.
. *DVR complexity* - DVR addressed the routing bottleneck but its implementation was complex and introduced new failure modes.
. *Flow table scale* - Large deployments could end up with tens of thousands of flows per compute node.

=== The Shift to OVN

OVN was created specifically to address these problems:

* *Agent changes* - OVN replaces the OVS, L3 and DHCP agents for ordinary instance networking; an OVN metadata agent remains on compute nodes.
* *Native distributed routing* - Every hypervisor can route traffic locally.
* *Built-in services* - DHCP and DNS are integrated into OVN; OpenStack metadata still requires its agent/proxy service.
* *Database-driven state* - OVSDB replaces RabbitMQ for state distribution.
* *Single bridge* - One `br-int` handles everything, no separate `br-tun`.

=== RHOSP Migration Path: ML2/OVS to ML2/OVN

In Red Hat OpenStack Platform:

* *RHOSP 13* - OVN became fully supported, as recorded in the https://docs.redhat.com/en/documentation/red_hat_openstack_platform/13/pdf/release_notes/release-notes.pdf[RHOSP 13 release notes].
* *RHOSP 15* - ML2/OVN became the default for new deployments, according to the https://docs.redhat.com/en/documentation/red_hat_openstack_platform/17.0/html/testing_migration_of_the_networking_service_to_the_ml2ovn_mechanism_driver/planning-your-migration-ovs-to-ovn[RHOSP 17.0 migration guide].

* *RHOSP 17.0/17.1* - ML2/OVS is deprecated but retains maintenance support in the RHOSP 17 releases. Check the release-specific migration requirements; deprecation does not mean immediate removal.


[WARNING]
====
An ML2/OVS to ML2/OVN migration causes networking downtime. This must be planned as a maintenance window.
====


=== Performance Considerations in the Migration

* *East-west routing throughput*: OVN is generally better because routing is distributed.
* *North-south throughput*: Similar in most cases.
* *Connection setup latency*: OVN may have slightly higher first-packet latency due to the longer flow pipeline.
* *Flow table size*: OVN typically generates more flows per compute node than ML2/OVS.
* *Control plane responsiveness*: OVN's database-driven model is generally faster than ML2/OVS's RabbitMQ-based model.

== Performance Comparison

=== OVS Kernel Datapath Performance

The kernel datapath executes cached actions on a flow hit; those actions can include sending a packet to userspace. Throughput, latency and hit rate must be measured for the workload; neither equivalence to Linux bridge nor a universal 99% threshold follows from this architecture.

=== OVN-Programmed OVS Performance

OVN can program the same OVS datapath, but that does not guarantee identical forwarding performance. Differences include:

* *More flow rules* from the comprehensive logical pipeline
* *Megaflow cache* efficiency may vary with more complex flow tables
* *Connection tracking overhead* for ACLs, NAT, and load balancing
* *Metadata processing* for Geneve tunnel options

=== Flow Count Differences

*Standalone OVS (minimal):* A learning bridge can use one `normal` OpenFlow rule; explicit policies require additional rules.

*OVN-managed OVS:* Flow count depends on OVN version, topology and enabled services. Count OpenFlow and datapath flows separately in the actual environment.

=== OVS-DPDK with and without OVN

*OVS-DPDK standalone* uses the userspace `netdev` datapath and poll-mode drivers for DPDK ports, bypassing the OVS kernel datapath on that path. Throughput depends on hardware, NUMA placement, PMD configuration, packet mix and enabled features; line-rate forwarding is not guaranteed. See the https://docs.openvswitch.org/en/stable/intro/install/dpdk/#performance-tuning[OVS-DPDK performance tuning guide].

*OVS-DPDK with OVN* works the same way but with more OpenFlow rules from the OVN pipeline. Considerations include larger flow tables affecting EMC/SMC efficiency, connection tracking overhead in DPDK userspace, and the potential benefit of SmartNIC hardware offload.

=== Connection Tracking Overhead with OVN ACLs

OVN uses conntrack extensively for ACLs, NAT, and load balancing. The overhead has two components:

. *Per-connection setup*: Creating and committing connection state.
. *Per-packet lookup*: Looking up and updating connection state.

This becomes significant in high connection rate scenarios, large connection table scenarios, or short-lived connection workloads.


[NOTE]
====
For the Linux kernel datapath, inspect conntrack with `conntrack -C` and `sysctl net.netfilter.nf_conntrack_max`. These do not measure the `netdev` userspace conntrack table; use the OVS datapath commands appropriate to the installed version.
====

== Operational Differences

=== Day-to-Day Management

*Standalone OVS* - Direct and imperative. You interact with OVS using `ovs-vsctl`, `ovs-ofctl`, etc. Changes are made per-node.

*OVN* - Declarative and centralized. You interact with the OVN Northbound Database using `ovn-nbctl`. Changes propagate automatically to all relevant nodes.


[NOTE]
.Key Concept
====
With standalone OVS, you manage per-node state. With OVN, you manage a centralized logical topology and OVN handles the per-node implementation.
====


=== Monitoring Approaches

*Standalone OVS* - `ovs-appctl version`, `ovs-ofctl dump-flows`, `ovs-ofctl dump-ports`, `ovs-appctl dpctl/show`, `ovs-appctl coverage/show`.

*OVN (in addition to all OVS commands)* - `ovn-nbctl show`, `ovn-sbctl show`, `ovn-sbctl lflow-list`, `ovn-appctl cluster/status`, `conntrack -C`, `conntrack -S`.

=== Troubleshooting Methodology Differences

*Standalone OVS* - Bottom-up: port status, flow rules, packet counters, datapath cache, tcpdump.

*OVN* - Top-down then bottom-up: logical topology, logical flows, port bindings, `ovn-trace`, then physical flows, tcpdump.


[NOTE]
====
When troubleshooting OVN, always start with the logical layer before diving into physical flows. Many issues that look like OVS problems are actually logical configuration issues.
====


=== Backup and Recovery

*Standalone OVS* - Backup `/etc/openvswitch/conf.db` or use `ovsdb-client backup`.

*OVN* - Back up both NB DB and SB DB. The NB DB is the most critical piece of state.


[WARNING]
====
If you lose all copies of the NB DB (including all Raft replicas), you lose the entire logical network configuration. Regular backups are essential.
====


=== Upgrade Procedures

*Standalone OVS* - Per-node, independent rolling upgrades.

*OVN* - Upgrade central components first (NB DB, SB DB, northd), then rolling-upgrade ovn-controller on each node.

'''

== Key Takeaways

. *OVN is built on OVS, not a replacement for it.* Every OVN deployment runs OVS underneath. OVN adds a control plane; it does not replace the data plane.

. *OVS is imperative, OVN is declarative.* With OVS, you program each flow rule. With OVN, you describe the desired network topology and OVN generates the flows.

. *OVN adds a logical model for L3, security, DHCP, NAT, and LB.* OVS already supplies primitives such as conntrack, NAT and select groups; OVN configures them as network services.

. *OVN excels at multi-node, multi-tenant environments.* If you are managing networks across multiple hypervisors with multiple tenants, OVN provides automation and consistency that is very difficult to achieve with standalone OVS.

. *Performance depends on policy and workload.* Sharing the OVS datapath does not make different flow pipelines equally costly.

. *The Red Hat ecosystem has standardized on OVN.* RHOSP uses ML2/OVN, OCP uses OVN-Kubernetes.

. *Troubleshoot OVN top-down, OVS bottom-up.* Start with logical tools (ovn-trace, ovn-nbctl, ovn-sbctl), then dive into physical tools (ovs-ofctl, tcpdump).

. *Know both layers.* Even in an OVN-managed environment, you need to understand OVS to troubleshoot effectively.
