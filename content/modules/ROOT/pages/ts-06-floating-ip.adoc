= Scenario 06: Floating IP Not Accessible from External Network

== The Problem

*Customer report:* "Assigned a floating IP to a VM in RHOSP but cannot reach it from the
external network. VM can reach external network fine (outbound SNAT works). This started
after a controller node failover."

The customer has a VM running a web application with floating IP 10.20.30.100 assigned.
The VM was accessible from the external network until controller-0 (the active gateway
chassis) was rebooted for maintenance. After controller-0 came back up, outbound traffic
from the VM to the internet works (SNAT), but inbound traffic to the floating IP from
external clients does not reach the VM. External clients get "connection timed out" when
trying to reach 10.20.30.100.


[IMPORTANT]
.RHOSP 17.1: Containerized OVN Commands
====
In RHOSP 17.1, OVN databases run inside Pacemaker-managed containers. All `ovn-nbctl` and `ovn-sbctl` commands shown in this scenario must be executed via `podman exec` on the controller node. For example:

* `ovn-nbctl show` becomes `sudo podman exec -it ovn_cluster_north_db_server ovn-nbctl --no-leader-only show`
* `ovn-sbctl show` becomes `sudo podman exec -it ovn_cluster_south_db_server ovn-sbctl --no-leader-only show`

For brevity, this scenario shows the bare commands. Refer to xref:12-troubleshooting.adoc#_rhosp_red_hat_openstack_platform[Module 12: RHOSP Product-Specific Troubleshooting] for the full containerized command syntax.

== How Floating IPs Work in OVN

Understanding the floating IP architecture is essential for troubleshooting this issue.


[quote]
____
*Key Concept: Distributed vs. Centralized NAT in OVN*  OVN implements two types of NAT for routers:  - *SNAT (Source NAT / outbound):* Distributed across all compute nodes. Each compute node performs SNAT locally for VMs it hosts. Traffic exits through the local Geneve tunnel to the gateway chassis. Return traffic for established SNAT connections follows conntrack entries and can arrive at any gateway.  - *DNAT (Destination NAT / floating IP inbound):* Centralized on the gateway chassis. Inbound traffic to a floating IP must arrive at the gateway chassis, which performs DNAT (translating 10.20.30.100 to 192.168.100.50) and forwards the packet to the correct compute node via the Geneve overlay.  This asymmetry is why outbound SNAT can work while inbound DNAT fails - they use different paths.
____


=== The Floating IP Packet Path

----
INBOUND (external -> VM):

External client -> Upstream router -> ARP for 10.20.30.100 ->
  Gateway chassis (controller-X) receives on br-ex ->
    DNAT: 10.20.30.100 -> 192.168.100.50 ->
      Geneve tunnel to compute node hosting the VM ->
        VM receives packet with src=external_client, dst=192.168.100.50

OUTBOUND (VM -> external):

VM sends packet -> Compute node local OVS ->
  Geneve tunnel to gateway chassis ->
    SNAT: 192.168.100.50 -> 10.20.30.100 ->
      br-ex on gateway chassis ->
        Physical network -> Upstream router -> Internet
----

=== Gateway Chassis HA

----
OVN supports multiple gateway chassis for high availability:

  controller-0: priority 1 (highest - preferred active)
  controller-1: priority 2 (standby)
  controller-2: priority 3 (standby)

When the active gateway fails:
  1. BFD detects the failure
  2. OVN selects the next highest-priority chassis (controller-1)
  3. The chassisredirect port binding moves to controller-1
  4. controller-1 sends gratuitous ARP (GARP) for all floating IPs
  5. Upstream router updates its ARP cache
  6. Traffic flows to the new active gateway

If step 4 or 5 fails, the upstream router still sends traffic to the
old gateway's MAC address, and inbound traffic is black-holed.
----

=== Step 6: Check ARP on the External Network (KEY FINDING)

*Why:* For external traffic to reach the floating IP, the upstream router must have the
correct ARP entry mapping 10.20.30.100 to the MAC address of the ACTIVE gateway chassis.
If the ARP cache still points to the old gateway (controller-0), traffic will be sent to
the wrong destination.

From a machine on the external network (or the upstream router):

[source,bash]
----
[admin@upstream-router ~]# arp -n | grep 10.20.30.100
----

----
10.20.30.100             ether   52:54:00:ex:c0:01   C                     eth1
----

*Finding:* The ARP entry for 10.20.30.100 points to MAC `52:54:00:ex:c0:01`. Let's
identify which controller this belongs to:

[source,bash]
----
[root@controller-0 ~]# ip link show br-ex | grep ether
----

----
    link/ether 52:54:00:ex:c0:01 brd ff:ff:ff:ff:ff:ff
----

[source,bash]
----
[root@controller-1 ~]# ip link show br-ex | grep ether
----

----
    link/ether 52:54:00:ex:c1:01 brd ff:ff:ff:ff:ff:ff
----

*Finding:* The ARP entry points to `52:54:00:ex:c0:01`, which is *controller-0's*
br-ex MAC address. But the active gateway is now *controller-1* (MAC
`52:54:00:ex:c1:01`). The upstream router is sending traffic for the floating IP to
the WRONG controller.

----
Current (broken) state:

External client -> upstream router -> ARP: 10.20.30.100 = 52:54:00:ex:c0:01
  -> Sends to controller-0 (OLD gateway, not active)
    -> controller-0 does NOT process the floating IP (not the active gateway)
      -> TRAFFIC BLACK-HOLED

Should be:

External client -> upstream router -> ARP: 10.20.30.100 = 52:54:00:ex:c1:01
  -> Sends to controller-1 (NEW active gateway)
    -> controller-1 performs DNAT and forwards to VM
      -> VM receives the traffic
----

This is the root cause. The upstream router's ARP cache was not updated after the
failover.

*Why:* After a gateway failover, OVN should send gratuitous ARP (GARP) from the new

or was not received by the upstream router, the old ARP entry persists.

----

*Finding:* ovn-controller on controller-1 DID send gratuitous ARP for 10.20.30.100 at
09:31:12, right after the failover. So the GARP was sent - but the upstream router did
not update its ARP cache.

Verify with tcpdump (if we had captured at the time):

[source,bash]

# tcpdump -i br-ex -n arp | grep 10.20.30.100
#
# Expected output:
# 09:31:12.123456 ARP, Reply 10.20.30.100 is-at 52:54:00:ex:c1:01 (gratuitous), length 28
----


[NOTE]
.Key Concept
====
Gratuitous ARP (GARP) is an ARP Reply packet sent without a corresponding ARP Request. It announces "I am now at this MAC address" to all devices on the L2 network. However, not all network devices honor GARP:  - Some switches/routers have GARP filtering enabled for security - Some routers have static ARP entries that GARP cannot override - GARP may be lost if the network is congested at the moment of failover - Some enterprise routers have long ARP cache timeouts and ignore GARP  When GARP fails to update the upstream router, inbound traffic continues to flow to the old gateway's MAC address, causing a black hole.
====

[source,bash]

52:54:00:up:rr:01). OVN knows how to reach the upstream router. The problem is the

== Root Cause

The root cause is a *stale ARP entry on the upstream router* after an OVN gateway
failover:

. *controller-0 was the active gateway* for tenant-router with the highest priority (3).
   The floating IP 10.20.30.100 was advertised from controller-0's br-ex with MAC
   `52:54:00:ex:c0:01`.

. *controller-0 was rebooted* for maintenance. OVN HA failover triggered, moving the
   active gateway to *controller-1* (priority 2).

. *OVN sent gratuitous ARP* from controller-1, announcing that 10.20.30.100 is now at
   MAC `52:54:00:ex:c1:01`.

. *The upstream router did not update its ARP cache.* The GARP was either:
** Received but ignored (some routers have GARP filtering or static ARP entries)
** Lost due to network timing during the failover transition
** The ARP entry had not yet expired and the router's ARP implementation does not
     honor GARP for existing entries

. *Result:* The upstream router continued sending traffic for 10.20.30.100 to
   controller-0's MAC (`52:54:00:ex:c0:01`). Controller-0 was either down or no longer
   the active gateway, so traffic was black-holed.

. *Outbound SNAT continued to work* because SNAT is processed at the gateway and return
   traffic for established connections follows conntrack entries. The established TCP/UDP
   connections could still return via the old conntrack entries, and new outbound connections
   from the VM used controller-1 (the new active gateway) for SNAT, which worked because
   controller-1 could reach the upstream router directly.

'''

== Resolution

=== Immediate Fix: Trigger ARP Refresh

*Option 1: Re-add the NAT rule to trigger new GARP*

This is the least invasive approach - removing and re-adding the NAT rule causes OVN to
re-send gratuitous ARP:

[source,bash]
----
[root@controller-0 ~]# ovn-nbctl lr-nat-del tenant-router dnat_and_snat 10.20.30.100
[root@controller-0 ~]# ovn-nbctl lr-nat-add tenant-router dnat_and_snat 10.20.30.100 192.168.100.50
----

Verify the NAT rule is back:

[source,bash]
----
[root@controller-0 ~]# ovn-nbctl lr-nat-list tenant-router
----

----
TYPE             EXTERNAL_IP        LOGICAL_IP            EXTERNAL_MAC         LOGICAL_PORT
dnat_and_snat    10.20.30.100       192.168.100.50
snat             10.20.30.5         192.168.100.0/24
----

Check ovn-controller logs for GARP on controller-1:

[WARNING]
====
Removing and re-adding the NAT rule causes a brief disruption to any active connections using the floating IP. The disruption should be very short (sub-second) but should be communicated to the customer.
====


*Option 2: Clear ARP on the upstream router*

If you have access to the upstream router, clear the ARP entry directly:

For Cisco IOS:

----
router# clear arp-cache 10.20.30.100
----

For Linux-based router:

[source,bash]
----
[admin@upstream-router ~]# ip neigh del 10.20.30.100 dev eth1
----

The upstream router will then send a new ARP request, which controller-1 will answer
with its own MAC.

*Option 3: Send manual gratuitous ARP from controller-1*

[source,bash]
----
[root@controller-1 ~]# arping -c 5 -A -I br-ex 10.20.30.100
----

----
ARPING 10.20.30.100 from 10.20.30.100 br-ex
Sent 5 probes (5 broadcast(s))
Received 0 response(s)
----


[NOTE]
====
The `arping -A` command sends unsolicited ARP Reply packets (gratuitous ARP). This is equivalent to what OVN does automatically after failover. If OVN's GARP did not work, manually sending GARP may not work either if the upstream router filters GARP. In that case, clearing the ARP cache on the upstream router (Option 2) is the only reliable approach.
====

== Prevention

=== 1. Configure Proper BFD Intervals for Fast Failover Detection

Reduce BFD intervals for faster failover detection:

[source,bash]
----
# Set BFD interval to 300ms with multiplier 3 (failure detected in ~1 second):
ovn-nbctl set nb_global . options:bfd-min-rx=300
ovn-nbctl set nb_global . options:bfd-min-tx=300
ovn-nbctl set nb_global . options:bfd-mult=3
----


[NOTE]
====
Aggressive BFD intervals (below 300ms) can cause false positives in congested networks. Test in your environment before deploying. The recommended minimum for production is 300ms with multiplier 3 (approximately 1-second detection time).
====


=== 2. Monitor Gateway Chassis HA Status

Set up monitoring for gateway failovers:

[source,bash]
----
# Check current active gateway:
ovn-sbctl find port_binding type=chassisredirect | grep chassis

# Monitor gateway changes:
watch -n 5 'ovn-sbctl find port_binding type=chassisredirect | grep -E "chassis|logical_port"'
----

Prometheus alert for gateway failover:

----
- alert: OVNGatewayFailover
  expr: changes(ovn_gateway_chassis_active[5m]) > 0
  labels:
    severity: warning
  annotations:
    summary: "OVN gateway failover detected"
    description: "Gateway chassis changed on {{ $labels.router }}. Verify floating IP accessibility."
----

=== 3. Verify GARP Is Working After Every Failover

Create a verification script to run after any planned failover:

[source,bash]
----
#!/bin/bash
# verify-floating-ip-arp.sh
# Run after any gateway failover to verify ARP is correct

FLOATING_IPS=$(ovn-nbctl lr-nat-list tenant-router | grep dnat_and_snat | awk '{print $2}')
ACTIVE_GW=$(ovn-sbctl find port_binding type=chassisredirect | grep chassis | awk '{print $3}')
ACTIVE_GW_MAC=$(ovn-sbctl get chassis $ACTIVE_GW encaps | head -1)

echo "Active gateway chassis: $ACTIVE_GW"
echo "Checking floating IPs..."

for FIP in $FLOATING_IPS; do
    echo -n "  $FIP: "
    # Send GARP just in case
    arping -c 3 -A -I br-ex $FIP > /dev/null 2>&1
    echo "GARP sent"
done
----

=== 4. Configure Upstream Routers to Accept GARP

Work with the network team to ensure upstream routers honor gratuitous ARP:

----
Upstream router configuration recommendations:
- Enable GARP processing (many routers have this disabled by default)
- Reduce ARP cache timeout to 300 seconds (default is often 14400 seconds / 4 hours)
- Do not use static ARP entries for floating IPs
- Consider enabling ARP proxy if GARP is not supported
----

=== 5. Reduce ARP Timeout on Upstream Routers

A shorter ARP cache timeout means stale entries are cleared faster, reducing the duration
of floating IP outages after failover:

For Cisco IOS:

----
interface GigabitEthernet0/1
  arp timeout 300
----

For Linux:

[source,bash]
----
echo 300 > /proc/sys/net/ipv4/neigh/eth1/gc_stale_time
----

=== 6. Document the Failover Procedure

----
Planned Gateway Maintenance Procedure:
1. Identify the current active gateway:
   ovn-sbctl find port_binding type=chassisredirect | grep chassis
2. If the active gateway is the node being maintained, trigger a graceful failover:
   ovn-nbctl lrp-set-gateway-chassis lrp-ext-tenant-router controller-1 3
   (temporarily give the backup higher priority)
3. Wait for failover to complete
4. Verify GARP was received by upstream router:
   arp -n | grep <floating-ip> (on upstream router)
5. If ARP is stale, manually clear it
6. Verify floating IP accessibility from external
7. Proceed with maintenance
8. After maintenance, restore priorities:
   ovn-nbctl lrp-set-gateway-chassis lrp-ext-tenant-router controller-0 3
----

== OVN Gateway HA Architecture Reference

=== How Gateway Chassis Priorities Work

----
Each logical router port (lrp) that connects to an external network has a list
of gateway chassis with priorities:

  lrp-ext-tenant-router:
    controller-0: priority 3 (highest - preferred)
    controller-1: priority 2
    controller-2: priority 1 (lowest)

OVN selects the highest-priority chassis that is "alive" (BFD reports UP)
as the active gateway.

When the active chassis fails:
  1. BFD on other chassis detects the failure (within mult * max(min_rx, min_tx))
  2. ovn-controller on the remaining chassis re-evaluates the priority list
  3. The highest-priority remaining chassis becomes active
  4. The chassisredirect port binding is updated in the SB DB
  5. The new active chassis installs gateway flows and sends GARP
----

=== BFD-Based Health Monitoring

----
BFD (Bidirectional Forwarding Detection) runs between all gateway chassis pairs:

  controller-0 <--BFD--> controller-1
  controller-0 <--BFD--> controller-2
  controller-1 <--BFD--> controller-2

BFD parameters:
  min_tx:  Minimum interval between transmitted BFD packets
  min_rx:  Minimum interval between received BFD packets
  mult:    Number of missed packets before declaring failure

Detection time = mult * max(min_rx, min_tx)

Example: min_tx=300ms, min_rx=300ms, mult=3
  Detection time = 3 * 300ms = 900ms (~1 second)
----

=== Chassisredirect Port Bindings

----
The chassisredirect (cr-) port is a special port type in the SB DB:
- Type: chassisredirect
- Purpose: Represents the active gateway for a logical router
- Binding: Points to the active gateway chassis
- nat_addresses: Lists all floating IPs and SNAT IPs to be advertised via GARP

When the binding changes (failover), the new chassis:
1. Installs OpenFlow rules for gateway processing
2. Sends GARP for all addresses in nat_addresses
3. Begins processing DNAT for inbound floating IP traffic
----

=== GARP Mechanism

----
After failover, the new active gateway sends:
1. Gratuitous ARP Reply for each floating IP
2. Gratuitous ARP Reply for the router's external IP (SNAT address)

Each GARP packet:
- Is an ARP Reply (opcode 2)
- sender IP = sender protocol address = floating IP
- sender MAC = new gateway's br-ex MAC
- target IP = floating IP (same as sender)
- Broadcast to ff:ff:ff:ff:ff:ff

All devices on the L2 segment that receive this should update their ARP cache.
----

== Key Takeaways

* *Floating IP accessibility depends on correct ARP on the external network.* After a
  gateway failover, the upstream router must learn the new MAC address for the floating IP.
  If GARP fails, the floating IP becomes unreachable from the external network.

* **Outbound SNAT working while inbound DNAT fails is the hallmark of a gateway
  failover ARP issue.** SNAT and DNAT use different paths - SNAT is partially distributed
  while DNAT is centralized on the gateway chassis.

* *Not all network devices honor gratuitous ARP.* Always verify that the upstream router
  accepts GARP. If it does not, plan for manual ARP cache clearing during failovers.

* *BFD is essential for fast failover detection.* Without BFD, OVN relies on the inactivity
  probe timeout (default 5 seconds), which means a longer disruption window. Configure BFD
  with aggressive intervals (300ms x 3 = ~1 second detection).

* *Always verify floating IP accessibility after any gateway maintenance.* Do not assume
  GARP worked - check the upstream router's ARP table and test from an external client.
