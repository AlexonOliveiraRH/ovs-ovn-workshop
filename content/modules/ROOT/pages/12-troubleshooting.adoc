= Module 12: Troubleshooting OVS and OVN

== Overview

Troubleshooting is the single most valuable skill you will use in the field. Every customer engagement eventually leads to a moment where something is broken and you need to find out why. A floating IP that stopped working after a migration, pods that cannot reach the internet, a database that takes thirty seconds to respond - these are real situations that land in support queues every day.

This module is deliberately the longest and most detailed in the workshop. It is designed as a reference you keep open during live incidents. Rather than theory, it focuses on the exact commands to run, the exact output to look for, and the exact steps to resolve each problem.

The module is organized from methodology (how to think about problems) through tool reference (what commands to use) to specific problem categories (what to do when X is broken) and finally real-world scenarios (complete walk-throughs of realistic support cases).


[NOTE]
.Key Concept
====
Troubleshooting is not guessing. It is a systematic process of forming hypotheses, testing them with diagnostic commands, and narrowing down the root cause. Every command you run should answer a specific question.
====

== 1. Troubleshooting Methodology

=== Systematic Approach to Network Troubleshooting

When a network problem is reported, resist the urge to immediately start running commands. The first few minutes spent thinking about the problem will save you hours of chasing false leads.

Follow this process:

. *Understand the symptom* - What exactly is failing? "The network is broken" is not a symptom. "VM A on compute-1 cannot ping VM B on compute-2, but VM C on compute-1 can reach VM B" is a symptom. Ask clarifying questions until you have a precise description.

. *Determine the scope* - Is this affecting one VM, one compute node, one network, or everything? Scope immediately tells you where to look.

. *Establish a timeline* - When did it start? Was anything changed? Did someone apply a configuration update, restart a service, or deploy new workloads? Changes correlate with problems.

. *Form a hypothesis* - Based on the symptom, scope, and timeline, what is your best guess about where the problem is?

. *Test the hypothesis* - Run specific diagnostic commands to confirm or reject your hypothesis.

. *Iterate* - If your hypothesis was wrong, form a new one based on what you learned. Each test narrows the search space.

=== Isolating the Problem Layer

In an OVS/OVN environment, problems can exist at several layers. Before diving into OVN-specific debugging, determine which layer is involved:


[cols="1,1,1",options="header"]
|===
|Layer
|What Lives Here
|How to Test

|Physical / Underlay
|Cables, NICs, physical switches, IP connectivity between hosts
|`ping` between hypervisors, `ethtool`, `ip link show`

|OVS Datapath
|Kernel module, flow cache, packet forwarding
|`ovs-dpctl show`, `ovs-appctl dpctl/dump-flows`

|OVS Daemon
|ovs-vswitchd, ovsdb-server, bridge/port/flow config
|`ovs-vsctl show`, `ovs-ofctl dump-flows`, `systemctl status`

|OVN Southbound
|ovn-controller, chassis registration, port bindings
|`ovn-sbctl show`, `ovn-sbctl list chassis`, `ovn-sbctl find port_binding`

|OVN Northbound
|Logical switches, routers, ACLs, NAT rules
|`ovn-nbctl show`, `ovn-nbctl list ACL`, `ovn-trace`

|Application / Orchestrator
|OpenStack Neutron, OpenShift SDN, Kubernetes Services
|Orchestrator-specific commands, API checks

|===


=== Top-Down vs Bottom-Up Approach

*Top-down approach* - Start at the application layer and work down. Best when:

* The user reports an application-level symptom ("My web app is not reachable")
* You suspect a configuration error in the orchestrator (OpenStack, OpenShift)
* The physical network is known to be healthy

Steps: Check orchestrator config (Neutron ports, K8s Services) -> Check OVN logical topology -> Check OVN southbound bindings -> Check OVS flows -> Check underlay connectivity.

*Bottom-up approach* - Start at the physical layer and work up. Best when:

* Multiple unrelated things are broken simultaneously
* A physical change was recently made (cable replacement, switch config, NIC replacement)
* You suspect an infrastructure-level problem

Steps: Check link status and physical connectivity -> Check OVS daemons and bridge config -> Check tunnel status -> Check OVN controller -> Check OVN database -> Check orchestrator.


[NOTE]
.Key Concept
====
Use top-down when one thing is broken. Use bottom-up when many things are broken. If you are unsure, bottom-up is safer because it rules out infrastructure problems first, but it takes longer.
====


=== Comprehensive Troubleshooting Checklist

Use this checklist to ensure you do not skip any step during an investigation. Not every step applies to every problem, but reviewing the list helps you avoid blind spots.

. Confirm the exact symptom (source, destination, protocol, port, direction)
. Check if the problem is reproducible right now or intermittent
. Check the timeline - when did it start, what changed
. Verify underlay connectivity between the involved hosts
. Verify OVS daemons are running on all involved hosts
. Verify OVN daemons are running (ovn-controller on computes, ovn-northd on controllers)
. Check OVS bridge and port configuration on the source host
. Check OVS bridge and port configuration on the destination host
. Verify the logical port is bound to the correct chassis in OVN SB
. Check OVN NB for correct logical topology (switch, router, ports, ACLs)
. Run ovn-trace for the failing traffic path
. Compare ovn-trace output with actual OVS flows on the datapath
. Use tcpdump on relevant interfaces to confirm where packets are and are not seen
. Check for recent log entries in ovn-controller, ovs-vswitchd, and the orchestrator
. If the problem is performance-related, check CPU, memory, conntrack table size, and flow table size
. Document your findings and resolution for the knowledge base

== 3. OVS Troubleshooting

=== Bridge and Port Configuration Problems

==== Port Not Showing in Bridge

*Symptoms:*

* Traffic to/from a VM or container is completely dead
* `ovs-vsctl show` does not list the expected port on the bridge
* The VM or container appears to have no network connectivity at all

*Diagnosis Steps:*

First, check what ports are currently on the bridge:

[source,bash]
----
sudo ovs-vsctl show
----

----
a1b2c3d4-e5f6-7890-abcd-ef1234567890
    Bridge br-int
        fail_mode: secure
        Port br-int
            Interface br-int
                type: internal
        Port "ovn-node2-0"
            Interface "ovn-node2-0"
                type: geneve
                options: {csum="true", key=flow, remote_ip="172.16.0.2"}
    ovs_version: "3.1.0"
----

Notice that the expected port (for example `tap12345678-90`) is not listed. Verify the interface exists at the OS level:

[source,bash]
----
ip link show tap12345678-90
----

----
15: tap12345678-90: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc fq_codel state UP mode DEFAULT group default qlen 1000
    link/ether fe:16:3e:aa:bb:cc brd ff:ff:ff:ff:ff:ff
----

The interface exists but is not attached to the bridge. Check if it was recently removed or never added:

[source,bash]
----
sudo journalctl -u ovs-vswitchd --since "1 hour ago" | grep "tap12345678-90"
----

----
Aug 05 14:32:10 compute-1 ovs-vswitchd[1234]: bridge br-int: added interface tap12345678-90 on port 15
Aug 05 14:45:22 compute-1 ovs-vswitchd[1234]: bridge br-int: deleting interface tap12345678-90
----

Check whether the orchestrator (e.g., Neutron, ovnkube) requested the port to be removed:

[source,bash]
----
sudo ovs-vsctl --columns=name,external_ids find Interface name=tap12345678-90
----

If it returns nothing, the port was indeed removed from OVS.

*Common Causes:*

* The VM or container was migrated or restarted and the port was not re-created
* The orchestrator agent (neutron-ovn-metadata-agent, ovnkube-node) crashed before creating the port
* A manual `ovs-vsctl del-port` command was accidentally run
* The interface name does not match what the orchestrator expects (naming mismatch)

*Resolution:*

If the port should exist and was accidentally removed, re-add it:

[source,bash]
----
sudo ovs-vsctl add-port br-int tap12345678-90
----

If the port needs specific external_ids for OVN to claim it:

[source,bash]
----
sudo ovs-vsctl set Interface tap12345678-90 \
  external_ids:iface-id="12345678-1234-1234-1234-123456789012"
----

However, in most production environments, you should not manually add ports. Instead, restart the orchestrator agent so it re-creates the port with the correct configuration:

[source,bash]
----
# For RHOSP
sudo systemctl restart tripleo_neutron_ovn_metadata_agent

# For OpenShift
oc delete pod -n openshift-ovn-kubernetes <ovnkube-node-pod>
----

==== Interface Shows Error or Down State

*Symptoms:*

* Port is present on the bridge but traffic does not flow
* `ovs-vsctl show` shows the port but `ovs-ofctl show` shows the port as `state: LINK_DOWN`

*Diagnosis Steps:*

[source,bash]
----
sudo ovs-ofctl show br-int | grep -A 2 "tap12345678"
----

----
 15(tap12345678-90): addr:fe:16:3e:aa:bb:cc
     config:     0
     state:      LINK_DOWN
----

The port is LINK_DOWN in OpenFlow. Check the Linux interface state:

[source,bash]
----
ip link show tap12345678-90
----

----
15: tap12345678-90: <BROADCAST,MULTICAST> mtu 1500 qdisc noop state DOWN mode DEFAULT group default qlen 1000
    link/ether fe:16:3e:aa:bb:cc brd ff:ff:ff:ff:ff:ff
----

The interface is DOWN (no UP flag). Check if the backing VM or container is actually running:

[source,bash]
----
sudo virsh list --all | grep instance-00001234
----

----
 15    instance-00001234              shut off
----

*Common Causes:*

* The VM is shut off or suspended
* The container is not running
* The tap interface was created but never brought up
* The QEMU process died

*Resolution:*

If the VM should be running, start it:

[source,bash]
----
sudo virsh start instance-00001234
----

If the interface simply needs to be brought up:

[source,bash]
----
sudo ip link set tap12345678-90 up
----

==== VLAN Mismatch

*Symptoms:*

* Connectivity works within a single host but not across hosts
* Traffic between VMs on different networks within the same host works, but cross-host traffic for a specific network fails
* tcpdump on the physical interface shows VLAN-tagged packets with an unexpected tag

*Diagnosis Steps:*

Check the VLAN configuration on the port:

[source,bash]
----
sudo ovs-vsctl show | grep -A 5 "Port.*phy"
----

----
        Port phy-br-ex
            Interface phy-br-ex
                type: patch
                options: {peer=int-br-ex}
----

Check if VLAN trunking is correctly configured on the physical bridge:

[source,bash]
----
sudo ovs-vsctl get port eth1 tag
sudo ovs-vsctl get port eth1 trunks
----

----
[]
[100, 200, 300]
----

If the port expects VLAN 150 but the trunk only allows 100, 200, 300, traffic for VLAN 150 will be silently dropped.

Check what VLAN tags OVN is using internally:

[source,bash]
----
sudo ovs-ofctl dump-flows br-int | grep "dl_vlan"
----

*Common Causes:*

* Physical switch trunking configuration does not include the required VLAN
* OVS port `tag` or `trunks` configuration is wrong
* The provider network VLAN configured in OpenStack does not match the physical switch

*Resolution:*

Add the missing VLAN to the trunk:

[source,bash]
----
sudo ovs-vsctl set port eth1 trunks=[100,150,200,300]
----

Or if this is a provider network issue, ensure the physical switch port is configured as a trunk carrying the required VLAN.


[WARNING]
====
In OVN-managed environments, OVN uses internal VLAN tags on br-int to identify traffic from different logical networks on the same host. These internal tags are not related to the physical VLAN tags. Do not confuse the two. The internal tags are managed entirely by ovn-controller and should not be manually modified.
====

=== Flow Table Problems

==== Missing Flows

*Symptoms:*

* Traffic is dropped at the OVS level
* `ovs-appctl ofproto/trace` shows the packet being dropped at a specific table
* Flow table has fewer entries than expected

*Diagnosis Steps:*

First, trace the packet through the OVS pipeline to find where it is dropped:

[source,bash]
----
sudo ovs-appctl ofproto/trace br-int \
  "in_port=5,dl_src=fa:16:3e:aa:bb:cc,dl_dst=fa:16:3e:dd:ee:ff,dl_type=0x0800,nw_src=10.0.0.5,nw_dst=10.0.0.10,nw_proto=1"
----

----
Flow: in_port=5,dl_vlan=0,dl_vlan_pcp=0,dl_src=fa:16:3e:aa:bb:cc,dl_dst=fa:16:3e:dd:ee:ff,dl_type=0x0800,nw_src=10.0.0.5,nw_dst=10.0.0.10,nw_proto=1,nw_tos=0,nw_ecn=0,nw_ttl=64

bridge("br-int")
-----------------
    0. in_port=5,vlan_tci=0x0000/0x1fff, priority 9000, cookie 0xdeadbeef
        set_field:0x5->reg13
        set_field:0x3->reg11
        set_field:0x2->reg12
        set_field:0x1->metadata
        set_field:0x1->reg14
        resubmit(,8)
    8. metadata=0x1,dl_src=fa:16:3e:aa:bb:cc, priority 50, cookie 0xdeadbeef
        resubmit(,9)
    9. No match.
        drop

Final flow: unchanged
Megaflow: recirc_id=0,eth,in_port=5,dl_src=fa:16:3e:aa:bb:cc,dl_dst=fa:16:3e:dd:ee:ff,dl_type=0x0800
Datapath actions: drop
----

The packet reaches table 9 and there is no matching flow - it gets dropped. Check what flows exist in table 9:

[source,bash]
----
sudo ovs-ofctl dump-flows br-int table=9
----

----
 cookie=0xdeadbeef, duration=86400.123s, table=9, n_packets=0, n_bytes=0, priority=0,metadata=0x1 actions=resubmit(,10)
----

There is a table-miss flow (priority 0) that should catch all traffic for this metadata value and send it to table 10. But our trace said "No match" at table 9. This could mean the metadata was set differently than expected, or the flow expired.

Check if ovn-controller is running and programming flows:

[source,bash]
----
sudo ovn-appctl -t ovn-controller connection-status
----

----
connected
----

[source,bash]
----
sudo ovn-appctl -t ovn-controller debug/status
----

If ovn-controller is connected but flows are missing, force a recompute:

[source,bash]
----
sudo ovn-appctl -t ovn-controller recompute
----

Then re-check the flows:

[source,bash]
----
sudo ovs-ofctl dump-flows br-int table=9 | wc -l
----

*Common Causes:*

* ovn-controller crashed or disconnected and flows were not reprogrammed after restart
* A flow recompute is needed after a database change
* The OVN southbound database is missing the logical flows for this datapath
* A race condition during port creation - the port was bound before its flows were fully installed

*Resolution:*

Force ovn-controller to recompute all flows:

[source,bash]
----
sudo ovn-appctl -t ovn-controller recompute
----

If that does not work, restart ovn-controller:

[source,bash]
----
sudo systemctl restart ovn-controller
----

If flows are still missing after restart, the problem is likely in the OVN southbound database. Check the logical flows:

[source,bash]
----
sudo ovn-sbctl lflow-list <datapath-name> | head -50
----

==== Flow Loops

*Symptoms:*

* High CPU usage on ovs-vswitchd
* Packets are endlessly resubmitted between tables
* `ovs-appctl ofproto/trace` output is very long and shows the same tables being visited repeatedly

*Diagnosis Steps:*

Run a trace and look for repeated table visits:

[source,bash]
----
sudo ovs-appctl ofproto/trace br-int \
  "in_port=5,dl_src=fa:16:3e:aa:bb:cc,dl_dst=fa:16:3e:dd:ee:ff,dl_type=0x0800,nw_src=10.0.0.5,nw_dst=10.0.0.10" 2>&1 | grep "resubmit" | head -30
----

If you see the same table numbers appearing repeatedly (e.g., table 20 -> table 25 -> table 20 -> table 25), there is a flow loop.

*Common Causes:*

* Manual flow insertion that conflicts with OVN-programmed flows
* Bug in ovn-controller flow generation (rare, but it happens)
* Two different OVN controllers programming conflicting flows on the same bridge

*Resolution:*

Check if there are manually added flows:

[source,bash]
----
sudo ovs-ofctl dump-flows br-int | grep "cookie=0x0"
----

Flows with cookie=0x0 (or a cookie that does not match OVN's pattern) are likely manually added. Remove them:

[source,bash]
----
sudo ovs-ofctl del-flows br-int cookie=0x0/-1
----


[WARNING]
====
Never manually add flows to br-int in an OVN-managed environment. ovn-controller is the sole owner of the flows on br-int. Manually added flows will conflict with OVN's flow programming and cause unpredictable behavior.
====

=== Tunnel Connectivity Issues

==== Geneve/VXLAN Tunnel Not Established

*Symptoms:*

* Cross-host connectivity is completely broken

==== Tunnel MTU Problems

*Symptoms:*

* Small packets (pings with default size) work, but large packets fail
* TCP connections establish (SYN/SYN-ACK are small) but stall when data transfer begins
* `ping -s 1400 <destination>` fails but `ping -s 100 <destination>` succeeds

*Diagnosis Steps:*

Test with different packet sizes to find the MTU boundary:

[source,bash]
----
# Inside the VM or container
ping -c 3 -M do -s 1400 10.0.0.10
----

----
PING 10.0.0.10 (10.0.0.10) 1400(1428) bytes of data.
From 10.0.0.5 icmp_seq=1 Frag needed and DF set (mtu = 1442)

--- 10.0.0.10 ping statistics ---
1 packets transmitted, 0 received, +1 errors, 100% packet loss, time 0ms
----

The kernel is telling us the path MTU is 1442. Geneve encapsulation adds approximately 58 bytes of overhead (14 Ethernet + 20 IP + 8 UDP + 8 Geneve + 8 options). If the physical network MTU is 1500, the maximum VM MTU is 1500 - 58 = 1442.

Check the physical interface MTU:

[source,bash]
----
ip link show eth0 | grep mtu
----

----
2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc fq_codel state UP mode DEFAULT group default qlen 1000
----

Check the tunnel interface MTU:

[source,bash]
----
ip link show genev_sys_6081 | grep mtu
----

----
3: genev_sys_6081: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 65000 qdisc noqueue master ovs-system state UNKNOWN mode DEFAULT group default qlen 1000
----

*Common Causes:*

* Physical network MTU is 1500 but no adjustment was made for tunnel overhead
* Some physical switches in the path have a smaller MTU
* Jumbo frames were configured on some links but not all

*Resolution:*

Option 1: Increase physical network MTU to accommodate tunnel overhead:

[source,bash]
----
# On all hypervisors and physical switches in the tunnel network path
sudo ip link set eth0 mtu 9000
----

Option 2: Decrease VM/container MTU to fit inside the physical MTU:

For OpenStack, set the network MTU:

[source,bash]
----
openstack network set --mtu 1442 my-network
----

For OVN DHCP, ensure the MTU option is advertised:

[source,bash]
----
sudo ovn-nbctl set Logical_Switch_Port <port> options:mtu=1442
----


[NOTE]
.Key Concept
====
The golden rule of tunnel MTU: inner MTU + tunnel overhead must be less than or equal to outer MTU. For Geneve, the overhead is typically 58 bytes. For VXLAN, it is 50 bytes. If you are unsure, set the inner MTU to 1400 - it is conservative but safe.
====

==== Conntrack Table Exhaustion

*Symptoms:*

* New connections fail while existing connections continue to work
* `dmesg` shows `nf_conntrack: table full, dropping packet`
* Stateful ACLs / security groups stop allowing new connections

*Diagnosis Steps:*

Check the conntrack table size:

[source,bash]

----

----
262144
----

Check the conntrack table limit:

[source,bash]
----

----

----

----

The table is full. Check what is filling it:

[source,bash]
----

----

----
 185234 tcp
  52341 udp
  24569 icmp
----

Find the top talkers:

[source,bash]
----

  45234 src=10.0.0.5

  18976 src=10.0.0.8
----

[source,bash]
----
sudo conntrack -L -p tcp --state TIME_WAIT | wc -l
----

* Application opening many short-lived connections without closing them properly
* Port scan or DDoS creating many conntrack entries
* Conntrack timeout too long (default TCP ESTABLISHED is 5 days)
* Conntrack limit too low for the workload
* OVN zone-based conntrack creating duplicate entries

[source,bash]

----

[source,bash]
----
sudo conntrack -D -s 10.0.0.5
----


[NOTE]
====
In OVN environments, conntrack is used by the logical firewall (ACLs/security groups). Every connection that passes through an ACL with `ct_state` matching creates a conntrack entry. High-throughput workloads with security groups can exhaust the conntrack table quickly.

==== Port Security Blocking Traffic

*Symptoms:*

* VM can receive traffic but cannot send certain types
* Only traffic matching the VM's configured MAC/IP addresses passes
* ARP or DHCP works but other traffic is dropped

*Diagnosis Steps:*

Check the port security configuration:

[source,bash]
----
sudo ovn-nbctl get Logical_Switch_Port port1 port_security
----

----
["fa:16:3e:aa:bb:cc 10.0.0.5"]
----

Port security is configured to allow only traffic from MAC `fa:16:3e:aa:bb:cc` with IP `10.0.0.5`. If the VM is trying to use a different IP (e.g., it has multiple IPs or is doing NAT), the traffic will be dropped.

Trace the traffic through OVN to see where port security drops it:

[source,bash]
----
sudo ovn-trace --detailed net1 \
  'inport=="port1" && eth.src==fa:16:3e:aa:bb:cc && eth.dst==fa:16:3e:dd:ee:ff && ip4.src==10.0.0.99 && ip4.dst==10.0.0.10 && ip.ttl==64'

----
ingress(dp="net1", inport="port1")
-----------------------------------
 0. ls_in_check_port_sec (northd.c:8234): 1, priority 50, uuid 12345678
    reg0[15] = check_in_port_sec(inport);
    next;
 1. ls_in_apply_port_sec (northd.c:8256): reg0[15] == 1, priority 50, uuid 23456789
    /* Packet fails port security check. */
    drop;
    /* output to "port1" */
----

The trace confirms that port security is dropping the packet because the source IP `10.0.0.99` does not match the allowed IP `10.0.0.5`.

*Common Causes:*

* VM has multiple IP addresses but only one is configured in port security
* VM is doing source NAT
* VM has a floating IP and the VM's actual IP does not match what port security expects
* Allowed address pairs were not configured for additional addresses

*Resolution:*

Add additional allowed addresses:

[source,bash]
----
sudo ovn-nbctl lsp-set-port-security port1 \

----

Or disable port security entirely (use with caution):

[source,bash]
----
sudo ovn-nbctl lsp-set-port-security port1
----

[source,bash]

openstack port set --allowed-address ip-address=10.0.0.99 <port-id>

=== ACLs Blocking Traffic

==== Security Groups Too Restrictive

*Symptoms:*

* Certain types of traffic are blocked while others work
* ICMP works but TCP does not (or vice versa)
* Traffic works in one direction but not the other

*Diagnosis Steps:*

List all ACLs on the logical switch:

[source,bash]
----
sudo ovn-nbctl acl-list net1
----

----
from-lport  1002 (inport == "port1" && ip4) allow-related
from-lport  1002 (inport == "port1" && ip6) allow-related
from-lport  1001 (inport == "port1" && ip4 && ip4.dst == 10.0.0.0/24 && tcp && tcp.dst == 80) allow-related
  to-lport  1002 (outport == "port1" && ip4 && ip4.src == 10.0.0.0/8) allow-related
  to-lport  1001 (outport == "port1" && ip4) drop
----

Read these ACLs carefully:

* From-lport (egress from the VM) with priority 1002: allow-related for all IPv4/IPv6
* From-lport with priority 1001: allow-related for TCP port 80 to 10.0.0.0/24
* To-lport (ingress to the VM) with priority 1002: allow-related from 10.0.0.0/8
* To-lport with priority 1001: drop all other IPv4 ingress

The problem here is the priority ordering. Priority 1002 rules are evaluated before priority 1001 rules. The to-lport allow-related rule at priority 1002 allows return traffic from 10.0.0.0/8, and the drop at priority 1001 drops everything else.

If the VM needs to receive traffic from outside 10.0.0.0/8, there is no allow rule for that.

Trace the failing traffic:

[source,bash]
----
sudo ovn-trace --detailed net1 \
  'inport=="external-port" && eth.src==fa:16:3e:xx:yy:zz && eth.dst==fa:16:3e:aa:bb:cc && ip4.src==192.168.1.100 && ip4.dst==10.0.0.5 && tcp.dst==22 && ip.ttl==64'
----

----
 ...
 16. ls_in_acl_eval (northd.c:12345): outport == "port1" && ip4, priority 1001, uuid 67890123
     /* drop */
     reg8[16] = 1;
     next;
 17. ls_in_acl_action (northd.c:12456): reg8[16] == 1, priority 100, uuid 78901234
     drop;
----

The trace confirms the packet is being dropped by the ACL at priority 1001.

*Common Causes:*

* Missing allow rule for the required traffic
* Using `allow` instead of `allow-related` (breaks return traffic for stateful connections)
* Wrong direction (from-lport vs to-lport)
* Priority conflicts - a lower-priority allow is shadowed by a higher-priority drop

*Resolution:*

Add the missing ACL rule:

[source,bash]
----
sudo ovn-nbctl acl-add net1 to-lport 1002 \
  'outport == "port1" && ip4 && tcp && tcp.dst == 22' allow-related
----

In OpenStack, add a security group rule:

[source,bash]
----
openstack security group rule create --protocol tcp --dst-port 22 --remote-ip 0.0.0.0/0 <security-group>
----

==== Missing allow-related

*Symptoms:*

* Outbound traffic from the VM works (SYN goes out)
* Return traffic (SYN-ACK) is dropped
* Unidirectional connectivity

*Diagnosis Steps:*

This is a classic stateful firewall issue. Check if the ACLs use `allow` instead of `allow-related`:

[source,bash]
----
sudo ovn-nbctl acl-list net1 | grep "allow$"
----

----
from-lport  1002 (inport == "port1" && ip4 && tcp && tcp.dst == 80) allow
----

This rule uses `allow` instead of `allow-related`. The `allow` action permits the outgoing packet but does not create a conntrack entry for the return traffic. The return SYN-ACK packet will need its own explicit allow rule in the to-lport direction.

*Common Causes:*

* ACL was created with `allow` instead of `allow-related`
* Misunderstanding of stateful vs stateless ACLs in OVN

*Resolution:*

Change the ACL to use `allow-related`:

[source,bash]
----
# Remove the old rule
sudo ovn-nbctl acl-del net1 from-lport 1002 \
  'inport == "port1" && ip4 && tcp && tcp.dst == 80'

# Add the corrected rule
sudo ovn-nbctl acl-add net1 from-lport 1002 \
  'inport == "port1" && ip4 && tcp && tcp.dst == 80' allow-related
----


[NOTE]
.Key Concept
====
In OVN, `allow-related` creates a conntrack entry for the matched traffic and automatically allows return traffic that belongs to the same connection. Always use `allow-related` for stateful traffic (TCP, UDP with reply). Use `allow` only for stateless traffic like broadcasts or when you explicitly want one-way rules.
====

==== Floating IP Not Working After Migration

*Symptoms:*

* Floating IP was working before VM migration, stopped working after
* External clients cannot reach the VM via the floating IP
* The VM can still reach the internet (SNAT works)

*Diagnosis Steps:*

Check where the port is now bound:

[source,bash]
----
sudo ovn-sbctl find Port_Binding logical_port=port1 | grep chassis
----

----
chassis             : d5e6f7a8-b9c0-1234-def0-567890123456
----

[source,bash]
----
sudo ovn-sbctl get Chassis d5e6f7a8-b9c0-1234-def0-567890123456 name
----

----
"compute-2"
----

The port migrated to compute-2. Check the NAT rule:

[source,bash]
----
sudo ovn-nbctl lr-nat-list router1 | grep "10.0.0.5"
----

----
dnat_and_snat    172.16.0.101       10.0.0.5              fa:16:3e:aa:bb:cc    port1
----

The NAT rule exists and references `port1` in the `logical_port` column - this is for distributed NAT. Check the gateway chassis:

[source,bash]
----
sudo ovn-nbctl list Gateway_Chassis | grep -A 3 "router1-external"
----

Check if the gateway chassis is aware of the migration. Verify that gratuitous ARP was sent for the floating IP:

[source,bash]
----
# On the gateway chassis node, check recent ARP activity
sudo tcpdump -i br-ex -nn arp | grep 172.16.0.101
----

If no gratuitous ARP was sent, the upstream physical network still has the old ARP entry pointing to the previous host.

*Common Causes:*

* Gratuitous ARP not sent after migration, so the upstream switch has a stale ARP entry
* The NAT rule's logical_port was not updated (in some older versions)
* The gateway chassis is not reachable from the new compute node
* The external bridge (br-ex) is not properly configured on the new compute node

*Resolution:*

Force a gratuitous ARP from OVN:

[source,bash]
----
# Trigger a port update to refresh ARP
sudo ovn-nbctl set Logical_Switch_Port port1 options:requested-chassis=compute-2
----

If the upstream router has a stale ARP cache, clear it on the upstream router or wait for the ARP timeout.

Verify the external bridge connectivity on the new compute node:

[source,bash]
----
# On compute-2
sudo ovs-vsctl show | grep -A 5 "br-ex"
----


[NOTE]
.Key Concept
====
When a VM with a floating IP (DNAT) migrates, the upstream physical network needs to learn that the floating IP is now reachable through a different host. OVN sends a gratuitous ARP for this purpose, but if the gratuitous ARP is lost or the upstream switch does not honor it, external traffic continues to be sent to the old host.

== 6. Real-World Scenarios

=== Scenario 1: VM-to-VM Connectivity Failure Across Compute Nodes

*Customer Report:*

"We have two VMs - vm-web (10.0.0.5 on compute-1) and vm-db (10.0.0.10 on compute-2) - both on the same network 'internal-net'. They were communicating fine until yesterday afternoon. Now vm-web cannot ping vm-db. Both VMs can ping their default gateway (10.0.0.1). Other VMs on the same network can reach vm-db from compute-2 but not from compute-1. We did not make any changes."

*Investigation Steps:*

Step 1: Verify the symptom and scope.

[source,bash]
----
# From inside vm-web
ping -c 3 10.0.0.10
----

----
PING 10.0.0.10 (10.0.0.10) 56(84) bytes of data.
From 10.0.0.5 icmp_seq=1 Destination Host Unreachable
From 10.0.0.5 icmp_seq=2 Destination Host Unreachable
From 10.0.0.5 icmp_seq=3 Destination Host Unreachable
----

Confirmed. Can vm-web reach its gateway?

[source,bash]
----
ping -c 3 10.0.0.1
----

----
PING 10.0.0.1 (10.0.0.1) 56(84) bytes of data.
64 bytes from 10.0.0.1: icmp_seq=1 ttl=254 time=0.345 ms
64 bytes from 10.0.0.1: icmp_seq=2 ttl=254 time=0.234 ms
----

Gateway is reachable. Since both VMs are on the same L2 network, traffic should go directly through the tunnel without routing. This points to a tunnel issue between compute-1 and compute-2.

Step 2: Check the tunnel from compute-1 to compute-2.

[source,bash]
----
# On compute-1
sudo ovs-vsctl show | grep -A 4 "compute-2\|node2"
----

----
        Port "ovn-comput-0"
            Interface "ovn-comput-0"
                type: geneve
                options: {csum="true", key=flow, remote_ip="172.16.0.2"}
----

The tunnel port exists and points to 172.16.0.2. Test underlay connectivity:

[source,bash]
----
ping -c 3 172.16.0.2
----

----
PING 172.16.0.2 (172.16.0.2) 56(84) bytes of data.
64 bytes from 172.16.0.2: icmp_seq=1 ttl=64 time=0.456 ms
64 bytes from 172.16.0.2: icmp_seq=2 ttl=64 time=0.345 ms
----

Underlay connectivity is fine. So the tunnel endpoint is reachable but VM traffic is not flowing.

Step 3: Check if Geneve traffic is being sent and received.

[source,bash]
----
# On compute-1, capture Geneve traffic to compute-2
sudo tcpdump -i eth0 -nn "host 172.16.0.2 and port 6081" -c 5
----

While tcpdump is running, send a ping from vm-web:

----
15:45:01.123456 IP 172.16.0.1.55432 > 172.16.0.2.6081: Geneve, Flags [C], vni 0x5, proto TEB: fa:16:3e:aa:bb:cc > fa:16:3e:dd:ee:ff, ethertype IPv4, length 98: 10.0.0.5 > 10.0.0.10: ICMP echo request, id 1234, seq 1, length 64
----

Packets are leaving compute-1 over the tunnel. Check if they arrive on compute-2:

[source,bash]
----
# On compute-2
sudo tcpdump -i eth0 -nn "host 172.16.0.1 and port 6081" -c 5
----

----
(no output - no packets captured)
----

Geneve packets are leaving compute-1 but not arriving at compute-2. This means something in the physical network between compute-1 and compute-2 is dropping the packets.

Step 4: Check the physical network path.

[source,bash]
----
traceroute -n 172.16.0.2
----

----
traceroute to 172.16.0.2 (172.16.0.2), 30 hops max, 60 byte packets
 1  172.16.0.254 (172.16.0.254)  0.345 ms  0.234 ms  0.123 ms
 2  172.16.0.2 (172.16.0.2)  0.456 ms  0.345 ms  0.234 ms
----

The path goes through 172.16.0.254, which is a physical switch/router. The ICMP traceroute works (small packets), but Geneve packets do not. This suggests an MTU issue or a firewall on the intermediate device.

Step 5: Test with different packet sizes.

[source,bash]
----
ping -c 3 -M do -s 1450 172.16.0.2
----

----
PING 172.16.0.2 (172.16.0.2) 1450(1478) bytes of data.
From 172.16.0.254 icmp_seq=1 Frag needed and DF set (mtu = 1400)
----

The intermediate switch has an MTU of only 1400. Geneve-encapsulated packets (which are at least 1500 + 58 = 1558 bytes for full-size inner packets) are being dropped because they exceed the path MTU.

*Root Cause:*

The physical switch at 172.16.0.254 was replaced yesterday during maintenance ("we did not make any changes" often means "we did not make any changes to the virtual infrastructure"). The replacement switch has a default MTU of 1400 instead of 9000 (jumbo frames) like the old switch.

*Resolution:*

Option 1 (preferred): Configure the physical switch to support jumbo frames:

----
# On the physical switch (example for Cisco)
interface GigabitEthernet0/1
  mtu 9000
----

Option 2 (temporary): Reduce the VM MTU to accommodate the smaller physical MTU:

[source,bash]
----
# Calculate: 1400 (physical) - 58 (Geneve overhead) = 1342
openstack network set --mtu 1342 internal-net

# Update DHCP options
sudo ovn-nbctl set DHCP_Options <uuid> options:mtu="1342"
----

*Prevention:*

* Document the required physical network MTU for tunnel traffic
* Add MTU validation to infrastructure change procedures
* Monitor encapsulated packet drop counts on physical switches
* Set up end-to-end MTU probes between all compute nodes

[IMPORTANT]
.Key Diagnostic Insight: ovn-trace Shows Success, But Packets Still Fail
====
`ovn-trace` operates at the *logical layer only*. It traces packets through OVN logical flows and shows successful delivery to the output port. But it has *no visibility* into the physical transport layer (Geneve tunnels, host firewall rules, MTU issues).

When `ovn-trace` says the packet is delivered but connectivity fails, the problem is between the logical and physical layers. Use *BFD (Bidirectional Forwarding Detection)* to bridge this gap:

[source]
----
# Check BFD status on a compute node (real output from RHOSP 17.1)
sudo ovs-vsctl show | grep -A 5 "bfd_status"

    Port ovn-36ab4d-0
        Interface ovn-36ab4d-0
            type: geneve
            options: {csum="true", key=flow, remote_ip="172.20.0.35"}
            bfd_status: {diagnostic="Control Detection Time Expired",
                         flap_count="2", forwarding="false",
                         remote_state=down, state=down}           <1>
----
<1> `state=down` and `forwarding=false` - BFD detected the tunnel is down even though the Geneve port exists

*Diagnostic decision tree when ovn-trace succeeds but traffic fails:*

. `ovn-trace` shows output -> logical layer OK
. `ping` fails -> physical layer problem
. Check BFD status (`ovs-vsctl show | grep -A 5 bfd_status`) -> tunnel health
. If BFD is down: check `iptables -L -n | grep 6081`, MTU, physical network path
. If no BFD: `tcpdump -i <NIC> -nn udp port 6081` to verify Geneve packets
====

  ssh $node "echo 'net.netfilter.nf_conntrack_tcp_timeout_time_wait = 30' | sudo tee -a /etc/sysctl.d/99-conntrack.conf"
done

[source,bash]

1048576
----

The conntrack table now has plenty of headroom. Ping latency should return to sub-millisecond within a few minutes as the system stabilizes.

*Prevention:*

* Plan conntrack and flow table capacity as part of scale-up planning
* Set conntrack limits proportional to the expected number of VMs and connections
* Monitor conntrack usage, OVS CPU usage, and flow table sizes with alerting
* Perform load testing before production scale-up to identify bottlenecks
* Document the conntrack and OVS tuning parameters for each environment size

== Summary

Troubleshooting OVS and OVN is a skill that improves with practice. The key principles to remember:

. *Be systematic* - Follow a methodology. Do not guess randomly.
. *Isolate the layer* - Determine if the problem is physical, OVS, OVN, or application.
. *Use the right tool* - `ovn-trace` for logical pipeline issues, `ovs-appctl ofproto/trace` for OVS flow issues, `tcpdump` for packet-level verification.
. *Check the basics first* - Is the daemon running? Is the port bound? Is the tunnel up? 90% of problems are configuration issues.
. *Document everything* - Keep notes on what you checked, what you found, and what you changed. This helps when the problem recurs and when handing off to another engineer.
. *Know your environment* - RHOSP, RHOSO, and OCP each have different deployment patterns. Know where to find logs and how to access OVN commands in each.

The diagnostic commands and scenarios in this module cover the vast majority of issues you will encounter in the field. Use this module as a reference during live investigations - it was designed to give you the exact command to run for each situation.
