= Scenario 02: Intermittent Packet Loss on Overlay Network

== The Problem

*Customer report:* "VMs experience intermittent packet loss when communicating across
compute nodes. Same-node VM communication works fine. Large file transfers fail but small
pings usually work."

The customer observes that SCP transfers between VMs on different compute nodes stall and
eventually time out, but simple pings (default 64 bytes) succeed most of the time. Applications
relying on TCP connections across nodes experience frequent retransmissions and timeouts.


[IMPORTANT]
.RHOSP 17.1: Containerized OVN Commands
====
In RHOSP 17.1, OVN databases run inside Pacemaker-managed containers. All `ovn-nbctl` and `ovn-sbctl` commands shown in this scenario must be executed via `podman exec` on the controller node. For example:

* `ovn-nbctl show` becomes `sudo podman exec -it ovn_cluster_north_db_server ovn-nbctl --no-leader-only show`
* `ovn-sbctl show` becomes `sudo podman exec -it ovn_cluster_south_db_server ovn-sbctl --no-leader-only show`

For brevity, this scenario shows the bare commands. Refer to xref:12-troubleshooting.adoc#_rhosp_red_hat_openstack_platform[Module 12: RHOSP Product-Specific Troubleshooting] for the full containerized command syntax.
====

== Step-by-Step Investigation

=== Step 1: Verify Symptoms with Different Ping Sizes

*Why:* Intermittent packet loss that correlates with packet size is a classic MTU issue
indicator. By testing with different sizes, we can confirm the pattern and find the exact
threshold.

First, try a standard ping from VM-A to VM-B:

*Finding:* Standard ping works perfectly - 0% packet loss. This is expected because the
default ping sends only 64 bytes of ICMP data (84 bytes total with headers).

Now try with a larger payload - 1400 bytes, with the Don't Fragment (DF) bit set:

[source,bash]
----
[root@vm-a ~]# ping -s 1400 -c 5 -M do 192.168.50.20

*Finding:* 100% packet loss with 1400-byte payload. The `-M do` flag sets the Don't Fragment
bit, which prevents the kernel from fragmenting the packet. This is critical for diagnosing
MTU issues because without it, the kernel might fragment the packet and mask the problem.


[NOTE]
.Key Concept
====
The `-M do` flag sets the IP Don't Fragment (DF) bit. This is essential for MTU troubleshooting because it forces the packet to be dropped rather than fragmented if it exceeds the path MTU. Without this flag, Linux might silently fragment the packet, making MTU issues harder to detect.
====


Try with 1300 bytes:

[NOTE]
====

====

=== Step 2: Identify the MTU Issue Pattern

*Why:* We need to understand why the effective MTU is 1442 instead of the expected 1500.
The difference (58 bytes) is suspiciously close to Geneve encapsulation overhead.

The pattern we see:

* Packets up to 1442 bytes: *work*
* Packets above 1442 bytes: *fail*
* Same-node communication: *works at any size* (no encapsulation needed)
* Cross-node communication: *fails above 1442* (requires Geneve encapsulation)

This strongly points to an MTU mismatch between the VM's configured MTU (1500) and the
actual available MTU after Geneve encapsulation.


[NOTE]
.Key Concept
====
When a packet travels between VMs on different compute nodes, it must be encapsulated in a Geneve tunnel. The encapsulation adds headers around the original packet, making it larger. If the physical network cannot carry the enlarged packet, it gets dropped. This is the most common cause of "large packets fail, small packets work" symptoms in overlay networks.
====


'''

=== Step 3: Check VM MTU

*Why:* We need to confirm what MTU the VMs are configured with and whether it matches
the network's capabilities.

[source,bash]
----
[root@vm-a ~]# ip link show eth0
----

----
2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc fq_codel state UP mode DEFAULT group default qlen 1000
    link/ether fa:16:3e:aa:11:01 brd ff:ff:ff:ff:ff:ff
    altname enp0s3
----

*Finding:* The VM's MTU is 1500. This is the standard Ethernet MTU, but it does NOT
account for Geneve encapsulation overhead. The VM believes it can send 1500-byte frames,
but once encapsulated, these become ~1558-byte frames that the physical network (also MTU
1500) cannot carry.

Check the route MTU as well:

[source,bash]
----
[root@vm-a ~]# ip route get 192.168.50.20
----

----
192.168.50.20 dev eth0 src 192.168.50.10 uid 0
    cache
----

*Finding:* No specific route MTU is set, so the interface MTU (1500) is used. There is
no PMTUD-adjusted cached route with a lower MTU either, which tells us PMTUD is not
functioning (we will investigate this later).

'''

[NOTE]
====
In Neutron, the `mtu` field on a network represents the maximum transmission unit that VMs should use. For overlay networks, this should be the physical MTU minus the encapsulation overhead. Neutron can calculate this automatically based on the `global_physnet_mtu` and `path_mtu` settings in `ml2_conf.ini`, but if these are misconfigured, the wrong MTU gets advertised.
====


Check the Neutron ML2 configuration:

[source,bash]
----
[root@controller-0 ~]# grep -E "^(global_physnet_mtu|path_mtu)" /var/lib/config-data/puppet-generated/neutron/etc/neutron/plugins/ml2/ml2_conf.ini
----

----

path_mtu = 1500
----

*Finding:* `global_physnet_mtu` is set to 1500 (the physical network MTU) and `path_mtu`
is also 1500. However, Neutron should subtract the Geneve overhead from `path_mtu` to
calculate the tenant network MTU. If `path_mtu` equals `global_physnet_mtu`, Neutron may
not be subtracting the overhead correctly, or the overhead calculation is not being applied.

=== Step 6: Calculate the Real MTU

*Why:* To understand exactly how much overhead Geneve encapsulation adds, we need to break
down the encapsulated packet structure.

Here is the anatomy of a Geneve-encapsulated packet:

----
+------------------------------------------------------------------+
|                    PHYSICAL NETWORK FRAME                         |
|                                                                   |
|  +------------------------------------------------------------+  |
|  | Outer Ethernet Header                          | 14 bytes   |  |
|  +------------------------------------------------------------+  |
|  | Outer IP Header (IPv4)                         | 20 bytes   |  |
|  +------------------------------------------------------------+  |
|  | Outer UDP Header (dst port 6081)               |  8 bytes   |  |
|  +------------------------------------------------------------+  |
|  | Geneve Header (base)                           |  8 bytes   |  |
|  +------------------------------------------------------------+  |
|  | Geneve Options (variable, OVN uses ~8 bytes)   |  8 bytes   |  |
|  +------------------------------------------------------------+  |
|  |                                                             |  |
|  |              ORIGINAL VM PACKET (inner)                     |  |
|  |                                                             |  |
|  |  +-------------------------------------------------------+ |  |
|  |  | Inner Ethernet Header                     | 14 bytes   | |  |
|  |  +-------------------------------------------------------+ |  |
|  |  | Inner IP Header                           | 20 bytes   | |  |
|  |  +-------------------------------------------------------+ |  |
|  |  | Inner TCP/UDP/ICMP Header                 | 8-20 bytes | |  |
|  |  +-------------------------------------------------------+ |  |
|  |  | Payload Data                              | variable   | |  |
|  |  +-------------------------------------------------------+ |  |
|  |                                                             |  |
|  +------------------------------------------------------------+  |
+------------------------------------------------------------------+

Geneve Encapsulation Overhead:
  Outer Ethernet:     14 bytes
  Outer IPv4:         20 bytes
  Outer UDP:           8 bytes
  Geneve base:         8 bytes
  Geneve options:      8 bytes (OVN typically uses 4-8 bytes for VNI metadata)
  ----------------------------
  Total overhead:     58 bytes
----

*Calculation:*

----
Physical Network MTU:           1500 bytes
Geneve overhead:              -   58 bytes
                              -----------
Maximum inner frame size:       1442 bytes

The inner frame includes:
  Inner Ethernet header:         14 bytes
  Maximum inner IP packet:      1428 bytes (1442 - 14)

This means the VM's MTU should be: 1442 bytes
(MTU refers to the maximum IP packet size, which includes the Ethernet payload minus the Ethernet header)

Actually, since OVS handles the inner Ethernet header:
  Physical MTU:                 1500 bytes
  Geneve overhead:            -   58 bytes
  Available for inner frame:    1442 bytes
  Inner Ethernet header:      -   14 bytes
  Maximum IP packet (VM MTU):   1428 bytes

Wait - let's be more precise. The physical MTU (1500) limits the total size of the
outer IP packet. So:

  Outer IP packet max size:     1500 bytes (physical MTU, excluding outer Ethernet)
  Outer IP header:            -   20 bytes
  Outer UDP header:           -    8 bytes
  Geneve base header:         -    8 bytes
  Geneve options:             -    8 bytes
  Available for inner frame:    1456 bytes
  Inner Ethernet header:      -   14 bytes
  Maximum inner IP packet:      1442 bytes
----


[NOTE]
.Key Concept
====
The physical network MTU (1500) limits the *outer IP packet* size. Subtracting the outer IP header (20), UDP header (8), and Geneve headers (8+8=16) from 1500 gives 1456 bytes for the inner Ethernet frame. Subtracting the inner Ethernet header (14 bytes) leaves 1442 bytes as the maximum inner IP packet - this is what the VM's MTU should be set to.
====


This matches our ping test results exactly: packets up to 1442 bytes worked, anything
larger was dropped.


[WARNING]
====
The exact Geneve overhead can vary depending on the Geneve options used. OVN typically uses 4-8 bytes of options. Always verify the actual overhead in your environment rather than assuming a fixed value. The safe conservative value for VM MTU on a 1500-byte physical network is *1442*.
====


'''

=== Step 7: Check if PMTUD is Working

*Why:* Path MTU Discovery (PMTUD) should automatically detect the MTU limitation and
signal VMs to reduce their packet size. If PMTUD is working, large packets would be
fragmented or the sending VM would learn the correct MTU. The fact that packets are
being silently dropped suggests PMTUD is broken.


[NOTE]
.Key Concept
====
Path MTU Discovery (PMTUD) works by sending packets with the Don't Fragment (DF) bit set. When a router or switch along the path cannot forward the packet because it exceeds the link MTU, it should send back an ICMP Type 3, Code 4 message ("Fragmentation Needed and Don't Fragment was Set") containing the next-hop MTU. The sender then reduces its packet size accordingly.
====


Check for ICMP "Fragmentation Needed" messages on the source compute node:

[source,bash]
----
[root@compute-0 ~]# tcpdump -i any -n 'icmp[icmptype] == 3 and icmp[icmpcode] == 4' -c 5 &
[1] 12345

[root@vm-a ~]# ping -s 1422 -c 5 -M do 192.168.50.20
----

----
PING 192.168.50.20 (192.168.50.20) 1422(1450) bytes of data.

--- 192.168.50.20 ping statistics ---
5 packets transmitted, 0 received, 100% packet loss, time 4003ms
----

Back on compute-0, check the tcpdump:

[source,bash]
----
[root@compute-0 ~]# fg
tcpdump -i any -n 'icmp[icmptype] == 3 and icmp[icmpcode] == 4' -c 5
^C
0 packets captured
0 packets received by filter
0 packets dropped by kernel
----

*Finding:* No ICMP "Fragmentation Needed" messages are being received. This means PMTUD
is not functioning. The oversized Geneve-encapsulated packets are being silently dropped
somewhere in the physical network without generating the required ICMP responses.


[WARNING]
====
Many network administrators filter ICMP traffic for security reasons. While this can block some attack vectors, filtering ICMP Type 3, Code 4 breaks Path MTU Discovery and causes exactly the symptoms we are seeing. ICMP Type 3, Code 4 should NEVER be filtered in a production network.
====


Check if there is any ICMP filtering on the compute node itself:

[source,bash]
----
[root@compute-0 ~]# iptables -L -n | grep -i icmp
----

----
(no output - no ICMP filtering on the compute node)
----

[source,bash]
----
[root@compute-0 ~]# nft list ruleset | grep -i icmp
----

----
(no output - no ICMP filtering via nftables either)
----

*Finding:* The compute nodes themselves are not filtering ICMP. The filtering must be
happening on a network device between the compute nodes (physical switch, firewall, or
router).

'''

*Why:* We need to confirm that the physical network does not support jumbo frames and

----

expansion-rom-version:

----

[source,bash]
----

----

----

    link/ether 52:54:00:a1:b2:c3 brd ff:ff:ff:ff:ff:ff
    promiscuity 1  allmulti 1 minmtu 68 maxmtu 9978
    openvswitch master ovs-system addrgenmode eui64 numtxqueues 8 numrxqueues 8 gso_max_size 65536 gso_max_segs 65535 tso_max_size 65536 tso_max_segs 65535 gro_max_size 65536
----

*Finding:* The NIC supports up to MTU 9978 (`maxmtu 9978`), so the hardware is capable
of jumbo frames. However, the current MTU is set to 1500. This means either the physical
network switches do not support jumbo frames, or jumbo frames were never configured.

Verify end-to-end physical path MTU by sending a large packet between compute nodes at the
physical layer:

[source,bash]
----
[root@compute-0 ~]# ping -s 8972 -c 3 -M do 10.0.0.22
----

----
PING 10.0.0.22 (10.0.0.22) 8972(9000) bytes of data.
ping: local error: message too long, mtu=1500

--- 10.0.0.22 ping statistics ---
3 packets transmitted, 0 received, +3 errors, 100% packet loss, time 2003ms
----

*Finding:* The physical network path between compute nodes has an MTU of 1500. Jumbo
frames are not configured on the physical network infrastructure. This confirms the root
cause.

'''

== Root Cause

The root cause is an *MTU mismatch* between the overlay network and the physical underlay:

. *Physical network MTU is 1500 bytes* - standard Ethernet, no jumbo frames configured

. *Geneve encapsulation adds ~58 bytes of overhead* per packet:
** Outer Ethernet: 14 bytes
** Outer IPv4: 20 bytes
** Outer UDP: 8 bytes
** Geneve base header: 8 bytes
** Geneve options: 8 bytes

. *VMs are configured with MTU 1500* because Neutron's network MTU was set to 1500
   without accounting for encapsulation overhead

. *Result:* When a VM sends a packet close to 1500 bytes, encapsulation inflates it
   to ~1558 bytes. The physical network cannot carry this frame, so it is silently dropped.

. *PMTUD is non-functional* because ICMP Type 3, Code 4 (Fragmentation Needed) messages
   are being filtered somewhere in the physical network path, preventing automatic MTU
   adjustment.

----
VM sends 1500-byte packet
        |
        v
   [OVS br-int on compute-0]
        |
        v
   [Geneve encapsulation: +58 bytes = 1558 bytes]
        |
        v
   [Physical NIC ens1f0: MTU 1500]
        |
        v
   PACKET DROPPED! (1558 > 1500)
   No ICMP "Frag Needed" sent back to VM (PMTUD broken)
----

'''

== Resolution

=== Option A: Increase Physical Network MTU (Preferred)

This is the preferred solution because it allows VMs to use the standard 1500-byte MTU
and provides headroom for encapsulation overhead.

*Step 1:* Configure jumbo frames on compute node physical NICs:

[source,bash]
----
[root@compute-0 ~]# ip link set ens1f0 mtu 9000
----

Make it persistent via NetworkManager:

[source,bash]
----
[root@compute-0 ~]# nmcli connection modify ens1f0 802-3-ethernet.mtu 9000
[root@compute-0 ~]# nmcli connection up ens1f0
----

Repeat on all compute nodes.


[WARNING]
====
You MUST configure jumbo frames on ALL devices in the path - compute node NICs, physical switches (all ports and VLANs), and any routers between compute nodes. If even one device in the path has MTU 1500, large packets will be dropped. Coordinate with the network team before making changes.
====


*Step 2:* Configure jumbo frames on physical switches:

This is network-vendor-specific. Example for a common switch:

----
interface GigabitEthernet1/0/1
  mtu 9216

interface Vlan100
  mtu 9216
----

*Step 3:* Verify end-to-end jumbo frame support:

[source,bash]
----
[root@compute-0 ~]# ping -s 8972 -c 5 -M do 10.0.0.22
----

----

'''

If jumbo frames cannot be configured on the physical network (a common constraint in
shared or legacy environments), reduce the VM MTU to account for Geneve overhead.

[source,bash]

(overcloud) [stack@undercloud ~]$ openstack network set --mtu 1442 data-net
----

'''

=== Fix PMTUD (Should Be Done Regardless of Option A or B)

Regardless of which MTU solution you choose, PMTUD should be functional for defense in depth.

Identify and fix the ICMP filtering in the physical network:

----
Required ICMP types that must NOT be filtered:

  ICMP Type 3, Code 4 - Fragmentation Needed / Packet Too Big
  ICMP Type 3, Code 0 - Destination Network Unreachable
  ICMP Type 3, Code 1 - Destination Host Unreachable
  ICMP Type 11          - Time Exceeded (needed for traceroute)
----

Example firewall rule to allow PMTUD (iptables syntax):

[source,bash]
----
iptables -A FORWARD -p icmp --icmp-type 3/4 -j ACCEPT
----

Example for nftables:

[source,bash]
----
nft add rule inet filter forward icmp type destination-unreachable accept
----

'''

== Prevention

=== 1. Always Account for Overlay Overhead When Setting MTU

Create a standard calculation for every deployment:

----
VM MTU = Physical MTU - Encapsulation Overhead

Encapsulation overheads:
  Geneve:  58 bytes (with typical OVN options)
  VXLAN:   50 bytes
  GRE:     42 bytes (without key)
  GRE+key: 46 bytes
----

=== 2. Document MTU Requirements in Deployment Guides

Include in every deployment runbook:

----
Pre-deployment MTU checklist:
[ ] Physical network MTU verified on all switches and routers
[ ] Compute node NIC MTU verified
[ ] Neutron global_physnet_mtu configured correctly
[ ] Neutron path_mtu configured correctly
[ ] Network MTU accounts for encapsulation overhead
[ ] DHCP offers verified with correct MTU
[ ] End-to-end large packet test performed
[ ] PMTUD verified functional (ICMP not filtered)
----

=== 3. Test with Large Packets During Deployment Validation

Add these tests to post-deployment validation:

[source,bash]
----
# Test from inside a VM to another VM on a different compute node:
ping -s 1414 -c 10 -M do <other-vm-ip>

# Test with iperf3 for throughput validation:
iperf3 -c <other-vm-ip> -t 30 -M 1400

# Test end-to-end physical network:
ping -s 8972 -c 10 -M do <other-compute-node-ip>   # Only if jumbo frames configured
----

=== 4. Monitor for MTU-Related Drops

Set up monitoring for interface drop counters:

[source,bash]
----
# Check for drops on Geneve tunnel interfaces:
ovs-vsctl list interface genev_sys_6081 | grep -E "statistics.*tx_dropped"

# Watch for increasing drop counters:
watch -n 5 'ip -s link show ens1f0 | grep -A1 TX'
----

== Key Takeaways

* **MTU mismatches are the most common cause of "large packets fail" symptoms in overlay
  networks.** Always account for encapsulation overhead when configuring network MTU.

* *The safe VM MTU for Geneve over a 1500-byte physical network is 1442 bytes.* This
  accounts for the ~58 bytes of Geneve encapsulation overhead.

* *PMTUD depends on ICMP Type 3 Code 4 messages.* Never filter these. If PMTUD is broken,
  MTU issues cause silent packet drops that are difficult to diagnose.

* *Always test with large packets during deployment.* A simple `ping -s 1414 -c 10 -M do`
  between VMs on different compute nodes will immediately reveal MTU problems.

* *Jumbo frames (MTU 9000) are the preferred solution* when the physical network supports
  them, as they provide ample headroom for encapsulation overhead while allowing VMs to use
  the standard 1500-byte MTU.
